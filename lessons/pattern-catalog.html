Pattern Catalog

One entry per principle and pattern, added as we learn it. Reread it before any design decision or interview.

The golden rule above every entry: a pattern is a named cure for a specific pain. If you cannot name the pain, you do not yet need the pattern.

?How to read an entry

Every entry answers the same questions in the same order, so entries can be compared side by side:

  • Intent: what it is, in one plain sentence.
  • The pain it cures: the specific problem that makes you reach for it.
  • Use it when…: the concrete signals that it fits.
  • Do NOT use it when…: the equally concrete signs that it is the wrong tool. Over-using patterns is the classic beginner mistake. So this field is never left thin.
  • The cost: the indirection or complexity it always adds. Nothing is free.
  • Relatives: what it resembles, and the one-line difference.
  • Seen in the wild: one place the JDK or a popular framework already uses it.
  • Where it lives: its kata package, and its home in the Smart Home Hub if it has one.

Single Responsibility Principle (SRP) principle

A class should have one reason to change. Put another way, it should answer to one group of people who might ask for changes.

The pain it cures
A "god class" serves several groups at once. One group's change quietly breaks another group's feature, often through a shared helper. Every change touches the same file. And the class is hard to test, because every test needs everything.
Use it when…
  • You cannot describe the class in one sentence without "and."
  • Different people (accounting, HR, the display designer, the installer) request changes to different parts of it.
  • Two methods serving different groups share a private helper.
  • Testing one behaviour forces you to set up, or capture output from, unrelated ones.
Do NOT use it when…
  • The parts always change together, for the same people. Splitting them just scatters one purpose across files.
  • The split would produce one-method classes that only forward calls ("anemic" fragments with no rules of their own).
  • The "reasons to change" are imagined. Wait for the second real request before splitting.
  • It is a short script or prototype that will be thrown away.
The cost
More classes and files. Wiring code somewhere (an assembly point like Main) to put the pieces together. Callers may have to know several objects instead of one. Finding your way around takes more hops.
Relatives
  • Cohesion (Lesson 04): SRP is cohesion turned into a rule, with "reason to change" as the measuring stick.
  • Interface Segregation (Lesson 08): the same idea, seen from the client's side. No client should depend on methods it does not use.
  • DRY (Lesson 11): SRP sometimes keeps look-alike code apart, because the copies change for different reasons (accidental duplication).
Seen in the wild
java.time keeps LocalDate (the date value and its arithmetic) separate from DateTimeFormatter (how a date looks as text). Display rules change for different reasons than calendar rules, so they live in different classes.
Where it lives
Kata: com.katas.srp (EmployeeData, PayCalculator, HoursReporter, EmployeeCsv; the god class in naive/Employee). Hub: Main split into home.HomeSetup (which devices), home.Hub (operating them) and report.HouseReport (how it looks). Lesson: 05.

Open/Closed Principle (OCP) principle

Code should be open for extension but closed for modification. Add new behaviour by adding new code, not by editing code that already works.

The pain it cures
A class must be opened and edited for every new variant. Usually the cause is an if-else (or switch) on a type name, repeated in several places. Every edit risks breaking the variants that already worked. Forgetting one ladder breaks the new one.
Use it when…
  • A second variant has arrived and more are clearly coming (shipping methods, house modes, payment providers).
  • The same ladder on a type name appears in more than one method or file.
  • New variants are requested by people other than the code's maintainers.
  • You want others (another team, a plugin, a test) to add behaviour without touching your code.
Do NOT use it when…
  • The set of variants is small and truly fixed (days of the week, on/off). A plain switch is clearer.
  • Only one variant exists so far. Wait for the second ("take the first bullet") so you know what really varies.
  • It is one local if-else that is not repeated and not growing.
  • The interface would be a guess about future needs (speculative generality).
The cost
More classes and files. Indirection: the rule for one variant is in its own file, not on the screen with the others. Loss of overview across variants. And it protects against only one chosen kind of change. A different kind, such as a new question every variant must answer, still means editing the interface and every implementation.
Relatives
  • SRP (Lesson 05) decides where code lives. OCP decides how it grows. Each variant class is also one responsibility.
  • Liskov Substitution (Lesson 07) is OCP's safety rule. New implementations must keep the contract the closed code trusts.
  • Dependency Inversion (Lesson 09) is the same "point the arrows at the contract" move, seen across a whole program.
  • Most patterns ahead are ready-made OCP variation points for one particular kind of change.
Seen in the wild
List.sort(Comparator): the JDK's sorting algorithm is closed. What "before" means is open. You supply it as a Comparator (e.g. Comparator.reverseOrder()). Plugin systems (browser extensions, IDE plugins) are OCP turned into products.
Where it lives
Kata: com.katas.ocp (ShippingMethod + four methods, ShippingQuoter; ladders in naive/ShippingQuoter; test-only PickupInStore). Hub: routines.Routine (AllOn, AllOff, KeepOnly) run by home.Hub.run. Lesson: 06.

Liskov Substitution Principle (LSP) principle

Code that works with a type must keep working with any subtype or implementation, without noticing the difference. Every substitute keeps every promise of the type it stands in for.

The pain it cures
Honest client code is written only against a type's promises. Then it is handed a subclass or implementation that claims the type but breaks one of its promises. The client breaks, or quietly gives wrong answers. Examples: Square in place of Rectangle, or a device that refuses turnOff().
Use it when…
  • Designing any class hierarchy or interface that has, or will have, more than one implementation.
  • Reviewing an override. Does it demand more? Promise less? Throw where the parent succeeded? Change state the parent promised to leave alone?
  • You see instanceof checks in client code, or overrides that throw UnsupportedOperationException or do nothing.
  • Others will implement your interface. Write the contract down and give them a contract test.
Do NOT use it when…
  • You are tempted to demand identical behaviour. Different behaviour inside the promise is the point of polymorphism.
  • You are writing contracts so detailed that no second implementation could fit them.
  • A type has one implementation and no more are expected. Clear names and ordinary tests are enough, without a formal contract suite.
  • You are tempted to ban inheritance outright out of fear. Fix the contract instead.
The cost
Contracts must be written down and kept in step with the code. Contract tests add an extra (abstract) test class per contract. Sometimes an "obvious" inheritance must be given up for siblings or immutability, which can feel less natural at first.
Relatives
  • OCP (Lesson 06): LSP is what makes plugging new classes into closed code safe.
  • Fragile base class (Lesson 03): the danger from the parent's side. LSP is the danger from the child's side.
  • Interface Segregation (Lesson 08): the usual cure for refused bequests. It makes contracts small enough for every implementer to keep.
  • Design by Contract (Meyer): the pre-/postcondition toolset LSP is stated in.
Seen in the wild
java.util.List.add is documented as an "optional operation" that may throw UnsupportedOperationException. So List.of(...) can refuse it and still be a List. It is a refused bequest, made legal by writing it into the contract. java.util.Stack extends Vector is an older mistake. Its documentation now points to Deque.
Where it lives
Kata: com.katas.lsp (Shape, immutable Rectangle and Square as siblings, AreaTotaller; the broken hierarchy in naive/). Hub: devices.Device's written contract, checked by DeviceContractTest for Light, Thermostat and LoggedDevice. Lesson: 07.

Interface Segregation Principle (ISP) principle

No client should be forced to depend on methods it does not use. So split fat interfaces into small role interfaces, each signed only by classes that can keep it.

The pain it cures
A fat interface hurts from both sides. Implementers are forced to "implement" methods they cannot honour (refused bequests, which are LSP violations). Clients are coupled to methods they never call. So unrelated changes ripple into them, and their test fakes must implement everything.
Use it when…
  • An implementer cannot keep part of a contract and is tempted to throw or do nothing (an old printer that can't scan; a smoke alarm that must never switch off).
  • Different clients clearly use different subsets of an interface's methods.
  • Test fakes for a client must implement many methods the client never calls.
  • A shared interface keeps growing to serve one more kind of client.
Do NOT use it when…
  • The methods are always used together by the same clients (turnOn, turnOff and isOn stay together).
  • One implementation and one client fit the interface perfectly. There is nothing to split.
  • It would produce one interface per method. That scatters an idea into pieces nobody can see whole.
  • You are splitting by what implementers happen to do, instead of by what clients actually call.
The cost
More types to name and find your way around. Classes that list several interfaces. Code that must send the right objects to the right clients (e.g. separate typed lists). Wrappers that show only the contract they wrap, hiding other abilities. And a wide edit when an interface that many classes depend on is split late.
Relatives
  • SRP (Lesson 05): splits classes by who asks for changes. ISP splits interfaces by who calls them.
  • LSP (Lesson 07): ISP is the usual cure for refused bequests. A contract small enough to keep leaves nothing to refuse.
  • Cohesion (Lesson 04): a well-segregated interface is a cohesive one.
Seen in the wild
java.lang.AutoCloseable: one method, close(). That is all try-with-resources needs. Files, sockets and database connections sign it beside their other contracts. Also Runnable, Comparable, and Iterable (all the for-each loop needs).
Where it lives
Kata: com.katas.isp (Printer, Scanner, Fax, OldPrinter, MultiFunctionMachine, ReportPrinter; fat Machine in naive/). Hub: Device (name, status) + Switchable / Lockable (both extend Device) + Dimmable; SmokeAlarm, DoorLock; routines take List<Switchable>; contract tests split per capability. Lesson: 08.

Dependency Inversion Principle (DIP) principle

High-level policy should not depend on low-level details. Both should depend on abstractions that belong to the policy. The details are injected from one composition root.

The pain it cures
A valuable, stable rule names and creates a mechanism that changes often (new EmailSender() inside the alert policy). So the mechanism can't be swapped without editing the rule. The rule can't be tested without the real mechanism. And the rule can't be reused elsewhere.
Use it when…
  • Policy code depends on something that really varies: devices, sensors, networks, storage, clocks, third-party services.
  • You need to test a rule without its real collaborators (a recording channel, a fixed sensor).
  • A second implementation of a detail has arrived or is clearly coming.
  • You want the core of an application to stay free of vendor and infrastructure names.
Do NOT use it when…
  • The dependency is stable and will never be swapped: String, List, java.time, your own small value classes.
  • There is one implementation and no testing pain. Plain new is simpler until the second one arrives.
  • You would be wrapping the detail in an interface shaped like the detail (sendEmail(to, subject, body)). That is not inversion. Write it in the policy's terms, or don't bother.
  • A class needs so many injected dependencies that the real problem is too many responsibilities. Fix that with SRP first.
The cost
An interface per inverted boundary. Wiring code in the composition root, which grows with the program. An extra hop when reading: "which implementation is this at run time?" Only the composition root can answer. And with frameworks, the risk of wiring that feels like magic.
Relatives
  • Dependency Injection: the technique usually used to achieve DIP. You hand dependencies in from outside. You can also inject a concrete class. That is DI without DIP.
  • Inversion of Control: the broad idea of a framework calling your code. DI containers are one example.
  • OCP (Lesson 06) and ISP (Lesson 08): the abstraction owned by the policy is the variation point. It should be small.
  • Factories (Lessons 14–15) and Service Locator (Lesson 37) deal with the creating side. Service Locator does it less cleanly.
Seen in the wild
Spring's constructor injection. A class has a constructor that takes an interface. The container passes in a matching object (a "bean"). That is the composition root, automated. Logging facades such as SLF4J let libraries depend on an interface while the application plugs in the real logging engine.
Where it lives
Kata: com.katas.dip (AlertChannel owned by the policy, TemperatureMonitor, Main as composition root) + com.katas.dip.channels (EmailChannel, SmsChannel); welded version in naive/. Hub: climate.TemperatureSensor (policy-owned) + climate.ClimateControl, implemented by sensors.SimulatedThermometer; composition root com.smarthome.Main + HomeSetup; core packages import only device contracts. Lesson: 09.

DRY — Don't Repeat Yourself principle

Every piece of knowledge (a rule, a number with meaning, a format) is written down in exactly one place. Everything that needs it asks that place.

The pain it cures
One fact is typed in several places. Every change must be made in all of them (shotgun surgery). The day one is missed, the program contradicts itself. For example, a banner promises free delivery while the checkout charges for it.
Use it when…
  • Changing one copy means you must change the other, or the program is wrong.
  • The same threshold, rate, format or validation rule appears in two classes, or in code and in a message shown to users.
  • A bug fix had to be applied "in a few places."
  • You have just written a third copy of something (the rule of three).
Do NOT use it when…
  • The code that looks alike serves different actors and will change for different reasons (accidental duplication, Lesson 05). Merging couples them.
  • Merging would need flags or parameters to cover each caller's differences. That is the wrong abstraction. Duplication is cheaper.
  • There are only two copies and you can't yet see what really repeats. Wait for the third.
  • It is test code, where a little repetition often makes each test readable on its own.
The cost
A new home (a class, constant or method) that both callers depend on, which couples them to it. One more hop when reading. And the risk of merging too early: a shared helper full of flags, harder to change than the copies were.
Relatives
  • SRP (Lesson 05): the other half of the question "must these change together?" When the answer is no, SRP keeps look-alikes apart.
  • Single source of truth: the name for the one place that holds a fact.
  • Template Method (Lesson 26): a pattern for writing a shared skeleton once.
Seen in the wild
java.util.AbstractList implements indexOf, equals, hashCode and its iterator once. It builds them on each list's own get and size. The name DRY comes from Hunt and Thomas, The Pragmatic Programmer (1999).
Where it lives
Kata: com.katas.dry (DeliveryPolicy shared by CartBanner and Checkout; drifted copies in naive/). Hub: home.Hub.findNamed, the one by-name lookup shared by switchableNamed and unlock. Lesson: 11.

KISS — Keep It Simple principle

Of the designs that fully do the job, choose the one with the fewest parts and nothing hidden. Every extra part must earn its place.

The pain it cures
Machinery bigger than the problem: registries, plug-in rules, configuration. It must be read, tested and understood. It also hides the thing that decides the answer, so the first extension goes wrong.
Use it when…
  • A newcomer can't predict the output by reading the code once, top to bottom.
  • There are interfaces with one implementation and no second in sight.
  • Order, priority or behaviour depends on registration, configuration or naming conventions you can't see in one place.
  • A "clever" one-liner needs a comment to explain what it does.
Do NOT use it when…
  • "Simple" is an excuse for no structure at all (one 600-line Main). That is easy to start, not simple.
  • The problem really is complex (many modes, many channels, real variation). Then the structured design is the simple one.
  • Simplicity is judged only by line count. Short and cryptic is not simple.
  • You would delete a variation point that two or more real variants already use.
The cost
Code may need restructuring later, when real complexity arrives. And some people think quality means machinery. To them, simple code can look "naive," so you may have to defend it in review.
Relatives
  • YAGNI: KISS is about how a solution is built. YAGNI is about whether to build a feature at all.
  • Needless complexity (Lesson 04): the design smell KISS prevents.
  • SOLID (Lessons 05–10): adds parts so change stays local. KISS asks each part to justify itself.
Seen in the wild
A motto usually credited to the aircraft engineer Kelly Johnson. In code it shows up mostly in review comments ("can this just be an if?") and in libraries that offer a plain method beside the configurable one.
Where it lives
Kata: com.katas.kiss (Greeter, four plain ifs; the over-built GreetingEngine in naive/). Hub: Hub.findNamed stays a plain loop, with no index or name map for four devices. Lesson: 11.

YAGNI — You Aren't Gonna Need It principle

Don't build a feature, option or extension point until a real need for it arrives.

The pain it cures
Guessed features cost effort now. They burden every caller (knobs to choose). They rot untested. And they usually guess wrong: the real request turns out to be something none of the guesses covered.
Use it when…
  • The justification is "in case," "one day," or "to be flexible."
  • An option or format has no caller today.
  • You are about to add an interface, parameter or setting with a single known use.
  • Code paths exist that no test exercises because nothing uses them.
Do NOT use it when…
  • It would mean skipping tests, error handling, clear names or security. Those are quality, needed today.
  • The decision is very costly to change later: a published API, a stored data format, a security model. Think those through up front.
  • The need is real and scheduled (it is in this release's agreed work), not imagined.
  • You are using it to refuse keeping code easy to change. YAGNI only works because code stays cheap to change.
The cost
When the need does arrive, you build it then, sometimes with a small refactoring first. That is usually cheaper than the speculative version, but it is not free.
Relatives
  • Take the first bullet / OCP (Lesson 06): YAGNI applied to variation points. Wait for the second real variant.
  • Speculative generality (Lesson 06): the smell YAGNI prevents.
  • KISS: whether to build it (YAGNI) versus how simply to build it (KISS).
Seen in the wild
A rule of Extreme Programming (Kent Beck, Ron Jeffries, late 1990s), and the most common question in code review: "who asked for this option?"
Where it lives
Kata: com.katas.yagni (ShoppingList; the over-prepared ListPrinter with an unfinished columns knob in naive/). Hub: Hub has unlock(name) but no lock(name) or turnOn(name), and only one alert channel, because nothing needs more. Lesson: 11.

Law of Demeter (principle of least knowledge) principle

Talk only to your friends. A method calls methods only on its own object, its parameters, objects it creates, and its own fields. It never calls methods on objects those friends hand back.

The pain it cures
Train-wreck calls (customer.getWallet().take(2)) couple a class to the inside structure of other objects. When that structure changes, every class that reaches through breaks, often quietly, without being edited.
Use it when…
  • You see a chain of getters ending in an action: a.getB().getC().doD().
  • A class asks another for its insides and then makes a decision that belongs to the other class.
  • A change inside one class forces edits in classes that only use it.
  • Code depends on an item's position in someone else's list (lockables().get(0)).
Do NOT use it when…
  • The chain calls methods on the same object each time (StringBuilder.append(…).append(…), builders, streams). Count strangers, not dots.
  • The returned thing is a stable value or plain data (String, numbers, java.time values).
  • Obeying would mean wrapper methods that only forward (getWalletCashInEuros()). That is the middle man smell. Give the friend a method that does the job instead.
  • The code is a composition root that only passes objects along without calling them.
The cost
Friends gain methods shaped like tasks (pay, unlock(name)), so their interfaces grow. Done mechanically, it produces piles of forwarding code. And a caller can no longer improvise with another object's insides.
Relatives
  • Tell, Don't Ask: the usual way to obey it. Tell the friend what you want done.
  • Encapsulation (Lesson 01): Demeter is encapsulation seen from the caller's side.
  • ISP (Lesson 08): both make clients know less. ISP limits methods. Demeter limits objects.
  • Message chains and middle man: Fowler's names for the violation and for the over-correction.
Seen in the wild
Named after the Demeter project at Northeastern University (Ian Holland, 1987). David Bock's short paper The Paperboy, The Wallet, and The Law of Demeter is the classic example. This course's kata borrows its story.
Where it lives
Kata: com.katas.demeter (Paperboy → Customer.pay; the reaching paperboy in naive/). Hub: Main calls hub.unlock("Front Door") instead of hub.lockables().get(0).unlock(). Lesson: 11.

Favor composition over inheritance principle

When in doubt, build behaviour by holding other objects and delegating to them (has-a), rather than by extending a class (is-a).

The pain it cures
Three pains. Subclasses broken by changes inside their parent (the fragile base class problem). Class explosion when features combine (LoggingLight, LoggingThermostat…). And behaviour fixed at compile time, which cannot be swapped or injected.
Use it when…
  • You want to add a feature (logging, counting, retrying) to several existing classes.
  • The class you would extend is not yours, or was not designed for extension.
  • "X is a Y" sounds forced, or holds only for some of Y's methods.
  • You want to choose or swap the behaviour at run time or in tests.
Do NOT use it when…
  • It is a true is-a with a small, stable parent you own and designed for extension (the hub's SwitchableDevice).
  • The wrapper would only forward many methods and add nothing. That is needless complexity.
  • A framework requires extending its base class to plug in (you follow its rules).
  • You are replacing working inheritance that causes no pain, just to follow the slogan. "Favor" is not "always."
The cost
Forwarding methods for every operation of the interface. Two objects where there was one. An interface, so the held object can be swapped. And the parts must be wired together, usually at the composition root.
Relatives
  • LSP / OCP / DIP (Lessons 07, 06, 09): a wrapper promises only the interface it signs. It adds behaviour without edits. Its parts can be injected.
  • Delegation and wrapper (Lesson 03): the mechanics it uses.
  • Decorator, Proxy, Adapter, Strategy (Lessons 18–25): named patterns built on composition. You tell them apart by their purpose.
Seen in the wild
Stated in the Gang of Four's Design Patterns (1994). Joshua Bloch's Effective Java has an item of the same name (Item 18 in the 3rd edition; check the number). It names Stack extends Vector and Properties extends Hashtable as JDK mistakes.
Where it lives
Kata: com.katas.composition (CountingPlaylist wrapping a SongList; the double-counting subclass in naive/). Hub: activity.LoggedDevice logs any switchable device by wrapping it. Lessons: 03, 11.
