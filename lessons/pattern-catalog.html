?How to read an entry

Every entry answers the same questions in the same order, so entries can be compared side by side:

  • Intent: what it is, in one plain sentence.
  • The pain it cures: the specific problem that makes you reach for it.
  • Use it when…: the concrete signals that it fits.
  • Do NOT use it when…: the equally concrete signals that it is the wrong tool. Over-applying patterns is the classic beginner mistake, so this field is never left thin.
  • The cost: the indirection or complexity it always adds. Nothing is free.
  • Relatives: what it resembles, and the one-line difference.
  • Seen in the wild: one place the JDK or a popular framework already uses it.
  • Where it lives: its kata package, and its home in the Smart Home Hub if it has one.

Single Responsibility Principle (SRP) principle

A class should have one reason to change. Put another way, it should answer to one group of people who might ask for changes.

The pain it cures
A "god class" serving several groups at once: one group's change silently breaks another group's feature (often through a shared helper), every change touches the same file, and the class is hard to test because every test needs everything.
Use it when…
  • You cannot describe the class in one sentence without "and."
  • Different people (accounting, HR, the display designer, the installer) request changes to different parts of it.
  • Two methods serving different groups share a private helper.
  • Testing one behaviour forces you to set up, or capture output from, unrelated ones.
Do NOT use it when…
  • The parts always change together, for the same people. Splitting them just scatters one purpose across files.
  • The split would produce one-method classes that only forward calls ("anemic" fragments with no rules of their own).
  • The "reasons to change" are imagined. Wait for the second real request before splitting.
  • It is a short script or prototype that will be thrown away.
The cost
More classes and files; wiring code somewhere (an assembly point like Main) to put the pieces together; callers may have to know several objects instead of one; navigating the design takes more hops.
Relatives
  • Cohesion (Lesson 04): SRP is cohesion turned into a rule, with "reason to change" as the measuring stick.
  • Interface Segregation (Lesson 08): the same idea seen from the client's side: no client should depend on methods it does not use.
  • DRY (Lesson 11): SRP sometimes keeps look-alike code apart, because it changes for different reasons (accidental duplication).
Seen in the wild
java.time keeps LocalDate (the date value and its arithmetic) separate from DateTimeFormatter (how a date looks as text). Display rules change for different reasons than calendar rules, so they live in different classes.
Where it lives
Kata: com.katas.srp (EmployeeData, PayCalculator, HoursReporter, EmployeeCsv; the god class in naive/Employee). Hub: Main split into home.HomeSetup (which devices), home.Hub (operating them) and report.HouseReport (how it looks). Lesson: 05.
