D — Dependency Inversion Principle

The important rules of a program must not depend on its replaceable nuts and bolts. Both depend on an abstraction owned by the rules, and the pieces are plugged together by hand in one place.

Kata package: com.katas.dip + com.katas.dip.channels (wrong way in com.katas.dip.naive).
Smart Home Hub: created climate/TemperatureSensor, climate/ClimateControl, sensors/SimulatedThermometer and tests; moved HomeSetup (and its test) from home to the composition root beside Main; Hub.switchableNamed made public; Main rewritten as the composition root.
Prerequisites: Lesson 08; coupling from Lesson 04.

1The pain

A rule worth protecting ("alert someone when the server room is too hot") is welded to one particular way of delivering the alert.

public class TemperatureMonitor {
    private final EmailSender email = new EmailSender();   // names AND creates the detail

    public void check(int celsius) {
        if (celsius > 30) {
            email.sendEmail("ops@example.com", "Too hot", "Server room at " + celsius + "C");
        }
    }
}

Three ordinary requests now hurt. The night shift wants alerts by SMS: you must edit the monitor, the class holding the rule, to change how a message travels. You want to test the rule ("does 31°C alert? does 30°C not?"), but every test fires off a real email, because the monitor builds its own sender and nothing can be swapped in. Another team wants to reuse the monitor for its freezers, and can't, because it comes welded to EmailSender.

Predicted symptom

EMAIL to ops@example.com [Too hot]: Server room at 35C   <- and no way to send anything else

The pain, named: the important rule depends on the replaceable detail. The dependency arrow points the wrong way: from the stable, valuable code down to the volatile, swappable code. Every change in the detail threatens the rule.

Full wrong-way code: katas/src/main/java/com/katas/dip/naive/ (EmailSender, TemperatureMonitor)

2Real-world analogy

A laptop and its USB port. The laptop's makers decided what a USB port is: its shape, its voltages, the messages it sends. Mouse, keyboard and webcam makers build to that standard. The laptop was never redesigned for a new mouse, and a mouse can be swapped in seconds, because the plugging happens at your desk. Now imagine a laptop with one particular mouse soldered onto its motherboard. That is our naive monitor.

3The principle explained

3.1 High level and low level

Some code expresses what the program is for: "alert when too hot," "keep the room comfortable," "run the goodnight routine." It changes only when the business changes its mind, and it is what you would most like to keep and reuse. That is high-level policy. Other code expresses how a particular mechanism works: sending an email, talking to a sensor chip, writing to a database. It changes whenever a vendor, protocol or device changes. That is a low-level detail. In the naive monitor the rule is the policy and EmailSender is the detail.

3.2 The principle

Robert C. Martin stated it in two parts. In plain words:

  1. High-level policy should not depend on low-level details. Both should depend on abstractions.
  2. Abstractions should not depend on details. Details should depend on abstractions.

That is the Dependency Inversion Principle (DIP), the "D" in SOLID. The cure has three moves: (1) the policy declares an interface describing what it needs, in its own words; (2) the details implement that interface; (3) something outside both plugs a detail into the policy.

3.3 What exactly is "inverted"?

Two different arrows were pointing the same way in the naive code, and DIP separates them:

  • The flow of control, meaning who calls whom at run time, still goes down: the monitor calls the channel, which sends the message. Nothing changes there.
  • The source-code dependency, meaning which file imports and names which, now points up. EmailChannel imports AlertChannel, which belongs to the policy. The monitor imports nothing from the channels.

The dependency now runs against the flow of control, from the detail up to the policy. That reversal is the inversion.

3.4 Who owns the interface matters

Putting any interface between the two is not enough. Suppose we wrote interface EmailService { void sendEmail(String to, String subject, String body); }. The policy would still think in email terms (subjects, addresses), and SMS could not fit. The abstraction must be written in the policy's terms (send(String message)) and live in the policy's package. In the kata, AlertChannel sits in com.katas.dip beside the monitor, and the channels live in com.katas.dip.channels and import it. Check the imports: the policy package never imports the channels package.

3.5 Plugging it together: dependency injection

If the monitor no longer creates its channel, someone must hand it one. Every new SomeConcreteClass() written inside a class glues that class to that concrete detail. So instead the object receives what it depends on from outside, usually as constructor parameters: new TemperatureMonitor(new SmsChannel("555-0100"), 30). Handing an object its dependencies from outside, instead of letting it create them, is called dependency injection (DI). Passing them through the constructor, as here, is constructor injection. It is the preferred form, because the object can never exist without what it needs.

All that creating and plugging has to happen somewhere. The best place is one spot at the very start of the program, which is the only code that names concrete classes. That spot is called the composition root. In the kata it is Main; in the hub, Main plus HomeSetup. Doing it by hand with plain new calls, as this course does, is called manual (or "pure") DI. Frameworks such as Spring automate the composition root: they create the objects and pass constructor arguments for you (Section 6). They automate exactly what you are now writing by hand.

TermWhat it isKind of thing
Dependency Inversion (DIP)Point source dependencies at abstractions owned by the policyA design principle (which way the arrows go)
Dependency Injection (DI)Hand an object its dependencies from outsideA technique (how the pieces get connected)
Inversion of Control (IoC)A framework calls your code, rather than your code calling the frameworkA broad idea; DI containers are one example

They are often confused because they work together: DI is the usual way to achieve DIP. You can inject a concrete class, though (new Monitor(new EmailSender())), which is DI without DIP.

A class takes EmailSender (a concrete class) as a constructor parameter instead of creating it. Has it applied DIP?

Only half. It uses dependency injection, so a test could pass in a subclass, but its source code still names and depends on the email detail. SMS still can't be plugged in without editing it. DIP also needs the parameter's type to be an abstraction owned by the policy: AlertChannel.

4The kata

Package com.katas.dip (policy plus its abstraction) and com.katas.dip.channels (details).

Saved: katas/src/main/java/com/katas/dip/AlertChannel.java

// The RIGHT WAY, part 1: the abstraction, OWNED by the policy side.
package com.katas.dip;

// Written in the POLICY's terms ("send this alert"), not in any channel's
// terms (no email subjects, no phone numbers). It lives in the policy's
// package; the low-level channels come to IT and implement it. That reversal
// of who depends on whom is the "inversion".
public interface AlertChannel {

    // Deliver one alert message, however this channel does it.
    void send(String message);
}

Saved: katas/src/main/java/com/katas/dip/TemperatureMonitor.java

// The RIGHT WAY, part 2: the high-level policy, depending only on its abstraction.
package com.katas.dip;

// The same rule as the naive version, but it never names or creates a
// channel. The channel is INJECTED: handed in through the constructor by
// whoever assembles the program. Notice this file imports nothing from the
// channels package.
public class TemperatureMonitor {

    // The abstraction the policy needs; which channel it is, is not its business.
    private final AlertChannel channel;

    // The highest temperature that is still fine.
    private final int maxCelsius;

    // CONSTRUCTOR INJECTION: every dependency arrives as a parameter.
    public TemperatureMonitor(AlertChannel channel, int maxCelsius) {
        // Remember the channel we were given.
        this.channel = channel;
        // Remember the limit we were given.
        this.maxCelsius = maxCelsius;
    }

    // The policy: above the limit, raise the alarm. Returns whether it alerted.
    public boolean check(int celsius) {
        // Within the limit: nothing to do.
        if (celsius <= maxCelsius) {
            // No alert.
            return false;
        }
        // Too hot: send the alert in the policy's own terms.
        channel.send("Server room at " + celsius + "C (max " + maxCelsius + "C)");
        // An alert went out.
        return true;
    }
}

Saved: katas/src/main/java/com/katas/dip/channels/EmailChannel.java

// Low-level details live in their own package.
package com.katas.dip.channels;

// The detail depends UP on the policy's abstraction: this import points from
// the channels package to the policy package, never the other way round.
import com.katas.dip.AlertChannel;

// Email, as one way of keeping the AlertChannel contract.
public class EmailChannel implements AlertChannel {

    // Where to send; an email-specific detail the policy never sees.
    private final String address;

    // The address is chosen by whoever assembles the program.
    public EmailChannel(String address) {
        // Remember it.
        this.address = address;
    }

    // Translate the policy's request into email terms.
    @Override
    public void send(String message) {
        // Show what would be sent (prints instead of really emailing).
        System.out.println("EMAIL to " + address + ": " + message);
    }
}

Saved: channels/SmsChannel.java is the same shape, with a phone number, printing "SMS to " + number + ": " + message. It was added without touching the monitor.

Saved: katas/src/main/java/com/katas/dip/Main.java (the composition root)

// The runnable demo for Lesson 09's kata, and its COMPOSITION ROOT.
package com.katas.dip;

// The ONE place allowed to know the concrete channels: here they are chosen
// and plugged into the policy.
import com.katas.dip.channels.EmailChannel;
import com.katas.dip.channels.SmsChannel;

// Builds the object graph by hand (manual dependency injection) and runs it.
public class Main {

    // The JVM starts here when you run this class.
    public static void main(String[] args) {
        // NAIVE: the policy builds its own email sender; nothing can be swapped.
        new com.katas.dip.naive.TemperatureMonitor().check(35);

        // INVERTED: choose a channel HERE and inject it into the policy.
        TemperatureMonitor byEmail = new TemperatureMonitor(new EmailChannel("ops@example.com"), 30);
        // 25C is fine: nothing is sent, nothing is printed.
        byEmail.check(25);
        // 35C is too hot: the alert goes out by email.
        byEmail.check(35);

        // The SAME policy class, wired to a different detail. Zero edits to it.
        TemperatureMonitor bySms = new TemperatureMonitor(new SmsChannel("555-0100"), 30);
        // The alert goes out by SMS.
        bySms.check(35);
    }
}

What happens when it runs

  1. The naive monitor creates its own EmailSender during construction. check(35) exceeds 30, so it calls sendEmail, which prints the email-shaped line.
  2. Main creates an EmailChannel, then a monitor, and injects the channel through the constructor.
  3. byEmail.check(25): 25 ≤ 30, so it returns false. No call to the channel, no output.
  4. byEmail.check(35): too hot, so it calls channel.send(...). Dynamic dispatch runs EmailChannel.send.
  5. A second monitor, the very same class, gets an SmsChannel. check(35) now dispatches to SmsChannel.send.

SMS to 555-0100: Server room at 35C (max 30C)

5Applied to the Smart Home Hub

The audit: the hub's core already obeys DIP

Look back and you'll see we have been pointing arrows at contracts since Lesson 01. Today we check it package by package:

PackageRoleImports from devices
home (Hub)Policy: operate the houseDevice, Switchable: contracts only
routinesPolicy: house modesSwitchable only
reportPolicy: what the house looks likeDevice, Switchable only
home.HomeSetup (until today)WiringLight, Thermostat, SmokeAlarm, DoorLock: concrete

One file breaks the pattern, and for a good reason: HomeSetup is wiring code, the installer's choice of devices. It simply lived in the wrong place. Wiring belongs in the composition root, not inside a core package. So HomeSetup.java (and HomeSetupTest.java) moved from com.smarthome.home to com.smarthome, beside Main. The rule now holds without exception: the core packages never import a concrete device, only Main and HomeSetup do.

A new feature, built inverted from the start: climate control

The requirement: the hall has a temperature sensor, and the hub should keep the hall between 18°C and 24°C by switching the heating. The sensor will be a cheap simulated one for now, and a real third-party device later. The rule must survive that swap untouched.

Saved: smarthome/src/main/java/com/smarthome/climate/TemperatureSensor.java

// The climate POLICY package. It owns this abstraction, so it lives here,
// not in the sensors package that implements it.
package com.smarthome.climate;

// What the climate policy needs from "a thermometer", in the policy's own
// terms. Real sensor hardware (and the simulated one in com.smarthome.sensors)
// implements THIS interface, so the low-level detail depends on the
// high-level policy, not the other way round: the Dependency Inversion
// Principle.
public interface TemperatureSensor {

    // Where the sensor is, e.g. "Hall"; used in messages.
    String location();

    // The current temperature, in whole degrees Celsius.
    int readCelsius();
}

Saved: smarthome/src/main/java/com/smarthome/climate/ClimateControl.java

// The climate POLICY: high-level rules about comfort.
package com.smarthome.climate;

// The only device capability the policy needs: switching the heating.
import com.smarthome.devices.Switchable;

// Keeps a room between a minimum and a maximum temperature by switching the
// heating on or off. It depends ONLY on abstractions (TemperatureSensor,
// Switchable), both injected through the constructor; it never names or
// creates a sensor class or a thermostat class.
public class ClimateControl {

    // Where the readings come from: any sensor keeping the contract.
    private final TemperatureSensor sensor;

    // What heats the room: any switchable device (in the hub, the thermostat).
    private final Switchable heating;

    // The lowest comfortable temperature.
    private final int minCelsius;

    // The highest comfortable temperature.
    private final int maxCelsius;

    // CONSTRUCTOR INJECTION: every dependency and setting arrives from outside.
    public ClimateControl(TemperatureSensor sensor, Switchable heating, int minCelsius, int maxCelsius) {
        // A range upside down can never be satisfied: refuse it.
        if (minCelsius > maxCelsius) {
            // Loud refusal naming both values.
            throw new IllegalArgumentException("Range is upside down: " + minCelsius + "-" + maxCelsius + "C");
        }
        // Remember the sensor.
        this.sensor = sensor;
        // Remember the heating.
        this.heating = heating;
        // Remember the lower bound.
        this.minCelsius = minCelsius;
        // Remember the upper bound.
        this.maxCelsius = maxCelsius;
    }

    // Read the sensor once, act if needed, and describe what happened.
    public String regulate() {
        // One reading through the abstraction.
        int celsius = sensor.readCelsius();
        // What we decided to do, in words.
        String action;
        // Too cold: heating must be on.
        if (celsius < minCelsius) {
            // Switch only if it is not already on (no duplicate log entries).
            if (!heating.isOn()) {
                // On, through the Switchable contract.
                heating.turnOn();
            }
            // Describe the decision.
            action = "heating ON";
        } else if (celsius > maxCelsius) {
            // Too hot: heating must be off. Switch only if needed.
            if (heating.isOn()) {
                // Off, through the Switchable contract.
                heating.turnOff();
            }
            // Describe the decision.
            action = "heating OFF";
        } else {
            // Comfortable: leave everything as it is.
            action = "no change";
        }
        // e.g. "Climate: 26C in Hall (allowed 18-24C) -> heating OFF".
        return "Climate: " + celsius + "C in " + sensor.location()
                + " (allowed " + minCelsius + "-" + maxCelsius + "C) -> " + action;
    }
}

6In the wild

Spring's dependency injection automates the composition root. In a Spring application you would not write new TemperatureMonitor(new SmsChannel(...), 30) yourself. You mark classes as components, and Spring's container creates one object of each and calls their constructors with matching objects it has created:

@Component
public class TemperatureMonitor {
    private final AlertChannel channel;
    // Spring sees one constructor, finds a bean implementing AlertChannel, and passes it in.
    public TemperatureMonitor(AlertChannel channel) { this.channel = channel; }
}

The class is exactly our manually-injected one: a constructor that takes the abstraction. Spring only replaces Main's hand-written new calls. That is why learning manual DI first matters: the framework stops being magic. (Details such as when @Autowired is needed vary by Spring version. Recent versions inject through a single constructor without it. Check the Spring documentation for the version you use. Lesson 37 returns to this.)

Logging is DIP in daily use. Many Java libraries depend only on a logging facade, an interface layer such as SLF4J. The application then plugs in the real logging engine at deploy time. The library's authors never chose your logging engine, which is the policy owning the abstraction and the detail plugged in at the composition root. In interviews, "what is the difference between dependency inversion, dependency injection and inversion of control?" is a favourite question. The table in 3.5 is the answer.

7When NOT to use it

The over-application trap

DIP is about protecting stable, valuable policy from volatile details. Not every dependency is volatile. Depending directly on String, List, java.time.LocalDate or Math is fine: they are stable, will never be swapped, and wrapping them in your own interfaces would be pure needless complexity. The same goes for small value classes in your own code. Apply the inversion at the boundaries where things really vary or must be faked in tests: networks, devices, storage, clocks, third-party services.

Two more failure modes. Constructor bloat: a class that needs eight injected dependencies is usually doing several jobs. That is an SRP smell made visible by DI, not a reason to stop injecting. Container magic: teams that only ever let a framework wire things can lose sight of what depends on what. Manual DI keeps the graph readable in one file.

The simpler alternative, and the cost

For a small program with one implementation of each detail and no testing pain, plain new inside the class is simpler and honest. Introduce the abstraction when a second implementation or a test double is actually needed (OCP's "take the first bullet"). The costs DIP always charges: an extra interface per boundary; wiring code in the composition root that grows with the program; and one more hop when reading ("which AlertChannel is this, at run time?"), answered only by looking at the composition root.

Relatives and look-alikes

  • OCP (Lesson 06): new channels or sensors are added without editing the policy. DIP is what makes the policy closed at an architectural boundary.
  • ISP (Lesson 08): the policy-owned abstraction should be small and shaped by the policy's needs. ClimateControl asks for Switchable, not a whole thermostat.
  • Coupling (Lesson 04): DIP is the strongest tool for loose coupling between layers. It turns "knows a concrete class" into "knows a contract it owns."
  • Factories (Lessons 14–15) take over the creating part of the composition root when choosing which concrete class to build becomes its own problem. Service Locator (Lesson 37) is an alternative to injection, and an inferior one.

8Key takeaways

  • The Dependency Inversion Principle says high-level policy must not depend on low-level details; both depend on abstractions, and the details depend on those abstractions, not the other way round.
  • What is inverted is the source-code dependency: control still flows from policy to detail at run time, but the detail now imports the policy's interface.
  • The abstraction must be owned by the policy, living in its package and written in its terms (send(message), readCelsius()), or it is just the detail wearing an interface.
  • Dependency injection, preferably through constructors, supplies the details from outside. All creating and wiring happens in one composition root, the only code that names concrete classes, which frameworks like Spring automate.
  • Apply DIP at boundaries that really vary or need test doubles (devices, networks, storage), not to stable things like String or List. Every inverted boundary costs an interface, wiring code and an extra hop when reading.

9Challenge

A reporting module looks like this. (a) Name each dependency and whether it is policy or detail. (b) Redesign it with DIP: what interfaces, in which package, in whose terms? (c) Write the composition root, and a test that needs no database and no printer. (d) Predict the output of your composition root with a fake store returning sales of 120 and 80.

public class SalesReport {
    private final MySqlDatabase db = new MySqlDatabase("jdbc:mysql://prod/sales");
    private final PdfPrinter pdf = new PdfPrinter();
    public void run() {
        int total = 0;
        for (int sale : db.query("SELECT amount FROM sales")) total += sale;
        pdf.printPdf("report.pdf", "Total sales: " + total);
    }
}
Click to reveal the answer

(a) The policy is "add up the sales and publish the total." MySqlDatabase (with an SQL string and a production URL) and PdfPrinter (with a file name) are details. The policy names and creates both, so it can't be tested without a live database, and it can't publish anything except a PDF.

(b) Two small interfaces, written in the report's terms and living beside SalesReport in its package. The SQL and the PDF filename move into the details.

// Owned by the report: "give me the sale amounts", no SQL in sight.
public interface SalesSource { List<Integer> amounts(); }
// Owned by the report: "publish this line", no file formats in sight.
public interface Publisher { void publish(String line); }

public class SalesReport {
    private final SalesSource source;
    private final Publisher publisher;
    // Constructor injection: the report never creates its details.
    public SalesReport(SalesSource source, Publisher publisher) { this.source = source; this.publisher = publisher; }
    public void run() {
        int total = 0;
        for (int sale : source.amounts()) total += sale;
        publisher.publish("Total sales: " + total);
    }
}
// Details (another package) implement the report's interfaces:
//   class MySqlSalesSource implements SalesSource { ... the SQL lives here ... }
//   class PdfPublisher implements Publisher     { ... "report.pdf" lives here ... }

List<Integer> means "a list of whole numbers." Java lists hold objects, so Integer is the object form of int, and the for-each loop converts back automatically.

(c) The composition root, for production, is new SalesReport(new MySqlSalesSource("jdbc:mysql://prod/sales"), new PdfPublisher("report.pdf")).run();. A test injects fakes, for example a source returning List.of(120, 80) and a publisher that records lines, then asserts the recorded line is "Total sales: 200". No database and no printer are needed.

  • Intent: policy and details both depend on abstractions owned by the policy; details are injected.
  • Pain: a valuable rule welded to a replaceable mechanism: can't swap it, can't test it, can't reuse it.
  • Use when: a boundary really varies (devices, networks, storage, clocks) or needs a test double.
  • Do NOT use when: depending on stable things (String, List, value classes); one implementation and no testing pain.
  • Cost: an interface per boundary, wiring code in the composition root, an extra hop when reading.
  • Seen in the wild: Spring constructor injection; logging facades such as SLF4J.
  • Where: kata com.katas.dip; hub climate.TemperatureSensor + ClimateControl, sensors, composition root Main + HomeSetup.
