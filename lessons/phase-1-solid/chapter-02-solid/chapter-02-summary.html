3The story so far

  1. Lesson 05 (S): Main had become a god class. It split into HomeSetup (which devices), Hub (operating them) and HouseReport (how it looks). Each answers to one actor.
  2. Lesson 06 (O): house modes were an if-else on mode names. They became Routine classes, and hub.run(routine) never changes for a new mode.
  3. Lesson 07 (L): the Device contract was written down. Contract tests started checking every implementation, the logging wrapper included.
  4. Lesson 08 (I): a smoke alarm and a door lock arrived. They could not honestly "turn off." The fat Device split into Device plus Switchable, Lockable and Dimmable. The hub keeps typed groups, so routines never see the alarm.
  5. Lesson 09 (D): a climate policy arrived. It owns its TemperatureSensor contract. The simulated thermometer plugs in from outside. Main plus HomeSetup became the composition root.
  6. Lesson 10 (all five): a lock check was built SOLID from its first line, with its own AlertChannel. Meanwhile, a rotten module was refactored in the kata.
  7. Lesson 11 (companions): the audit found a train wreck in our own Main (lockables().get(0)). It became hub.unlock("Front Door"). Both by-name lookups now share one rule.

The hub's printed output has hardly changed across these seven lessons. What changed is how cheaply it can change next. That is the whole point of this chapter.

5How the principles connect

6Ideas that come back

  • The policy-owned interface with an injected detail (TemperatureSensor, AlertChannel) is the shape of most behavioral patterns. It returns as swappable algorithms in Lesson 25. It returns again in Lesson 37, where dependency injection is named as a pattern.
  • Routine, an object you hand to run, is very close to two patterns ahead. One swaps algorithms (Lesson 25). The other turns a request into an object you can queue and undo (Lesson 28). Lesson 12 explains why the same shape can be two different patterns.
  • The wrapper that keeps its contract (LoggedDevice, now backed by LSP, OCP and composition) becomes three named structural patterns in Lessons 18–22. You tell them apart by their purpose.
  • "Only the composition root says new" raises the next question. What happens when creating the right object gets complicated? That is the whole of Chapter 04, the creational patterns.
  • KISS and YAGNI become the course's defence against pattern fever: the urge to use a pattern just because you know it. They come back in Lesson 12 and in full in Lesson 41.

7Self-check

PayCalculator and HoursReporter each contain an identical-looking Math.min(...) line. Should DRY merge them?

No. They serve different actors (accounting and HR) and will change for different reasons. So it is accidental duplication (Lesson 05). DRY's test is "must they change together?" Here the answer is no (Lesson 11).

Why is QuietSecurityModule, which throws at night, an LSP violation and not just a design choice?

Code written against SecurityModule trusts checkHouse to check. The subclass refuses that promise (a refused bequest). So honest client code quietly loses smoke alerts. A substitute may ask for less and give more, never ask for more or give less (Lesson 07, Lesson 10).

The hub's smoke alarm implements only Device. Which principle made that possible, and what did routines gain?

ISP (Lesson 08): Switchable was split off, so the alarm is never forced to "turn off." Routines now take List<Switchable>. So the compiler itself guarantees that an "everything off" routine can never touch the alarm.

ClimateControl calls sensor.readCelsius(). Which way does the source-code arrow point, and why is that "inverted"?

From SimulatedThermometer up to TemperatureSensor, which lives in the policy's own climate package. At run time, control flows from the policy down to the detail. But the source-code dependency points from the detail up to the policy's abstraction, against that flow (Lesson 09).

text.append("a").append("b") and hub.lockables().get(0).unlock() both chain calls. Why is only one a Law of Demeter problem?

Each append returns the same builder, so you are still talking to your friend. The other chain reaches through the hub into its list, then into one item by position. Then it calls unlock on a stranger. Count strangers, not dots (Lesson 11).

8Boss challenge

A "movie night" feature arrived from another team. Check it against all ten catalog entries. Put your refactoring steps in a sensible order, and sketch the result. Then predict what it prints in this case: the living room has one light, one TV and one speaker, and the owner is told by SMS at 555-0100.

public interface Appliance {
    String name(); void powerOn(); void powerOff();
    int volume(); void setVolume(int percent); boolean isRecording();
}

// A camera "is an" appliance, so it must have a volume...
public class Camera implements Appliance {
    /* powerOn/powerOff/isRecording work; volume() and setVolume() throw UnsupportedOperationException */
}

public class MovieNight {
    public void start(Home home, String speakerBrand) {
        for (Appliance a : home.getLivingRoom().getAppliances()) {
            if (a.name().startsWith("Light")) a.powerOff();
            else if (a.name().startsWith("TV")) a.powerOn();
            else if (a.name().startsWith("Speaker")) { a.powerOn(); a.setVolume(speakerBrand.equals("Sonos") ? 30 : 25); }
            else a.setVolume(0);   // "mute everything else" — including the camera
        }
        System.out.println("Movie night: " + home.getLivingRoom().getAppliances().size() + " appliances (max volume 30)");
        new SmsSender().send("555-0100", "Movie night started");
    }
}

Diagnosis, entry by entry

EntryProblem
SRPstart runs the scene, writes a console report, and sends an SMS. That is three actors: the scene designer, whoever reads the console, and whoever runs messaging.
OCPA ladder on name prefixes. A projector means editing start. A device named "Lamp" quietly falls into "mute."
LSPCamera throws from setVolume. So the day a camera is in the living room, the else branch crashes the whole scene.

DIPnew SmsSender() and System.out are welded into the policy. So it cannot be tested without a phone and a console.

Demeterhome.getLivingRoom().getAppliances() is a train wreck. The scene is coupled to how homes and rooms are built.
Composition"A camera is an appliance" forced an is-a, and every inherited promise came with it. Each device should choose its own roles (capabilities).

Order:

  1. S: pull the report and the message out of the scene.
  2. I: split Appliance into small roles. LSP stops mattering once the camera signs only what it does.
  3. O: the setup hands over typed groups, so the ladder disappears.
  4. D: the scene owns a Notifier, and the SMS detail is injected.

The companions apply along the way: one volume value (DRY, YAGNI), no Home parameter (Demeter), no name guessing (KISS).

// Small roles (ISP). A camera signs neither of these.
public interface Switchable { void turnOn(); void turnOff(); }
public interface Speaker extends Switchable { void setVolume(int percent); }

// Owned by the scene's package (DIP); SmsNotifier lives elsewhere and implements it.
public interface Notifier { void notify(String message); }

public class MovieNight {
    private final List<Switchable> lights;     // typed groups from the setup (O): no name ladder
    private final List<Switchable> screens;
    private final List<Speaker> speakers;
    private final int volume;                      // ONE home for the number (DRY), no brand knob (YAGNI)
    private final Notifier notifier;

    public MovieNight(List<Switchable> lights, List<Switchable> screens, List<Speaker> speakers,
                      int volume, Notifier notifier) {
        this.lights = List.copyOf(lights); this.screens = List.copyOf(screens);
        this.speakers = List.copyOf(speakers); this.volume = volume; this.notifier = notifier;
    }

    // Talks only to its own fields (Demeter). One job: run the scene, then say so (S).
    public void start() {
        for (Switchable light : lights) { light.turnOff(); }
        for (Switchable screen : screens) { screen.turnOn(); }
        for (Speaker speaker : speakers) { speaker.turnOn(); speaker.setVolume(volume); }
        notifier.notify("Movie night started (volume " + volume + ")");
    }
}

Wiring it at a composition root: new MovieNight(List.of(light), List.of(tv), List.of(speaker), 30, new SmsNotifier("555-0100")).start(). Here the demo devices print one line per action: "Light: OFF", "TV: ON", "Speaker: ON", "Speaker: volume 30". SmsNotifier prints "SMS to " + number + ": " + message.

Prediction

The order follows the three loops, then the notification. A test passes a recording notifier and checks one message. A projector is just one more item in screens. The camera is never handed to the scene, so it can no longer crash it. Lesson 20 comes back to "movie night" with a pattern built for exactly this kind of job: many steps behind one call. If you build it in a scratch package, run it and compare. The machine is the judge.
