Phase 1 · Chapter 02 · Lesson 05

S — Single Responsibility Principle

A class should have one reason to change. It should answer to one group of people. When it answers to several, one group's change breaks another group's feature.

Kata package: com.katas.srp (wrong way in com.katas.srp.naive).
Smart Home Hub: created home/HomeSetup.java, home/Hub.java, report/HouseReport.java and their tests; modified Main.java.
Prerequisites: Lesson 04 — Coupling, Cohesion, and Reading UML and the Chapter 01 summary.

  • What SOLID is: five rules for classes that bend without breaking.
  • The first rule, Single Responsibility: how to find a class's "reasons to change" by asking who would request the change.
  • How to split a class that serves too many people, and how to avoid splitting too much.

1The pain

Here is a payroll class (the code that works out how much each worker is paid). It works perfectly. Then the Accounting team asks for a small change, and HR's weekly report quietly starts lying.

1.1 One class, three teams

A company has three teams that care about workers. Accounting pays them. HR (Human Resources, the team that looks after staff) tracks their working hours. The database team stores their records. One class, Employee, serves all three:

public int calculatePay() {                // used by ACCOUNTING
    return regularHours() * hourlyRate + overtimeHours() * hourlyRate * 2;
}
public String reportHours() {             // used by HR
    return name + ": " + regularHours() + " regular hours";
}
public String toCsv() { … }                // used by the DATABASE team

private int regularHours() {               // SHARED by pay and HR
    return Math.min(hoursWorked, 40);
}

(toCsv() turns the worker into one line of text with commas between the values, like Asha,45,20. That format is called CSV, "comma-separated values.")

1.2 A small change for one team

Accounting asks: "for pay, overtime should start after 35 hours." (Overtime is extra hours, paid at a higher rate.) Here is what happens next:

  1. A developer finds regularHours() and changes 40 to 35.
  2. The pay tests pass, so the change ships.
  3. HR never asked for anything. But reportHours() uses the same helper. So HR's report changed too:

Predicted symptom (Asha worked 45 hours)

Naive pay: 1100                              <- correct, as Accounting asked
Naive HR report: Asha: 35 regular hours      <- HR's rule is 40; nobody told HR

1.3 Naming the pain

Nobody was careless. The developer did exactly what Accounting asked, in the place where the rule lived. The fault lies in the class itself. It serves three different groups. So a change asked for by one group can reach the others.

This smell has a name. A class that does many unrelated jobs for many different groups is called a god class, because it tries to do everything. Our own hub has the start of one: Main. Lesson 04 noticed that it was losing cohesion.

Full wrong-way code: katas/src/main/java/com/katas/srp/naive/Employee.java

2Real-world analogy

One circuit breaker for the whole house. A circuit breaker is a safety switch in your fuse box. It cuts the power to one set of wires (a circuit) when something goes wrong, or when an electrician works on it.

  • Imagine every light, the fridge and the doorbell all on one breaker.
  • When the electrician works on the kitchen, the bedroom goes dark too.
  • A fault in the doorbell switches off the fridge.

Real houses have one breaker per circuit. So work on the kitchen touches only the kitchen. The breaker panel's only job is to hold the breakers side by side.

In the houseIn code
One breaker for everythingA god class (naive/Employee)
Work on the kitchen darkens the bedroomAccounting's change breaks HR's report
One breaker per circuitOne class per responsibility (PayCalculator, HoursReporter, EmployeeCsv)
Whoever uses that circuitThe group of people who request changes to that class
The breaker panelThe assembly point that wires the pieces together (Main)

3The principle explained

3.1 First, where "SOLID" comes from

Around the year 2000, Robert C. Martin gathered five rules for designing classes that bend without breaking. A few years later, Michael Feathers noticed that their first letters spelled a word. So people started calling the five rules SOLID:

  • Single responsibility (this lesson);
  • Open/closed (Lesson 06);
  • Liskov substitution (Lesson 07);
  • Interface segregation (Lesson 08);
  • Dependency inversion (Lesson 09).

Don't worry about the long names yet. This chapter teaches one rule per lesson, and each starts from a real pain. Each one is a sharper version of an idea from Chapter 01.

3.2 What a "responsibility" really is

"A class should do one thing" sounds right. But it is too vague to use. Is "calculate pay" one thing? Is "handle employees" one thing? Martin's sharper wording is about change. A class's responsibility depends on who would ask you to change it.

Think of the person or group that a piece of code serves. They are the ones who would ask for changes to it. Such a person or group is called an actor. (Like an actor in a play, it is someone who takes part.) The principle then reads:

A class should have one, and only one, reason to change. In other words, it should be responsible to one actor. This is the Single Responsibility Principle (SRP).

Apply it to Employee. Ask "who would ask me to change this method?":

MethodWho asks for changes (actor)Their kind of change
calculatePay()AccountingOvertime rules, pay rates
reportHours()HRWhat counts as a working week
toCsv()The database teamStorage format, new columns

Three actors means three reasons to change. So this one class has three responsibilities. The shared regularHours() helper is where they crashed into each other. It looked like one rule. But it was really two different rules (Accounting's 35 and HR's 40). They just happened to use the same number on day one.

"One responsibility" does not mean "one method." Many beginners count methods. But a class with ten methods can still have one responsibility, if one actor asks for all its changes. And a class with two methods can have two responsibilities, if two actors use them. Count actors, not methods.

3.3 The cure: split along the actors

The cure has two steps:

  1. Give each actor its own class, holding that actor's rules.
  2. Put the plain facts that every actor needs (name, hours, rate) in a separate data class. That data class holds no actor's rules.

Notice the two Math.min(...) lines in PayCalculator and HoursReporter. They look like duplicated code. On day one, they even used the same number. But they change for different reasons, when different actors ask. Code that looks the same but stands for different rules is called accidental duplication. Two twins can look alike and still be different people. Merging the two rules is what caused the bug. Lesson 11's "don't repeat yourself" rule comes with exactly this warning.

A class Invoice has total(), applyDiscount() and printAsPdf(). How many responsibilities, by the actor test?

Two. total() and applyDiscount() both change when the pricing and sales rules change. That is one actor, so they belong together. printAsPdf() changes when the person who designs the document wants a new layout. That is a different actor. So split out the printing (an InvoicePdf class), and keep total and discount together. Counting methods would have said "three," which is the wrong answer.

3.4 What each piece gains

  • Safety: a change for one actor cannot reach another actor's code, because they share nothing but plain data.
  • Findability: "where is the overtime rule?" has exactly one answer.
  • Testability: each class is tested alone, with no unrelated setup.
  • Fewer clashes in a team: when two developers work for two actors, they edit two different files.

The honest cost: the caller now deals with three small classes instead of one. And someone must wire them together (create them and connect them). In the kata, Main does that. In the hub, Main does it too, but now it does only the wiring. Sometimes callers find it painful to juggle many small objects. A single "front door" over them is a named pattern of its own (Lesson 20).

4The kata

The kata lives in package com.katas.srp. The god class stays in naive/Employee.java. It already has Accounting's change in it, so you can run its bug and test it. Two small files hold no rules at all:

  • Saved: katas/src/main/java/com/katas/srp/EmployeeData.java holds the plain facts (name, hoursWorked, hourlyRate) with getters.
  • Saved: katas/src/main/java/com/katas/srp/EmployeeCsv.java turns those facts into "Asha,45,20".

Saved: katas/src/main/java/com/katas/srp/PayCalculator.java

// The RIGHT WAY, part 2: Accounting's rules, and only Accounting's.
package com.katas.srp;

// Answers to ONE group: Accounting. Its overtime cutoff is private to it,
// so changing it can never touch HR's report.
public class PayCalculator {

    // Accounting's rule: for pay, overtime starts after 35 hours.
    private static final int PAY_OVERTIME_AFTER = 35;

    // Regular hours at the normal rate, overtime at double.
    public int calculatePay(EmployeeData employee) {
        // Hours up to Accounting's cutoff.
        int regular = Math.min(employee.getHoursWorked(), PAY_OVERTIME_AFTER);
        // Hours beyond it, never negative.
        int overtime = Math.max(employee.getHoursWorked() - regular, 0);
        // Normal pay plus double-rate overtime.
        return regular * employee.getHourlyRate() + overtime * employee.getHourlyRate() * 2;
    }
}

Saved: katas/src/main/java/com/katas/srp/HoursReporter.java

// The RIGHT WAY, part 3: HR's rules, and only HR's.
package com.katas.srp;

// Answers to ONE group: HR. Its idea of "regular hours" is its own, and it
// stays 40 no matter what Accounting decides about pay.
public class HoursReporter {

    // HR's rule: a regular working week is up to 40 hours.
    private static final int REGULAR_WEEK = 40;

    // One line for HR's weekly report.
    public String reportHours(EmployeeData employee) {
        // Hours up to HR's cutoff.
        int regular = Math.min(employee.getHoursWorked(), REGULAR_WEEK);
        // e.g. "Asha: 40 regular hours".
        return employee.getName() + ": " + regular + " regular hours";
    }
}

Saved: katas/src/main/java/com/katas/srp/Main.java

// The runnable demo for Lesson 05's kata.
package com.katas.srp;

// Runs one week for one employee through the god class and through the
// split classes, so the HR report's silent change is visible side by side.
public class Main {

    // The JVM starts here when you run this class.
    public static void main(String[] args) {
        // NAIVE: one class, three departments, one shared helper.
        com.katas.srp.naive.Employee asha = new com.katas.srp.naive.Employee("Asha", 45, 20);
        // Accounting's number is right: 35 x 20 + 10 x 40 = 1100.
        System.out.println("Naive pay: " + asha.calculatePay());
        // HR's number moved from 40 to 35 although HR asked for nothing.
        System.out.println("Naive HR report: " + asha.reportHours());

        // SRP: the same facts, three classes, each answering to one department.
        EmployeeData data = new EmployeeData("Asha", 45, 20);
        // Accounting's rule, kept in PayCalculator.
        System.out.println("SRP pay: " + new PayCalculator().calculatePay(data));
        // HR's rule, kept in HoursReporter: still 40.
        System.out.println("SRP HR report: " + new HoursReporter().reportHours(data));
        // Storage format, kept in EmployeeCsv.
        System.out.println("SRP CSV: " + new EmployeeCsv().toCsv(data));
    }
}

What happens when it runs

  1. Naive calculatePay(): regularHours() gives min(45, 35) = 35, overtime is 10, so 35 × 20 + 10 × 20 × 2 = 700 + 400 = 1100.
  2. Naive reportHours() calls the same regularHours(), which gives 35, so it prints "Asha: 35 regular hours." HR's rule (40) is lost.
  3. PayCalculator uses its private 35 and also gives 1100. Accounting is still served correctly.
  4. HoursReporter uses its private 40: min(45, 40) = 40, giving "Asha: 40 regular hours." HR is untouched by Accounting's change.
  5. EmployeeCsv prints the raw facts: "Asha,45,20".

5Applied to the Smart Home Hub

The pain, arriving in the hub

Three requests arrive in the same week, from three different people:

  • The installer will add devices next month.
  • The homeowner wants a fixed start-up routine: everything on, then the living-room light off.
  • The app designer wants a proper house report: how many devices, how many are on, each one's status, then the activity history.

All three would land in Main. It already builds the devices, wraps them, loops over them and prints the log. That is one method with three actors. And there is no way to test the report, because Main prints it straight to the console. It is the Employee problem, right here in our own project.

The split

Saved: smarthome/src/main/java/com/smarthome/home/HomeSetup.java

// Code about the house as a whole lives in the "home" package.
package com.smarthome.home;

// The logging wrapper and the log it writes to.
import com.smarthome.activity.ActivityLog;
import com.smarthome.activity.LoggedDevice;
// The contract and the concrete device kinds this house contains.
import com.smarthome.devices.Device;
import com.smarthome.devices.Light;
import com.smarthome.devices.Thermostat;

// The JDK's list interface.
import java.util.List;

// ONE responsibility: "which devices does this house have, and how are they
// wired?" It answers to whoever installs the house. Adding a device changes
// this class and nothing else.
public class HomeSetup {

    // Build every device in the house, each wrapped so its switching is logged.
    public List<Device> createDevices(ActivityLog log) {
        // An unmodifiable list: the setup is fixed once created.
        return List.of(
                // A real Light inside a LoggedDevice.
                new LoggedDevice(new Light("Living Room Light"), log),
                // A real Thermostat inside a LoggedDevice.
                new LoggedDevice(new Thermostat("Hall Thermostat", 21), log)
        );
    }
}

Saved: smarthome/src/main/java/com/smarthome/home/Hub.java

// Code about the house as a whole lives in the "home" package.
package com.smarthome.home;

// The contract: the hub never names a concrete device class.
import com.smarthome.devices.Device;

// The JDK's list interface.
import java.util.List;

// ONE responsibility: operating the house (starting it up, switching
// devices). It answers to whoever decides how the home behaves. It does not
// know which devices exist (HomeSetup) or how anything is displayed (report).
public class Hub {

    // The devices under control. Typed by the contract.
    private final List<Device> devices;

    // The devices are handed in: the hub operates them but did not choose them.
    public Hub(List<Device> devices) {
        // Keep an unmodifiable copy, so nobody can add or remove behind our back.
        this.devices = List.copyOf(devices);
    }

    // Switch every device on.
    public void startUp() {
        // Same call for every device; each does its own thing.
        for (Device device : devices) {
            // Polymorphism at work, through the Device contract.
            device.turnOn();
        }
    }

    // Switch one device off, found by its name.
    public void turnOff(String name) {
        // Find it (or fail loudly), then switch it off.
        find(name).turnOff();
    }

    // The devices, for anyone who needs to read their state.
    public List<Device> devices() {
        // Already unmodifiable (List.copyOf), so safe to hand out.
        return devices;
    }

    // Look a device up by its exact name.
    private Device find(String name) {
        // Check each device in turn...
        for (Device device : devices) {
            // ...and return the first whose name matches.
            if (device.getName().equals(name)) {
                // Found it.
                return device;
            }
        }
        // No match: refuse loudly, naming what was asked for.
        throw new IllegalArgumentException("No device named: " + name);
    }
}

The report builds its text piece by piece. The JDK has a tool for that: a piece of text that can grow. append(...) adds to its end. toString() gives back the finished String. That tool is called StringBuilder. It is faster than joining many strings with + in a loop.

Also notice: the report returns the text instead of printing it. That one choice is what makes the report testable.

Saved: smarthome/src/main/java/com/smarthome/report/HouseReport.java

// Presentation code lives in its own "report" package.
package com.smarthome.report;

// The contract: the report reads devices, whatever their kind.
import com.smarthome.devices.Device;

// The JDK's list interface.
import java.util.List;

// ONE responsibility: how the house's state LOOKS as text. It answers to
// whoever designs the display. It changes nothing; it only reads and formats.
public class HouseReport {

    // Turn the devices and the activity history into one block of text.
    public String render(List<Device> devices, List<String> activity) {
        // StringBuilder: a growable piece of text; append() adds to its end.
        StringBuilder text = new StringBuilder();
        // The heading.
        text.append("=== House report ===\n");
        // Count how many devices are currently on.
        int onCount = 0;
        // Look at each device...
        for (Device device : devices) {
            // ...and count it if it is on.
            if (device.isOn()) {
                // One more device on.
                onCount++;
            }
        }
        // Summary line, e.g. "Devices: 2 (1 on)".
        text.append("Devices: ").append(devices.size()).append(" (").append(onCount).append(" on)\n");
        // One indented status line per device.
        for (Device device : devices) {
            // Each device describes itself in its own words.
            text.append("  ").append(device.status()).append("\n");
        }
        // The activity heading, with the number of entries.
        text.append("Activity (").append(activity.size()).append(" entries):\n");
        // Each entry numbered from 1.
        for (int i = 0; i < activity.size(); i++) {
            // i starts at 0, so add 1 for human numbering.
            text.append("  ").append(i + 1).append(". ").append(activity.get(i)).append("\n");
        }
        // The finished text.
        return text.toString();
    }
}

What this adds: a proper house report that counts the devices that are on. And each of the three actors now has one file to change:

  • Adding a device touches only HomeSetup.
  • Changing the start-up routine touches only Hub.
  • Restyling the report touches only HouseReport.

6In the wild

The JDK's date-and-time library keeps what a date is separate from how a date looks:

  • java.time.LocalDate holds a date and knows calendar maths (plusDays, isLeapYear…).
  • java.time.format.DateTimeFormatter owns the display rules: "16/10/2026" versus "Oct 16, 2026".

LocalDate does have a handy method, format(formatter). But the formatting rules live in the formatter. So a designer who changes a date style never touches calendar code. And a calendar fix never touches display code. That is the hub's HouseReport split, at JDK size.

On teams, two developers sometimes edit the same lines of the same file at the same time. When Git tries to combine their work, it cannot decide whose version wins. That is called a merge conflict. SRP problems often show up this way: two developers, working for two different groups, keep editing the same file. "Who would ask for this change?" is also a strong code-review question. If the answer for one class is "three different teams," it is a god class in the making.

7When NOT to use it

The over-application trap

If you read it wrongly, "one responsibility" becomes "one method per class." Then a design turns into a crowd of tiny classes that only pass calls along.

Suppose we split HouseReport into ReportHeaderFormatter, DeviceLinesFormatter, ActivityLinesFormatter, and a ReportAssembler to call them. Check them with the actor test:

  • Every one of them would change for the same actor, the app designer.
  • They would usually change together: a new style touches all four.

So we would have taken one cohesive class and scattered it. Some classes have almost no behaviour of their own. They hold only a tiny slice of a job. They are called anemic classes ("anemic" means weak, lacking strength). They are the needless-complexity smell from Lesson 04.

The test is never "how many methods?" It is "how many actors?" One actor with ten methods is fine. Two actors sharing one helper is not.

The simpler alternative that often works

Sometimes a class serves two actors, but both parts are tiny and rarely change. Then a clear comment and well-separated private sections can be enough for now. Split the class when the second real change request arrives. That is the moment the clash would actually hurt.

The cost of SRP is real: more files, wiring code, and more hops when reading. Pay it when there are real, separate reasons to change, not imagined ones.

Relatives and look-alikes

  • Cohesion (Lesson 04) is the measure. SRP is the rule built on it, with "reason to change" as the ruler.
  • Interface Segregation (Lesson 08) applies the same instinct to interfaces, from the side of the code that uses them.
  • DRY (Lesson 11) says "don't repeat yourself." SRP explains when not to merge look-alike code: when the copies serve different actors (accidental duplication).

8Key takeaways

  • The Single Responsibility Principle says a class should have one reason to change. That means it should answer to one actor: one person or group who would ask for its changes.
  • Count actors, not methods. "Who would ask me to change this?" finds responsibilities far more reliably than "does it do one thing?"
  • When one class serves several actors, a change for one can quietly break another. A common cause is a shared helper that merges rules that only looked alike.
  • Splitting along actors gives each change one obvious home. It keeps teams out of each other's files, and each piece can be tested alone. The price is more classes and some wiring code.
  • Over-splitting is a smell too. Pieces that always change together for the same actor belong in one cohesive class, not in a crowd of anemic one-method classes.

10Catalog update

The first entry in the course's cheat-sheet: Single Responsibility Principle, in the pattern catalog. In brief:

  • Intent: one reason to change; answer to one actor.
  • Pain: a god class where one group's change breaks another's feature.
  • Use when: no one-sentence description without "and"; different people request changes to different parts; a helper shared across actors.
  • Do NOT use when: the parts always change together for one actor; the split would create anemic one-method classes; the reasons are imagined.
  • Cost: more classes, wiring code, more hops.
  • Seen in the wild: LocalDate vs DateTimeFormatter.
  • Where: kata com.katas.srp; hub home.HomeSetup, home.Hub, report.HouseReport.

11Key words

SOLID
Five class-design rules: Single responsibility, Open/closed, Liskov substitution, Interface segregation, Dependency inversion.
Payroll
The work (or code) of calculating how much each worker is paid.
HR
Human Resources: the team that looks after a company's staff.
CSV
Comma-separated values: data written as one line of text with commas between values.
God class
A class that does many unrelated jobs for many groups, so every change touches it.
Actor
A person or group whose needs some code serves, and who would ask for changes to it.
Responsibility
A reason to change: one actor that a class answers to.
Single Responsibility Principle (SRP)
A class should have one, and only one, reason to change: it answers to one actor.
Accidental duplication
Code that looks the same but stands for different rules for different actors. Merging it ties them together.
Wire (objects)
Create objects and connect them to each other, usually in one place like Main.
StringBuilder
The JDK's growable text: append(...) adds to its end, toString() gives the finished String.
Merge conflict
When Git cannot combine two people's edits to the same lines, and a human must choose.
Anemic class
A class with almost no behaviour of its own, holding a tiny slice of a job; the result of over-splitting.

12Quick recap

  • SRP: a class should have one reason to change, meaning it answers to one actor.
  • Find responsibilities by asking "who would ask me to change this?", not by counting methods.
  • A helper shared by two actors is where their changes crash into each other.
  • Split along actors; keep shared plain facts in a data class with no rules.
  • Do not over-split: parts that always change together for one actor belong together.
