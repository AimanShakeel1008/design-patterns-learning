I — Interface Segregation Principle

No class should be forced to promise what it cannot do. No client should depend on methods it never uses. Split fat contracts into small roles.

Kata package: com.katas.isp (wrong way in com.katas.isp.naive).
Smart Home Hub: Device slimmed; created Switchable, Dimmable, Lockable, SmokeAlarm, DoorLock; AbstractDevice renamed SwitchableDevice; modified Light, LoggedDevice, routines, Hub, HomeSetup, HouseReport, Main; contract tests reorganised.
Prerequisites: Lesson 07 — Liskov Substitution.

  • Why one big interface that bundles many jobs hurts both the classes that implement it and the code that uses it.
  • The Interface Segregation Principle: split big contracts into small "role" interfaces.
  • How the smoke alarm and a door lock finally join the hub safely.

1The pain

Lesson 07 ended with a smoke alarm that couldn't join the hub. Here is the same problem in its classic form: an office printer.

1.1 One interface for every machine

An office system has one interface for "a machine." A machine can print, scan, and fax. (To scan is to copy paper into the computer. To fax is an older way of sending a paper copy over a phone line.) A multi-function machine, which does all three, fits it perfectly. Then someone needs to plug in an old printer that only prints:

public interface Machine {
    String print(String document);
    String scan(String document);
    String fax(String document, String number);
}

public class OldPrinter implements Machine {
    public String print(String d)  { return "Printed: " + d; }
    public String scan(String d)   { throw new UnsupportedOperationException("Old printers cannot scan"); }
    public String fax(String d, String n) { throw new UnsupportedOperationException("Old printers cannot fax"); }
}

1.2 It hurts from both sides

This big interface hurts from both sides:

  • The implementer side (the class that implements it). OldPrinter is forced to "implement" two jobs it cannot do. So it refuses them. Those are two refused bequests. Each one breaks Liskov's rule, and waits for a client to trip over it.
  • The client side (the code that uses it). A report module only prints. But it must still depend on Machine. So it is coupled to scanning and faxing, which it never uses. If the fax method's signature changes, the report module must be compiled and checked again anyway. And its test needs a fake that implements all three methods, two of them for nothing.

Predicted symptom

Naive old printer: Printed: Invoice
Naive old printer refused: Old printers cannot scan

1.3 Naming the pain

This pain has a name: a fat interface. It is one contract that bundles several unrelated jobs. So implementers must promise too much, and clients must depend on too much.

Full wrong-way code: katas/src/main/java/com/katas/isp/naive/ (Machine, OldPrinter)

2Real-world analogy

Job adverts. A shop posts one job advert: "Must drive the van, bake the bread, and do the accounts." Here is what goes wrong:

  • Almost nobody can do all three. So the baker who gets hired fakes the accounting.
  • The delivery manager only needs a driver. But they must still quiz people on baking.

The fix is separate roles: Driver, Baker, Bookkeeper. One talented person may hold two roles. But each manager hires only for the role they need.

3The principle explained

3.1 The principle

Robert C. Martin first wrote this principle down after helping with a printing system at Xerox, a printer company. Its one central "job" class had grown huge. Every small change spread into code that didn't care about it. His rule:

"Clients should not be forced to depend upon interfaces that they do not use." This is the Interface Segregation Principle (ISP), the "I" in SOLID. ("Segregation" just means "separating.")

The cure is to split a fat interface into several small ones. Each small one is shaped around what one kind of client needs.

3.2 Role interfaces

Some small interfaces are named after one role a client needs: "something that prints," "something that can be switched." Such an interface is called a role interface. Three facts make it work:

  • A class may implement many interfaces. class MultiFunctionMachine implements Printer, Scanner, Fax. extends allows only one parent (Lesson 02). But a class can sign as many contracts as it can keep.
  • The same object can be seen through different roles. Scanner scanner = office; and Fax fax = office; point at one object. But each variable only allows that role's methods. So a client receives the object through the one role it needs. Think of one person who is both a parent and a teacher: their pupils only see the teacher.
  • An interface can build on another. In the hub, interface Switchable extends Device means "every switchable thing is also a device, plus three switching methods." An interface may extend several other interfaces. In UML, this is drawn like inheritance: a solid line with a hollow triangle.

3.3 How to split: by client, not by implementer

Where should you draw the lines? Ask "what does each client actually call?" Do not ask "what can each machine do?" In the hub:

  • Routines call turnOn, turnOff, isOn and getName.
  • The report calls getName and status.

Those two client needs become the two contracts: Switchable and Device. Splitting along what clients need keeps every interface meaningful. You don't end up with one interface per method.

ISP vs SRP. Both say "split," so they are easy to confuse. The quick check below explains the difference. In short: SRP splits classes by who asks for changes. ISP splits interfaces by who calls them.

ISP and SRP (Lesson 05) both say "split." What is the difference?

SRP looks at a class from the side of the people who ask for changes: one actor per class. ISP looks at an interface from the side of the code that uses it: no client should depend on methods it doesn't call.

They often agree. A class that answers to two actors often ends up offering two role interfaces. But one class can sign many small interfaces and still have one responsibility. MultiFunctionMachine is one example: its one job is "a multi-function office machine."

3.4 What each side gains

  • Implementers promise only what they can keep. So there are no more refused bequests. Contract tests (Lesson 07) can be split the same way.
  • Clients depend on fewer methods. That means less coupling, and fewer changes that spread to them. And the compiler stops them from calling something the object cannot do.
  • Tests need tiny fakes: a print-only client's fake implements one method.

4The kata

The kata lives in package com.katas.isp:

  • Saved: Printer.java, Scanner.java, Fax.java are one-method role interfaces (print, scan, fax). Scanner here is our own role. It has nothing to do with the JDK's java.util.Scanner.
  • Saved: OldPrinter.java now implements Printer only. It has nothing to refuse.

Saved: katas/src/main/java/com/katas/isp/MultiFunctionMachine.java

// A machine that really does all three jobs.
package com.katas.isp;

// One class may implement SEVERAL small interfaces. It can be handed to a
// print-only client as a Printer, to a scan-only client as a Scanner, and so
// on; each client sees only the role it needs.
public class MultiFunctionMachine implements Printer, Scanner, Fax {

    // Keeps the Printer role.
    @Override
    public String print(String document) {
        // Report the print.
        return "Printed: " + document;
    }

    // Keeps the Scanner role.
    @Override
    public String scan(String document) {
        // Report the scan.
        return "Scanned: " + document;
    }

    // Keeps the Fax role.
    @Override
    public String fax(String document, String number) {
        // Report the fax.
        return "Faxed " + document + " to " + number;
    }
}

Saved: katas/src/main/java/com/katas/isp/ReportPrinter.java

// A CLIENT that only prints, so it asks only for the printing role.
package com.katas.isp;

// The JDK's growable list.
import java.util.ArrayList;
// The JDK's list interface.
import java.util.List;

// Depends on Printer alone: changes to scanning or faxing can never affect
// it, any printer (old or multi-function) can serve it, and its test needs a
// one-method stand-in.
public class ReportPrinter {

    // The only capability this client needs.
    private final Printer printer;

    // The caller decides which printer.
    public ReportPrinter(Printer printer) {
        // Remember it.
        this.printer = printer;
    }

    // Print every document, collecting what the printer reports.
    public List<String> printAll(List<String> documents) {
        // One result line per document.
        List<String> results = new ArrayList<>();
        // Print each in turn.
        for (String document : documents) {
            // The single method this client uses.
            results.add(printer.print(document));
        }
        // An unmodifiable copy for the caller.
        return List.copyOf(results);
    }
}

5Applied to the Smart Home Hub

The pain, already in the hub

Device promised five things, including turnOn and turnOff. So every device had to be switchable. Lesson 07's smoke alarm could only join by refusing turnOff, and that would crash "Away" mode. Now a door lock is coming, and "turn on the front door" means nothing.

The tempting next step makes it worse: add setBrightness, lock and unlock to Device as well. Then:

  • every thermostat must refuse lock();
  • every lock must refuse setBrightness();
  • the house report depends on eleven methods, just to print a name and a status.

That is the fat Machine, in our own code.

The split

Ask what each client calls. Routines switch. The report names and describes. Some future feature will dim lights, and a security feature will lock doors. So we get these contracts:

Saved: smarthome/src/main/java/com/smarthome/devices/Device.java (slimmed) and Switchable.java

// THE hub's base contract: what EVERY device, of any kind, can promise.
public interface Device {
    // PROMISE: the same name it was created with, for its whole life.
    String getName();
    // PROMISE: starts with getName() + ": ".
    String status();
}

// A CAPABILITY: devices that can be switched on and off. "extends Device"
// means every Switchable is also a Device (it has a name and a status).
public interface Switchable extends Device {
    // PROMISE: never refuses; afterwards isOn() is true.
    void turnOn();
    // PROMISE: never refuses; afterwards isOn() is false.
    void turnOff();
    // PROMISE: reflects the most recent turnOn()/turnOff(); false when new.
    boolean isOn();
}

Two more contracts follow the same pattern:

  • Saved: Lockable.java: extends Device, and adds lock, unlock and isLocked.
  • Dimmable.java: setBrightness(0..100) and getBrightness. It does not extend Device, on purpose. It is an add-on that a class combines with other contracts.

Saved: smarthome/src/main/java/com/smarthome/devices/SmokeAlarm.java

// Same package as the base Device contract.
package com.smarthome.devices;

// A smoke alarm: a Device, and NOTHING else. It is always armed and must
// never be switched off, so it does not sign Switchable, and therefore has
// no turnOff() to refuse. Lesson 07 could not add it without breaking the
// fat contract; with small contracts it keeps every promise it makes.
public class SmokeAlarm implements Device {

    // The alarm's name, set once.
    private final String name;

    // Build an alarm with its name.
    public SmokeAlarm(String name) {
        // Store the name.
        this.name = name;
    }

    // Keeps Device's promise: the creation-time name.
    @Override
    public String getName() {
        // Hand back the private name.
        return name;
    }

    // Keeps Device's promise: starts with the name.
    @Override
    public String status() {
        // Always armed, e.g. "Hallway Smoke Alarm: ARMED".
        return name + ": ARMED";
    }
}
  • Saved: DoorLock.java implements Lockable. It starts locked (the safe default), and reports "Front Door: LOCKED".
  • Saved: SwitchableDevice.java is the old AbstractDevice, with a new name. The name "abstract device" stopped being true. It is now the shared parent for devices that switch. Keeping the old name would be the opacity smell from Lesson 04 (a name that hides what the code means).
  • Modified: Light.java now extends SwitchableDevice implements Dimmable. Its brightness starts at 100 and is guarded to 0–100. When dimmed, its status says "ON at 40%." At full brightness it still says just "ON." So nothing that worked before changes.

The clients now ask for exactly what they use:

  • Routine + AllOn/AllOff/KeepOnly: applyTo(List<Switchable> devices). "Away" can never be handed the smoke alarm, and the compiler enforces it.
  • LoggedDevice now implements and wraps Switchable: what it logs is switching.
  • HouseReport: render(List<Device> devices, List<Switchable> switchables, List<String> activity). It uses Device for the status lines, and Switchable only to count how many are on.

Saved: smarthome/src/main/java/com/smarthome/home/Hub.java (modified)

    // The devices that can be switched: the only ones routines may touch.
    private final List<Switchable> switchables;

    // Every device in the house, switchable or not, for reading and reporting.
    private final List<Device> allDevices;

    // The setup hands over switchable devices and all the others separately.
    public Hub(List<Switchable> switchables, List<Device> otherDevices) {
        // An unmodifiable copy of the switchable ones.
        this.switchables = List.copyOf(switchables);
        // Build the full list: switchables first, then the rest.
        List<Device> all = new ArrayList<>();
        // Every Switchable is also a Device, so it may join a List<Device>.
        all.addAll(switchables);
        // The devices that only promise the base contract.
        all.addAll(otherDevices);
        // Keep an unmodifiable copy.
        this.allDevices = List.copyOf(all);
    }

    // Run any routine on the switchable devices.
    public void run(Routine routine) {
        // Only switchable devices are handed over.
        routine.applyTo(switchables);
    }

Why two lists? Why not one list, plus a check at run time: "is this one switchable?" (instanceof)? Because Lesson 07 taught that instanceof in client code is a warning sign. Here is the better way:

  1. HomeSetup creates the devices, so it already knows each one's kind.
  2. So it hands them over in groups: createSwitchables(log) and createOtherDevices().
  3. The types now carry the knowledge, and the compiler checks it.

Main changes by two lines, to pass both groups along.

An honest cost. The light reaches the hub inside a LoggedDevice, which is a Switchable. So the hub cannot see that the light is also Dimmable. A wrapper shows only the contract it wraps. Nothing dims lights through the hub yet, so we stop here (no feature without a need). Later, dimming may become a real requirement. Then we will need to know how wrappers and extra abilities combine. Lesson 19 answers that properly.

6In the wild

java.lang.AutoCloseable is a role interface with exactly one method: close(). Some things must be closed after use, like an open file. Such things are called resources. Here is how Java uses the role:

  1. Java has a try-with-resources statement: try (FileInputStream in = new FileInputStream("a.txt")) { … }.
  2. At the end of the block, it closes the resource automatically, even if an exception happened.
  3. To do that, it depends on nothing but the one close() role.

Files, network connections and database connections all sign AutoCloseable, next to their many other contracts. Try-with-resources never needs to know what else they can do.

You will keep meeting other one-role JDK interfaces: Runnable (just run()), Comparable (just compareTo), and Iterable (just iterator(), which is all the for (x : list) loop needs).

Big projects often grow "god interfaces," like a UserService with forty methods. Then every test of every caller needs a forty-method fake. Splitting them by client (UserLookup, UserRegistration…) is one of the cheapest and most valuable refactorings in practice. "Which methods does this caller really use?" is a good code-review question.

7When NOT to use it

The over-application trap

Taken to the extreme, ISP produces an interface for every method: Nameable, Describable, TurnOnable, TurnOffable… Each class then implements a dozen interfaces. Nobody can see what a "device" is any more. That is scattering again: the anemic over-split from Lesson 05, now for interfaces.

Methods that the same clients always use together belong in one interface. turnOn, turnOff and isOn stay together in Switchable, because every client of one uses the others.

The simpler alternative, and the cost

Say an interface has one implementation and one client, and they fit perfectly. Then there is nothing to split. Leave it whole. Split only in two cases:

  • a real implementer can't keep part of the contract (the smoke alarm); or
  • real clients use clearly different parts.

The costs are real, and this lesson showed them:

  • More types to name and find your way around.
  • Classes that list several interfaces.
  • Code that must send the right objects to the right clients (our two lists). This is sometimes called routing.
  • Wrappers that hide extra abilities.
  • A wide edit when an interface used by many classes changes, as this lesson's refactoring was.

That last cost is the strongest reason to get contracts small before many classes depend on them.

Relatives and look-alikes

  • SRP (Lesson 05) splits classes by who asks for changes. ISP splits interfaces by who calls them.
  • LSP (Lesson 07): ISP is its usual cure. A contract small enough for every implementer to keep leaves nothing to refuse.
  • Cohesion (Lesson 04): a well-segregated interface is a cohesive interface, one purpose with one sentence and no "and."

8Key takeaways

  • The Interface Segregation Principle says no client should be forced to depend on methods it does not use. So no class should be forced to promise methods it cannot keep.
  • A fat interface hurts from both sides. Implementers end up refusing methods (LSP violations). Clients are coupled to methods they never call.
  • The cure is small role interfaces, shaped by what each client calls. A class may implement several of them. An interface may extend another to build on it.
  • Give each client exactly the role it needs. Then the compiler stops wrong calls before they happen. For example, "Away" can no longer be handed a smoke alarm.
  • Do not split into one-method pieces. Methods that are always used together belong together. Every split costs more types, more routing code, and abilities hidden behind wrappers.

interface Worker { String work(); String eat(); }

class HumanWorker implements Worker {

    public String eat()  { return "Human eating lunch"; }

// The canteen only ever calls eat().
static void serveLunch(List<Worker> workers) { for (Worker w : workers) System.out.println(w.eat()); }
Click to reveal the answer

Implementer-side pain: RobotWorker is forced to promise eat(), and refuses it. That is a refused bequest. Handing the canteen a robot crashes it.

Client-side pain: the canteen only ever calls eat(), yet depends on all of Worker, including work(). The production line only calls work(), yet depends on eat().

Split by client: the line needs "something that works," and the canteen needs "something that eats."

// The role the production line uses.
interface Workable { String work(); }
// The role the canteen uses.
interface Eater { String eat(); }

// A human holds both roles.
class HumanWorker implements Workable, Eater {
    public String work() { return "Human assembling"; }
    public String eat()  { return "Human eating lunch"; }
}
// A robot holds only the role it can keep: nothing to refuse.
class RobotWorker implements Workable {
    public String work() { return "Robot welding"; }
}

// The canteen asks only for eaters; the line asks only for workables.
static void serveLunch(List<Eater> diners) { for (Eater e : diners) System.out.println(e.eat()); }
static void runShift(List<Workable> crew)   { for (Workable w : crew) System.out.println(w.work()); }

10Catalog update

Entry 4 added: Interface Segregation Principle, in the pattern catalog. In brief:

  • Intent: no client should depend on methods it does not use; split fat interfaces into role interfaces.
  • Pain: implementers forced to refuse methods; clients coupled to methods they never call; bloated test fakes.
  • Use when: an implementer can't keep part of a contract; clients use clearly different subsets.
  • Do NOT use when: methods are always used together; one implementer and one client fit perfectly; it would mean one interface per method.
  • Cost: more types; routing objects to the right clients; capabilities hidden behind wrappers; wide edits when a shared interface is split late.
  • Seen in the wild: AutoCloseable and try-with-resources; Runnable, Comparable, Iterable.
  • Where: kata com.katas.isp; hub Device / Switchable / Dimmable / Lockable.

12Quick recap

  • ISP: no client should depend on methods it does not use.
  • A fat interface forces implementers to refuse methods, and ties clients to methods they never call.
  • Split by what each client calls, into small role interfaces; a class may implement several.
  • Give each client only the role it needs, and the compiler blocks wrong calls.
  • Do not split into one-method pieces: methods always used together belong together.

Lesson 09 — D: the Dependency Inversion Principle. Every lesson so far has quietly pointed the arrows at contracts. Now we make it a rule for the whole design: high-level policy must not depend on low-level detail. We wire the hub by hand, so its core never names a concrete device.
