L — Liskov Substitution Principle

A subclass, or any implementation of a contract, must keep every promise its parent makes. Then code written for the parent keeps working when it is handed the substitute.

Kata package: com.katas.lsp (wrong way in com.katas.lsp.naive).
Smart Home Hub: modified devices/Device.java (contract written down); created test files DeviceContractTest, LightContractTest, ThermostatContractTest, activity/LoggedDeviceContractTest.
Prerequisites: Lesson 06; inheritance and overriding from Lesson 02.

  • Why a subclass can compile and pass its own tests, yet still break other people's correct code.
  • The Liskov Substitution Principle: a stand-in must keep every promise of the thing it stands in for.
  • How to write promises down and test every class against them.

1The pain

In school geometry, a square is a rectangle. So in code, Square extends Rectangle must be right. It compiles, and it passes its own tests. Yet it breaks someone else's code that was never wrong.

1.1 A square that extends a rectangle

A Rectangle has setWidth and setHeight. A square must keep its sides equal. So Square overrides both setters to change both sides at once. Meanwhile, a teammate writes this perfectly reasonable code for Rectangle:

public int stretchTo5By4(Rectangle rectangle) {
    rectangle.setWidth(5);     // "changes the width only"
    rectangle.setHeight(4);    // "changes the height only"
    return rectangle.area();    // so this must be 20
}

1.2 Handing it a square

Hand it a real rectangle, and you get 20. Now hand it a Square. Java happily accepts it, because a Square is a Rectangle. Then:

  1. setWidth(5) makes it 5×5.
  2. setHeight(4) makes it 4×4.
  3. area() returns 16, not 20.

Predicted symptom

Naive rectangle stretched to 5x4: area 20
Naive square stretched to 5x4: area 16

1.3 Where is the bug?

  • The bug is not in Resizer. It relied only on what Rectangle promised.
  • It is not exactly in Square either. Square keeps its own rule perfectly.
  • The bug is the relationship. Square claims to be a Rectangle, but it breaks one of Rectangle's promises.

The OCP code from Lesson 06 trusted every new class to keep the contract. This is what happens when one doesn't.

Full wrong-way code: katas/src/main/java/com/katas/lsp/naive/ (Rectangle, Square, Resizer)

2Real-world analogy

A replacement delivery driver. Your usual parcel delivery driver (your courier) is off sick. The company sends a replacement. That is fine, as long as the replacement does everything the usual courier promised.

  • They may do more. Maybe they also take parcels after 5 pm, or also deliver on Sundays.
  • They may not do less. They must not refuse parcels over 2 kg. They must not deliver to the right street but the wrong house number.

You should never have to ask "is this the usual courier or the replacement?" before handing over a parcel.

The courierIn code
The usual courier's promisesThe parent type's contract (Rectangle, Device)
The replacementA subclass or another implementation (Square, a new device)
Accepts more parcels than requiredAllowed: a looser precondition
Refuses parcels the usual one tookForbidden: a stricter precondition
Delivers to the wrong house numberForbidden: a weaker postcondition (Square's setters)
"Is this the replacement?" before every hand-overType checks in client code: the symptom of a broken substitute

3The principle explained

3.1 The principle

First, two words. A subtype is any type that can stand in for another: a subclass, or a class that implements an interface. A substitute is a subtype used in place of its parent type. A Square passed where a Rectangle is expected is a substitute.

In 1987, the computer scientist Barbara Liskov gave a talk about what it really means for one type to be a subtype of another. In 1994, she wrote it up exactly, with Jeannette Wing. In plain words:

If some code works with objects of a type, it must keep working when given objects of any subtype. It should not even notice the difference. This is the Liskov Substitution Principle (LSP), the "L" in SOLID.

So a subtype is a safe substitute only if it keeps every promise its parent makes. The rule applies to subclasses and to classes that implement an interface. Both promise to stand in for something.

3.2 Promises, written as contracts

To check a substitute, we need the promises written down. Lesson 01 called the whole bundle of promises a contract. Each method's part of the contract has two halves, plus one rule for the whole object:

  • Before the call. What must be true before you may call a method. Making it true is the caller's job. For new Rectangle(w, h): "both sides are positive." If the caller breaks it, that is the caller's fault. This is called a precondition ("pre" means "before").
  • After the call. What the method guarantees will be true after it returns. Making it true is the method's job. For setWidth(w): "the width is now w, and the height is unchanged." This is called a postcondition ("post" means "after").
  • Always. What is true about the object at all times, between any two calls. For a rectangle: "both sides are positive." You met this in Lesson 01 as an invariant.

Think of a shop: the precondition is "you must pay first" (your job). The postcondition is "you get the item you paid for" (the shop's job).

3.3 The rules a substitute must follow

Part of the contractA substitute may…A substitute must never…
Preconditions (what it demands)demand the same, or less (accept more inputs)demand more: refuse inputs the parent accepted
Postconditions (what it promises)promise the same, or morepromise less: skip, or contradict, a guaranteed result
Invariantsadd invariants of its ownbreak any invariant of the parent
Exceptionsthrow the same kinds of failure the parent's contract allowsthrow where the parent promised success
Side effectschange its own extra statechange state the parent's methods promised to leave alone

(A side effect is any change a method makes besides returning its answer, such as changing a field or printing.)

One sentence holds the whole table: a substitute may ask for less and give more, never ask for more or give less.

"Ask for less" sounds backwards at first. Asking for less means accepting more inputs. A replacement courier who takes parcels of any weight asks for less than one who only takes light parcels. That is safe: everything the old courier accepted, the new one accepts too. The danger is the opposite: a substitute that suddenly refuses inputs the parent accepted.

3.4 The Square/Rectangle problem, worked in full

Trace stretchTo5By4(new Square(2)) against the rules:

  1. The parameter's declared type is Rectangle. The actual object is a Square with sides 2×2.
  2. setWidth(5): dynamic dispatch runs Square.setWidth, which sets width 5 and height 5. Rectangle's postcondition said "height unchanged." The postcondition has been weakened, and the substitute broke its first promise.
  3. setHeight(4) runs Square.setHeight, which sets both sides to 4. The same promise is broken again, in the other direction.
  4. area() returns 4 × 4 = 16. The client reasoned correctly from the contract that it "must be 20." The substitute made that false.

Can we fix Square while it stays a subclass? Try each option:

  • Let setWidth change only the width. Then the object stops being square. Its own invariant breaks.
  • Make setWidth throw an exception for squares. Then it refuses something the parent accepted. That is a stricter precondition.

Every option breaks a rule. The honest conclusion: "is-a" in code means "behaves as," for every promise. A square that can be changed does not behave like a rectangle that can be changed, whatever geometry says.

A subclass of Rectangle overrides setWidth to also log "width changed" to the console. Does it break LSP?

Usually not. It keeps every promise (width becomes w, height unchanged). It also does something extra, and no client relied on that extra thing not happening. It gives more and asks for no more. It would only break LSP in two cases:

  • if the parent's contract promised "no output"; or
  • if the logging could throw an exception where the parent promised success.

3.5 Spotting violations

LSP violations rarely announce themselves. Three signs give them away:

  • Type checks in client code. Java can ask an object whether it is of a given class. shape instanceof Square is true for squares. That is the instanceof operator. Now say a client contains if (rectangle instanceof Square) { … special case … }. That means the client has learned it cannot trust the substitute. Every such check is a patch over a broken promise. It also breaks OCP, because each new badly-behaved subclass needs another check.
  • Refused bequest. A subclass inherits a method it cannot keep. So it throws UnsupportedOperationException, or quietly does nothing. Code that relies on the parent's promise then crashes, or quietly does the wrong thing. ("Bequest" means something left to someone in a will. Here, the child refuses part of what it inherits.)
  • Surprising overrides. An override does something the parent's contract rules out. Examples: Square.setWidth changing the height, a getter that changes state, or a save() that doesn't save. It looks like a normal override, but it breaks clients from the inside.

3.6 The cures

  • Don't inherit what you can't keep. Make the two classes siblings (two children of the same parent) under a smaller contract that both truly keep (Shape).
  • Remove the promise that causes trouble. Square and Rectangle only clash because they can be changed. An object whose state can never change after it is created is called immutable. "Resizing" an immutable rectangle returns a new rectangle. So there is no promise about "the other side stays the same" to break. Think of a printed photo: to "resize" it, you print a new copy.
  • Split a contract that is too big for some implementers, so nobody inherits a method they must refuse. That is the next lesson, in full.

4The kata

The kata lives in package com.katas.lsp:

  • Saved: katas/src/main/java/com/katas/lsp/Shape.java is the small contract: int area() ("a positive number") and String describe().
  • Saved: Square.java has the same shape as the rectangle below, with one side and withSide(int).

Saved: katas/src/main/java/com/katas/lsp/Rectangle.java

// The RIGHT WAY, part 2: a rectangle that never changes after creation.
package com.katas.lsp;

// Immutable: its fields are final and there are no setters. "Resizing"
// returns a NEW rectangle, so no promise about one side staying the same
// can ever be broken behind a caller's back.
public class Rectangle implements Shape {

    // The width, fixed for this object's whole life.
    private final int width;

    // The height, fixed for this object's whole life.
    private final int height;

    // PRECONDITION: both sides must be positive. Callers must meet it.
    public Rectangle(int width, int height) {
        // Refuse a rectangle that cannot exist.
        if (width <= 0 || height <= 0) {
            // Loud refusal naming the bad values.
            throw new IllegalArgumentException("Sides must be positive: " + width + "x" + height);
        }
        // Store the width.
        this.width = width;
        // Store the height.
        this.height = height;
    }

    // A new rectangle with a different width and THIS height.
    public Rectangle withWidth(int newWidth) {
        // This object is untouched; the caller gets a fresh one.
        return new Rectangle(newWidth, height);
    }

    // A new rectangle with a different height and THIS width.
    public Rectangle withHeight(int newHeight) {
        // This object is untouched; the caller gets a fresh one.
        return new Rectangle(width, newHeight);
    }

    // Keeps Shape's promise: a positive area.
    @Override
    public int area() {
        // Width times height.
        return width * height;
    }

    // Keeps Shape's promise: one descriptive line.
    @Override
    public String describe() {
        // e.g. "Rectangle 5x4: area 20".
        return "Rectangle " + width + "x" + height + ": area " + area();
    }
}

(|| means "or": either condition being true is enough.)

Saved: katas/src/main/java/com/katas/lsp/AreaTotaller.java

// A client of the Shape contract: any honest Shape can be substituted.
package com.katas.lsp;

// The JDK's list interface.
import java.util.List;

// Relies only on Shape's promises, which every implementation keeps, so it
// works unchanged for rectangles, squares, and shapes not invented yet.
public class AreaTotaller {

    // Add up the areas of any shapes.
    public int totalArea(List<Shape> shapes) {
        // Start from zero...
        int total = 0;
        // ...and add each shape's area, whatever kind it is.
        for (Shape shape : shapes) {
            // Each shape keeps the promise "area() is its area".
            total += shape.area();
        }
        // The sum.
        return total;
    }
}

Saved: katas/src/main/java/com/katas/lsp/Main.java

// The runnable demo for Lesson 07's kata.
package com.katas.lsp;

// List.of to build a list of shapes.
import java.util.List;

// Shows a Square breaking Rectangle's promise, then a design where every
// substitute keeps every promise it makes.
public class Main {

    // The JVM starts here when you run this class.
    public static void main(String[] args) {
        // NAIVE: one honest client, two objects that both claim to be Rectangles.
        com.katas.lsp.naive.Resizer resizer = new com.katas.lsp.naive.Resizer();
        // A real rectangle keeps the promise: 5 x 4 = 20.
        System.out.println("Naive rectangle stretched to 5x4: area "
                + resizer.stretchTo5By4(new com.katas.lsp.naive.Rectangle(2, 3)));
        // A "rectangle" that is really a Square breaks it: 4 x 4 = 16.
        System.out.println("Naive square stretched to 5x4: area "
                + resizer.stretchTo5By4(new com.katas.lsp.naive.Square(2)));

        // RIGHT WAY: resizing a rectangle makes a new one; squares are siblings.
        Rectangle rectangle = new Rectangle(2, 3).withWidth(5).withHeight(4);
        // A square sized directly.
        Square square = new Square(2).withSide(4);
        // Each describes itself truthfully.
        System.out.println(rectangle.describe());
        // The square's own description.
        System.out.println(square.describe());
        // A client that needs only Shape's promises accepts both.
        System.out.println("Total area of both: " + new AreaTotaller().totalArea(List.of(rectangle, square)));
    }
}

What happens when it runs

  1. The naive rectangle 2×3 becomes 5×3, then 5×4: area 20. The promises are kept.
  2. The naive square 2×2 becomes 5×5 after setWidth(5) (Square's override), then 4×4 after setHeight(4): area 16. Two promises broken, as traced in 3.4.
  3. new Rectangle(2, 3).withWidth(5) creates a new 5×3, and .withHeight(4) creates a new 5×4. The original 2×3 is never touched.
  4. new Square(2).withSide(4) creates a new 4×4 square. A square only ever has one side, so it cannot be "half-resized."
  5. totalArea calls area() on each, dispatched to its own class: 20 + 16 = 36.

Naive square stretched to 5x4: area 16

5Applied to the Smart Home Hub

The pain, arriving in the hub

The hub has trusted every Device since Lesson 01. Since Lesson 06, its routines are closed code that relies on that trust. Now someone asks for a smoke alarm. A smoke alarm must never be switched off. So the obvious code refuses to switch off:

public class SmokeAlarm extends AbstractDevice {
    @Override
    public void turnOff() {
        throw new UnsupportedOperationException("Smoke alarms cannot be switched off");   // refused bequest
    }
    // ...
}

Then the homeowner leaves the house and runs "Away" (AllOff). Here is what happens:

  1. The routine's loop reaches the smoke alarm.
  2. turnOff() throws an exception, and the routine stops halfway.
  3. Every device after the alarm in the list stays on, in an empty house.

The routine's code was correct, closed and tested. Now a newcomer that refuses a promise has broken it.

Predicted symptom

Exception in thread "main" java.lang.UnsupportedOperationException: Smoke alarms cannot be switched off
    at ...SmokeAlarm.turnOff(...)
    at ...AllOff.applyTo(...)

What we do this lesson: write the contract down, and test every substitute against it

We can only check LSP against written promises. The hub's promises were never written down. So we do two things:

  1. Device now states its contract in comments.
  2. One set of tests checks those promises against every implementation.

A set of tests written against a contract, which every implementation must pass, is called a contract test. In JUnit, it is an abstract test class. You write the tests once. Each small subclass only says which kind of device to build. Think of a driving test: one test, and every new driver must pass it.

Saved: smarthome/src/main/java/com/smarthome/devices/Device.java (modified: comments only)

// The CONTRACT:
//   - A new device is OFF.
//   - turnOn() and turnOff() always succeed: no exceptions, no refusals.
//   - After turnOn(), isOn() is true. After turnOff(), isOn() is false.
//   - getName() returns the name the device was created with, never changing.
//   - status() always starts with getName() + ": ".
public interface Device { /* the same five methods, each with its PROMISE comment */ }

Saved: smarthome/src/test/java/com/smarthome/devices/DeviceContractTest.java

// Contract tests live beside the contract they check.
package com.smarthome.devices;

// The @Test marker.
import org.junit.jupiter.api.Test;

// Equality check.
import static org.junit.jupiter.api.Assertions.assertEquals;
// Fails unless the condition is false.
import static org.junit.jupiter.api.Assertions.assertFalse;
// Fails unless the condition is true.
import static org.junit.jupiter.api.Assertions.assertTrue;

// A CONTRACT TEST: the Device promises, written once, run against EVERY
// implementation. It is abstract, so JUnit never runs it on its own; each
// concrete subclass (LightContractTest, ...) supplies one kind of device and
// inherits all five tests. A new device kind earns its place in the hub by
// passing them: that is the Liskov Substitution Principle, checked by machine.
// The test methods are public so subclasses in OTHER packages (such as
// activity.LoggedDeviceContractTest) inherit and run them reliably.
public abstract class DeviceContractTest {

    // Each subclass answers: "build me one of YOUR devices with this name".
    protected abstract Device createDevice(String name);

    // Promise: a new device is off.
    @Test
    public void aNewDeviceIsOff() {
        // Freshly built.
        Device device = createDevice("Test Device");
        // Must report off.
        assertFalse(device.isOn());
    }

    // Promise: after turnOn(), isOn() is true.
    @Test
    public void turnOnMakesItOn() {
        // Freshly built...
        Device device = createDevice("Test Device");
        // ...switched on...
        device.turnOn();
        // ...reports on.
        assertTrue(device.isOn());
    }

    // Promise: after turnOff(), isOn() is false, and turnOff() never refuses.
    @Test
    public void turnOffMakesItOff() {
        // Built and switched on...
        Device device = createDevice("Test Device");
        device.turnOn();
        // ...then switched off (must not throw)...
        device.turnOff();
        // ...reports off.
        assertFalse(device.isOn());
    }

    // Promise: the name is the one it was created with.
    @Test
    public void nameIsTheOneGivenAtCreation() {
        // Built with a specific name.
        Device device = createDevice("Porch");
        // Reports exactly that name.
        assertEquals("Porch", device.getName());
    }

    // Promise: status() starts with "name: ", whether on or off.
    @Test
    public void statusStartsWithTheName() {
        // Built with a specific name.
        Device device = createDevice("Porch");
        // Off: the status line still begins with the name.
        assertTrue(device.status().startsWith("Porch: "));
        // On: same promise.
        device.turnOn();
        assertTrue(device.status().startsWith("Porch: "));
    }
}

Testing the wrapper matters too. Lesson 03's LoggedDevice is handed out in place of real devices. So it is a substitute, and it must keep the contract like any other.

And the smoke alarm? It does not join the hub this lesson. Put through DeviceContractTest, it would fail turnOffMakesItOff with an UnsupportedOperationException. So it is not a Device, and it must not pretend to be one. The honest fix is to stop forcing "can be switched off" on everything in the hub. The Device contract is too big for some devices. Splitting it into smaller, focused promises is the next lesson.

What this adds: no new hub feature, but a safety net for every future one. From now on, every device kind (and every wrapper) gets a three-line contract test. The hub's closed code (routines, report) can keep trusting Device, because the machine checks that trust.

  2. For LightContractTest, JUnit builds the class and finds five inherited @Test methods. Each calls createDevice(...). That call runs LightContractTest's override, which returns a fresh Light.
  3. The same five run for ThermostatContractTest (thermostats) and LoggedDeviceContractTest (wrapped lights). That makes 15 tests: the same promises, checked on three substitutes.
  4. Every existing implementation keeps every promise, so all 15 pass. Main is unchanged and prints the same report as Lessons 05–06.

6In the wild

The JDK's List admits a refused bequest, in writing

The documentation of java.util.List.add marks it as an "optional operation." It may throw UnsupportedOperationException. That is how List.of(...) and List.copyOf(...) can be Lists and still refuse add. You met this in Lesson 03 with ActivityLog.entries().

Strictly speaking, this keeps LSP, because the refusal is part of the written contract. But there is a price. Every caller must know which kind of list it has before calling add. That is exactly the "is this the replacement courier?" question LSP exists to remove. The JDK's designers made this trade-off (giving up one good thing to get another) on purpose, to keep the collections library small.

An older case: Stack

This case is harder to defend. A stack is a pile where you only add or remove at the top, like a stack of plates. java.util.Stack extends java.util.Vector, an older list class. So a "stack" also inherits methods to insert or remove at any position. No stack should allow that. Its own documentation now recommends the Deque interface instead. (A Deque, said "deck," is a list you can add to or remove from at either end.)

"Explain the Liskov Substitution Principle" is a standard interview question. The Square/Rectangle walk-through is the expected answer, as long as you can say which promise breaks (setWidth's "height unchanged" postcondition). In real codebases, look for two signs: instanceof checks scattered through calling code, and overrides that throw UnsupportedOperationException.

7When NOT to use it

What LSP does not demand

LSP does not mean "a subclass must behave exactly the same." That would make subclasses pointless. Puppy.speak() returning "Yip…" instead of "Woof" broke nothing in Lesson 02. Animal's contract only promised "a sound." Different behaviour within the promise is the whole point of polymorphism.

Over-applying LSP goes wrong in two ways:

  • banning all inheritance out of fear;
  • writing contracts so detailed ("status returns exactly these words") that no second implementation could ever fit.

Promise what clients really rely on, and no more.

The simpler alternative, and the cost

Take a type with one implementation and no plans for more. For it, a written contract and a contract-test suite are extra work with little gain. Clear names and ordinary tests are enough. Contract tests pay off from the second implementation onward. They pay off most for public interfaces that other people implement.

Their cost is real:

  • There is an abstract test class to look after.
  • The written contracts must stay in step with the code.
  • Someone must decide carefully what is promised.

Relatives and look-alikes

  • OCP (Lesson 06) lets new classes plug in without editing closed code. LSP is what makes that safe. A plug-in that breaks the contract breaks the closed code that trusts it.
  • The fragile base class problem (Lesson 03) is the danger from the parent's side (parent changes, child breaks). LSP is the danger from the child's side (child misbehaves, the parent's clients break).
  • Interface Segregation (Lesson 08) is the usual cure for refused bequests: a contract small enough that every implementer can keep all of it.
  • Design by Contract is Bertrand Meyer's name for writing pre- and postconditions into code. It is the toolset. LSP is the rule for using it with subtypes.

8Key takeaways

  • The Liskov Substitution Principle says code that works with a type must keep working with any subtype or implementation, without noticing the difference. So a substitute must keep every promise its parent makes.
  • Promises come in three kinds. Preconditions are what callers must make true. Postconditions are what the method guarantees. Invariants are what is always true. A substitute may ask for less and give more. It must never ask for more or give less.
  • "Is-a" in code means "behaves as." That is why a changeable Square is not a changeable Rectangle: its setters break the postcondition "the other side is unchanged."
  • Watch for three signs of a violation: instanceof checks in client code, refused bequests that throw or do nothing, and overrides that surprise their callers.
  • There are three cures. Don't inherit what you cannot honour (make siblings under a smaller contract). Make objects immutable. Or split the contract. Protect every contract with one contract test that every implementation must pass.

  3. Redesign it so the mistake cannot even be written.
class Bird {
    public String fly() { return "flap flap"; }
}
class Penguin extends Bird {
    @Override
    public String fly() { throw new UnsupportedOperationException("Penguins can't fly"); }
}
static void migrate(List<Bird> flock) {
    for (Bird bird : flock) { System.out.println(bird.fly()); }
}
Click to reveal the answer

(a) A refused bequest. Penguin inherits fly() and refuses it by throwing where Bird promised success. That is a weakened postcondition (and an exception the parent's contract never allowed).

(b) The first bird flies. The penguin throws, and nothing catches it, so the program stops:

Prediction

flap flap
Exception in thread "main" java.lang.UnsupportedOperationException: Penguins can't fly
    at Penguin.fly(...)
    at ...migrate(...)

(c) "Can fly" is not something every bird promises. So it must not be in Bird's contract. Give flying its own, smaller contract, and let only real flyers sign it:

// What EVERY bird can honestly promise.
abstract class Bird { abstract String name(); }
// A separate, smaller contract for the birds that really fly.
interface Flyer { String fly(); }

class Sparrow extends Bird implements Flyer {
    String name() { return "Sparrow"; }
    public String fly() { return "flap flap"; }
}
class Penguin extends Bird {        // no fly() to refuse
    String name() { return "Penguin"; }
}

// migrate now asks for exactly what it uses: flyers.
static void migrate(List<Flyer> flock) {
    for (Flyer flyer : flock) { System.out.println(flyer.fly()); }
}

Now migrate(List.of(new Sparrow(), new Penguin())) does not compile, because a Penguin is not a Flyer. The bug moved from a crash at run time to a red line in your editor. That is the best place for it. migrate(List.of(new Sparrow())) prints:

Prediction

flap flap

Notice the cure. One big promise is split into smaller ones. Each one is signed only by those who can keep it. That is the next lesson's principle. It is also how the hub's smoke alarm will finally get its place.

10Catalog update

Entry 3 added: Liskov Substitution Principle, in the pattern catalog. In brief:

  • Intent: every subtype or implementation must keep every promise of the type it stands in for.
  • Pain: honest client code broken by a substitute that claims a type but breaks its promises.
  • Use when: designing any hierarchy or interface with more than one implementation; reviewing overrides.
  • Do NOT use when: demanding identical behaviour; over-specifying contracts; formal contract suites for a single implementation.
  • Cost: written contracts and contract tests to maintain; sometimes giving up an "obvious" inheritance.
  • Seen in the wild: List.add's documented "optional operation"; Stack extends Vector.
  • Where: kata com.katas.lsp; hub Device's written contract + DeviceContractTest.

11Key words

Subtype
Any type that can stand in for another: a subclass, or a class that implements an interface.
Substitute
A subtype used in place of its parent type.
Liskov Substitution Principle (LSP)
Code that works with a type must keep working with any subtype, without noticing the difference.
Precondition
What must be true before a method may be called. The caller's job.
Postcondition
What a method guarantees is true after it returns. The method's job.
Side effect
Any change a method makes besides returning its answer, like changing a field or printing.
Substitution rule
A substitute may ask for less and give more; never ask for more or give less.
instanceof
Java's check "is this object of that class (or a subclass)?" In client code it often signals an LSP problem.
Refused bequest
A subclass that inherits a method it cannot keep, and throws or does nothing instead.
Surprising override
An override that does something its parent's contract rules out.
Siblings
Two classes that share the same parent type, without one extending the other.
Immutable
An object whose state can never change after it is created; "changing" it returns a new object.
Contract test
One set of tests, written against a contract, that every implementation must pass.
Trade-off
Giving up one good thing to get another.
Design by Contract
Bertrand Meyer's practice of writing pre- and postconditions as part of the code.
||
Java's "or": true if either condition is true.

12Quick recap

  • LSP: a substitute must keep every promise of the type it stands in for.
  • "Is-a" in code means "behaves as"; a changeable Square does not behave as a changeable Rectangle.
  • A substitute may ask for less and give more, never ask for more or give less.
  • Warning signs: instanceof checks, refused bequests, surprising overrides.
  • Cures: siblings under a smaller contract, immutable objects, split contracts, and contract tests.
