SOLID Together

One rotten module that breaks all five principles, refactored one principle at a time. How they reinforce each other, and where they honestly pull against each other.

Kata package: com.katas.solid + com.katas.solid.channels (the rotten module in com.katas.solid.naive).

Prerequisites: Lessons 05, 06, 07, 08, 09.

1The pain

Real rot never comes one principle at a time. Here is a security module after a year of "quick fixes," and it breaks all five at once.

public class SecurityModule {
    private final List<HomeDevice> devices;            // a FAT interface: locks must "detect smoke"
    private final String channel;                     // "email" or "sms", as a magic string
    private final List<String> history = new ArrayList<>();

    public void checkHouse(boolean nightTime) {
        for (HomeDevice device : devices) {
            if (device.type().equals("lock") && !device.isLocked()) send(device.name() + " is UNLOCKED", nightTime);
            else if (device.type().equals("smoke") && device.smokeDetected()) send("SMOKE at " + device.name(), nightTime);
        }
    }
    private void send(String problem, boolean nightTime) {
        String message = (nightTime ? "[NIGHT] " : "") + "ALERT: " + problem;   // wording
        history.add(message);                                                  // remembering
        if (channel.equals("email")) System.out.println("EMAIL to owner@example.com: " + message);
        else if (channel.equals("sms")) System.out.println("SMS to 555-0100: " + message);
        else throw new IllegalArgumentException("Unknown channel: " + channel);
    }
}

// "Don't wake the owner at night" was added by inheritance:
public class QuietSecurityModule extends SecurityModule {
    @Override public void checkHouse(boolean nightTime) {
        if (nightTime) throw new UnsupportedOperationException("Quiet hours: checks are switched off at night");
        super.checkHouse(false);
    }
}

By day it seems to work. At night, the "quiet" version refuses to check at all, so smoke at 3 am goes unreported. A typo like "emial" compiles fine and fails only when the first alert fires. Adding a water-leak sensor means editing the ladder, the fat interface, and every device that must now fake "leak detected."

Predicted symptoms

EMAIL to owner@example.com: ALERT: SMOKE at Kitchen

The pain is not one smell but a tangle of them, each feeding the others. Untangling it needs all five principles, in a sensible order.

2Real-world analogy

Renovating an old house. Over the years one room became kitchen, office and laundry at once. Appliances were hard-wired into the walls, every new gadget meant cutting new holes, and a "replacement" boiler was installed that shuts itself off at night, heating included. A good renovation has an order, with each trade fixing one kind of problem so the next trade can work.

Renovation stepPrincipleIn the module
Give each room one useSSplit wording, delivery and detection apart
Fit standard sockets so new appliances just plug inOReplace the type and channel ladders with interfaces
Only install replacements that work like the originalsLRemove the refusing "quiet" subclass
Separate switches per circuit, not one panel for everythingIReplace the fat device contract with one small role
The house defines the socket standard; appliances meet itDThe policy owns AlertChannel; channels plug in at the composition root

3The refactoring, step by step

A refactoring of this size is safest as small steps, each keeping the behaviour the same (except where a step deliberately fixes a bug). The order below works well because each step makes the next easier. It is not the only possible order.

Step 1 · S: one reason to change per class

Spotted: SecurityModule answers to four actors: whoever decides what counts as a problem, whoever writes what the owner reads, whoever runs the delivery channels, and whoever wants a history. Move: the wording becomes AlertFormatter. Delivery will become its own classes in step 2. Deciding stays in the check. The history goes away: the check now returns the alerts it sent, and the hub already has an activity log for keeping history. Splitting first gives the later steps small, single-purpose pieces to work on.

Step 2 · O: stop editing the check for every new kind

Spotted: two ladders on magic strings, one on type() and one on channel. Move: each watched thing answers "do you need attention, and what's your problem?" for itself, and each channel is a class keeping one send contract. A water-leak sensor is now a new class, with no edit to the check. The typo problem disappears too: there is no string left to misspell, and a wrong class name won't compile.

Step 3 · L: no substitute may refuse the job

Spotted: QuietSecurityModule overrides checkHouse to throw at night, a refused bequest. Worse, it hides smoke. Move: delete the subclass. "Quiet hours" is a setting (quietAtNight) that holds back only non-urgent problems. Each watched thing says whether it is urgent, and smoke always is. Nothing is left that could be substituted badly, and the night-time smoke bug is fixed. This is the one step that deliberately changes behaviour, because the old behaviour was a bug.

Step 4 · I: depend only on what you use

Spotted: HomeDevice forces locks to "detect smoke" and alarms to "be locked," and both to refuse turnOn. The check uses none of that. Move: one small role interface, Monitored (name, needsAttention, isUrgent, problem), signed by both. Nothing is faked and nothing is refused.

Step 5 · D: the policy owns its abstractions

Spotted: delivery is hard-coded inside the policy (System.out, addresses, numbers). Move: the policy declares AlertChannel in its own package. EmailAlerts and SmsAlerts live in channels and implement it. Everything is injected through the constructor at the composition root, and tests inject a recorder.

This is a MODEL of the refactoring's progress, a checklist rather than running code. The real authority is the kata: the rotten module in naive/, the finished one in com.katas.solid, and mvn test from katas/.

How the principles reinforce each other

  • S makes I easy: once a class has one job, the interface its clients need is naturally small.
  • I makes L easy: a small contract leaves nothing to refuse, so no refused bequests.
  • L makes O safe: new classes can plug in without editing closed code only if they keep the contract.
  • D makes O reach across layers: because the policy owns the abstraction, new details plug in from outside the policy's package.
  • O and D together make testing easy: a recording channel is just one more implementation.

…and where they honestly pull against each other

TensionWhat happensHow to decide
S vs simplicitySplitting by actor multiplies classes; one security class became eight filesSplit along real actors, not imagined ones
O vs "you aren't gonna need it"Every variation point is a bet on future variantsWait for the second real variant (Lesson 06)
I vs discoverabilityMany tiny interfaces make it hard to see what a thing isGroup methods that clients always use together
D vs readability"Which channel runs here?" is answered only in the composition rootKeep the composition root small and in one obvious place
L vs reuse by inheritanceSome convenient extends must be given upPrefer a setting or a wrapper (composition) over a refusing subclass

The principles are tools for one goal, loose coupling and high cohesion so that change stays local, not a checklist to max out. When two of them disagree, ask which choice keeps the changes you actually expect local, at the lowest cost.

Why is step 3 (L) the only step allowed to change what the module does?

Because the old behaviour was a bug: the quiet subclass silenced smoke at night. Every other step is a pure refactoring, so the same inputs give the same alerts. Keeping those two kinds of change separate (and saying so) is what lets tests act as a safety net: a test that changes during a "pure" step reveals a mistake.

4The kata

Package com.katas.solid. Saved: Monitored.java is the small role from step 4. Saved: DoorLock.java, SmokeAlarm.java sign it (a lock is not urgent, smoke always is). Saved: AlertChannel.java is policy-owned (step 5), implemented by channels/EmailAlerts.java and channels/SmsAlerts.java. Saved: AlertFormatter.java holds the wording from step 1: (nightTime ? "[NIGHT] " : "") + "ALERT: " + problem.

Saved: katas/src/main/java/com/katas/solid/SecurityCheck.java

// The refactored policy: all five principles applied.
package com.katas.solid;

// The JDK's growable list.
import java.util.ArrayList;
// The JDK's list interface.
import java.util.List;

// ONE job (SRP): decide which problems to report, and report them. It asks
// each watched thing about itself (OCP: no ladder), needs only the small
// Monitored role (ISP), depends only on abstractions injected through the
// constructor (DIP), and "quiet hours" is a SETTING rather than a subclass
// that refuses work (LSP: there is nothing left to substitute badly).
public class SecurityCheck {

    // What to watch, through the small role interface.
    private final List<Monitored> watched;

    // Where alerts go: any channel keeping the contract.
    private final AlertChannel channel;

    // How alerts are worded.
    private final AlertFormatter formatter;

    // If true, non-urgent problems are held back at night (smoke never is).
    private final boolean quietAtNight;

    // CONSTRUCTOR INJECTION: everything arrives from the composition root.
    public SecurityCheck(List<Monitored> watched, AlertChannel channel, AlertFormatter formatter,
                         boolean quietAtNight) {
        // An unmodifiable copy of the watched things.
        this.watched = List.copyOf(watched);
        // Remember the channel.
        this.channel = channel;
        // Remember the formatter.
        this.formatter = formatter;
        // Remember the setting.
        this.quietAtNight = quietAtNight;
    }

    // Check everything once. Returns the alerts actually sent, so callers (and
    // tests) can see what happened without a history inside this class.
    public List<String> run(boolean nightTime) {
        // The alerts sent during this run.
        List<String> sent = new ArrayList<>();
        // Ask every watched thing about itself.
        for (Monitored item : watched) {
            // Nothing wrong: move on.
            if (!item.needsAttention()) {
                // Next item.
                continue;
            }
            // Quiet hours hold back the non-urgent problems only.
            if (nightTime && quietAtNight && !item.isUrgent()) {
                // Next item.
                continue;
            }
            // Word it...
            String message = formatter.format(item.problem(), nightTime);
            // ...deliver it...
            channel.send(message);
            // ...and report it back to the caller.
            sent.add(message);
        }
        // An unmodifiable copy for the caller.
        return List.copyOf(sent);
    }
}

(continue ends the current pass of a loop early and moves straight on to the next item.)

5Applied to the Smart Home Hub

The rotten module lives frozen in the kata, on purpose. We would never knowingly commit a rotten module into the hub just to clean it up again. The hub instead gets two things: an audit against all five principles, and a new security feature built SOLID from its first line.

The audit

PrincipleWhere the hub honours it
SHomeSetup (which devices), Hub (operating), HouseReport (display), ClimateControl (comfort), each answering to one actor
ONew house modes are new Routine classes; new sensors are new TemperatureSensor classes; neither needs an edit to Hub or ClimateControl
LContract tests check every Device, Switchable and Lockable implementation, including the logging wrapper
IDevice / Switchable / Lockable / Dimmable: the smoke alarm is never asked to switch
DThe core packages import only contracts; the composition root (Main + HomeSetup) is the only code naming concrete classes

The new feature: a lock check

The requirement: when someone leaves the house, warn them about any unlocked door. Built the SOLID way from the start, it mirrors the kata's final shape:

  • security/AlertChannel.java: the policy's own delivery abstraction (D).
  • security/LockCheck.java: one job (S). It asks each Lockable about itself (O), every Lockable is contract-tested (L), it needs only the small Lockable role (I), and everything is injected (D).
  • alerts/ConsoleAlerts.java: the first delivery detail (prints), in its own package, implementing the policy's interface.
  • home/Hub.java gains a third typed group, lockables(), and the constructor becomes Hub(switchables, lockables, otherDevices). HomeSetup.createLockables() hands over the front door as a Lockable. This is the "when locks need operating" moment that Lesson 08 deferred.

Saved: smarthome/src/main/java/com/smarthome/security/LockCheck.java

// The security POLICY: rules about keeping the house secure.
package com.smarthome.security;

// The only device capability this policy needs.
import com.smarthome.devices.Lockable;

// The JDK's growable list.
import java.util.ArrayList;
// The JDK's list interface.
import java.util.List;

// Warns about every unlocked lock. Built SOLID from its first line:
// one job (SRP); asks each lock about itself, so new kinds of lock need no
// edit here (OCP); every Lockable keeps its contract, checked by
// LockableContractTest (LSP); needs only the small Lockable role (ISP);
// depends only on abstractions injected through the constructor (DIP).
public class LockCheck {

    // What to inspect: any lockable devices.
    private final List<Lockable> locks;

    // Where warnings go: any channel keeping the contract.
    private final AlertChannel channel;

    // CONSTRUCTOR INJECTION from the composition root.
    public LockCheck(List<Lockable> locks, AlertChannel channel) {
        // An unmodifiable copy of the locks.
        this.locks = List.copyOf(locks);
        // Remember the channel.
        this.channel = channel;
    }

    // Inspect every lock once; returns the alerts actually sent.
    public List<String> run() {
        // The alerts sent during this run.
        List<String> sent = new ArrayList<>();
        // Ask each lock about itself.
        for (Lockable lock : locks) {
            // Only unlocked ones are a problem.
            if (!lock.isLocked()) {
                // Word the alert.
                String message = "ALERT: " + lock.getName() + " is UNLOCKED";
                // Deliver it through whatever channel was injected.
                channel.send(message);
                // Report it back to the caller.
                sent.add(message);
            }
        }
        // An unmodifiable copy for the caller.
        return List.copyOf(sent);
    }
}

6In the wild

JUnit 5's own extension model shows several principles at once. To hook into a test's life cycle you implement small, separate interfaces such as BeforeEachCallback, AfterEachCallback or ParameterResolver (ISP: sign only the roles you need). You register an extension rather than editing JUnit (OCP). JUnit's engine depends on those interfaces, never on your classes (DIP). And every extension must keep its interface's contract, or other tests break (LSP). The tool running this course's tests is built the way this chapter teaches. (The exact interface names are worth checking in the JUnit 5 user guide, "Extension Model.")

In real teams, a refactoring like this one rarely happens in one heroic sitting. It happens in small, separately reviewed commits, each keeping the tests green, usually right before adding a feature that the rot would otherwise make painful. "Make the change easy, then make the easy change" is how experienced engineers put it.

7When NOT to, and tensions

When not to refactor towards SOLID

The rotten module deserved this treatment because it had already grown four jobs, two ladders, a fake-filled interface and a dangerous subclass, and more requirements were coming. A 30-line script that sends one email when a disk is full does not. Applying all five principles to it would turn one file into eight for no gain. SOLID is a set of answers to change pain. With no pain and no expected change, the simplest code that works is the right design. The signals that justify a refactoring like this: the class keeps getting edited for unrelated reasons, bugs come back, tests are hard to write, and the next feature looks scary.

The cost, all five at once

Count it honestly. The rotten module was 4 classes plus a fat interface. The refactored one is 6 types, 2 channel classes and 2 test fakes, and a reader must follow arrows across files and a composition root to see the whole picture. That price buys safe night-time alerts, easy new sensors and channels, and real tests. Pay it where those things matter, and not elsewhere.

Relatives and look-alikes

  • Every pattern ahead is a packaged combination of these moves. For example, "keeping the contract while adding behaviour by wrapping" (Lesson 19) is O + L + composition, and "choosing an algorithm at run time" (Lesson 25) is O + D.
  • The companion principles (Lesson 11), meaning DRY, KISS, YAGNI and the Law of Demeter, are the counterweights that stop SOLID from turning into over-design.

8Key takeaways

  • Real rot is a tangle in which several principles are broken at once, and a sensible order (S, O, L, I, D) lets each step make the next one easier.
  • A large refactoring is safest as small steps that keep behaviour identical, with any deliberate bug fix (like the night-time smoke) made as its own clearly named step.
  • The principles reinforce each other: single responsibilities lead to small interfaces, small interfaces leave nothing to refuse, honest substitutes make open/closed code safe, and inverted dependencies let new details plug in from outside.
  • They also pull against each other, against simplicity, readability and discoverability, so decide by asking which option keeps the changes you actually expect local at the lowest cost.
  • SOLID answers change pain. Apply it where the pain and the expected changes are real, and leave small, stable code simple.

9Challenge

Diagnose this module principle by principle, propose the order of your refactoring steps, and sketch the result. Then predict what your design prints for a CSV export of the rows ["a", "b"].

public interface Document { List<String> rows(); void save(); void print(); void email(String to); }

public class Exporter {
    public void export(Document doc, String format) {
        String text;
        if (format.equals("csv")) text = String.join(",", doc.rows());
        else if (format.equals("lines")) text = String.join("\n", doc.rows());
        else throw new IllegalArgumentException(format);
        new DiskWriter().write("export.txt", text);
        System.out.println("Exported " + doc.rows().size() + " rows as " + format);
    }
}
public class ReadOnlyDocument implements Document {
    /* rows() works; save(), print() and email() all throw UnsupportedOperationException */
}

(String.join(",", list) glues a list's items together with the given separator: ["a", "b"] becomes "a,b".)

PrincipleViolationFix

Order: S (pull out formatting and writing), then O (format classes), then I (narrow to HasRows, after which L stops mattering because ReadOnlyDocument just signs HasRows), then D (inject the sink and format).

public interface HasRows { List<String> rows(); }
public interface ExportFormat { String name(); String render(List<String> rows); }
public interface ExportSink { void write(String text); }

public class CsvFormat implements ExportFormat {
    public String name() { return "csv"; }
    public String render(List<String> rows) { return String.join(",", rows); }
}

public class Exporter {
    private final ExportSink sink;
    public Exporter(ExportSink sink) { this.sink = sink; }
    // Returns its summary instead of printing it (S: the caller decides where it goes).
    public String export(HasRows doc, ExportFormat format) {
        sink.write(format.render(doc.rows()));
        return "Exported " + doc.rows().size() + " rows as " + format.name();
    }
}
