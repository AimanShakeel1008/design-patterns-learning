Phase 1 · Chapter 02 · Lesson 11

The Companion Principles

DRY, KISS, YAGNI and the Law of Demeter: four short rules. They catch the rot SOLID misses, and they stop SOLID from turning into over-design. Plus "favor composition over inheritance," now seen through SOLID.

Kata packages: com.katas.dry, com.katas.kiss, com.katas.yagni, com.katas.demeter (each with its wrong way in naive/). Composition keeps its Lesson 03 kata, com.katas.composition.
Smart Home Hub: modified home/Hub.java (new unlock(name), one shared by-name lookup), Main.java (no more reaching into the hub's list), home/HubTest.java (+2 tests).
Prerequisites: Lessons 03, 04, 05, 06, 10.

  • Four short rules that travel with SOLID: DRY, KISS, YAGNI and the Law of Demeter.
  • What kind of rot each one catches, and how each one goes wrong when pushed too far.
  • Why SOLID explains the old advice "favor composition over inheritance."

1The pain

SOLID gives five ways to keep change local. But some rot slips past all five. And an eager beginner who uses SOLID everywhere can create a new kind of rot. Here are four small programs. Each one works today, and each one is about to hurt.

Pain 1 · one rule, typed twice

A shop shows a banner: "Add 5 EUR for free delivery." It also charges a delivery fee at checkout. Both classes contain the rule "free delivery from 50 EUR." Then the shop raises the limit to 60. Someone updates Checkout, and nobody remembers the banner.

// CartBanner: copy 1 of the rule, still the old number
if (totalEuros >= 50) { return "Free delivery!"; }
return "Add " + (50 - totalEuros) + " EUR for free delivery";

// Checkout: copy 2 of the rule, updated
return totalEuros >= 60 ? 0 : 5;

Predicted symptom (a 55 EUR basket)

Naive banner:   Free delivery!
Naive checkout: fee 5 EUR          <- promised free, then charged

The smell is needless repetition, one of the design smells from Lesson 04. Its symptom is shotgun surgery. One change of policy needs edits in many places, and nothing tells you when you have missed one.

Pain 2 · machinery bigger than the job

Someone wrote a "flexible greeting engine" to say good morning, afternoon or evening. It has four parts:

  • a rule interface;
  • one class for each part of the day;
  • a list of registered rules (rules added to the list when the engine starts);
  • a loop that asks each rule in turn.

Then a new request arrives: say "Good night" from 22:00. The engine is "extensible" (easy to add to), so someone adds a NightRule through addRule.

// registered on creation, in this order:
rules.add(new MorningRule());     // hour < 12
rules.add(new AfternoonRule());   // 12 to 17
rules.add(new EveningRule());     // hour >= 18   <- already claims 22 and 23

engine.addRule(new GreetingEngine.NightRule());   // hour >= 22, added at the END

Predicted symptom

Engine at 23: Good evening          <- the new rule is never reached

The order that decides the answer is not written anywhere you can see. It is hidden in the order the rules were added, spread over five classes. The smell is needless complexity: more parts than the problem needs, and the extra parts hide the bug.

Pain 3 · features for a future nobody ordered

A shopping-list printer was built "to be ready for anything." It has three options (programmers call them knobs): an HTML format (the language of web pages), numbering, and columns. The app only ever calls it one way.

public ListPrinter(String format, boolean numbered, int columns) { ... }

if (columns != 1) {
    throw new UnsupportedOperationException("Columns not implemented yet");
}

// the ONLY call in the whole app:
new ListPrinter("plain", false, 1).print(items);

Predicted symptom

Naive printer refused: Columns not implemented yet    <- compiles fine, fails when tried

Then the real second request arrived: "let me tick off what I have bought." Look at what the guesses cost:

  • None of the three knobs helps with the real request.
  • Every caller still has to choose all three.
  • The HTML branch has never been tested.
  • The columns knob is a trap, waiting for someone to try it.

This is speculative generality, met in Lesson 06.

Pain 4 · reaching through a stranger

A paperboy (a boy who delivers newspapers) collects 2 EUR a week. His code reaches through the customer into the customer's wallet. It counts the money, and takes it itself. Later, the customer starts keeping spare coins in a jar by the door. That change is made only inside Customer.

if (customer.getWallet().getCash() >= price) {   // two objects deep
    customer.getWallet().take(price);         // and again, taking the money himself
    return price;
}
return 0;                                    // never heard about the jar

Predicted symptom (1 EUR in the wallet, 10 EUR in the jar)

Naive paperboy collected: 0 EUR      <- the customer could pay; the paperboy didn't ask

The paperboy depends on the inside structure of another object. When that structure changed, the paperboy's code broke without being edited. So would every other class that reaches in the same way (the milkman, the window cleaner). Martin Fowler, a well-known writer on code smells, calls this a message chain: a chain of calls that reaches from one object into the next.

There is a fifth pain, an old one. In Lesson 03, a subclass broke when its parent changed. We return to it at the end of Section 3. Now SOLID can explain why the cure works.

3The principles explained

These are called the companion principles: short, practical rules that travel alongside SOLID (a "companion" is someone who goes along with you). Here is how they fit with SOLID:

  • SOLID tells you how to add structure, so change stays local.
  • DRY and the Law of Demeter catch rot that SOLID misses.
  • KISS and YAGNI tell you when to stop adding structure.

Each one is explained in four steps below: what it says, why it exists, a tiny example, and its name.

DRY: every piece of knowledge has one home

What it says. Your program knows many facts: rules, numbers with meaning, formats. Each fact should be written down in exactly one place. Everything else that needs the fact asks that place.

Why it exists. When a fact lives in two places, every change to it must be made twice. The day someone makes it once, the program contradicts itself, as the 55 EUR basket did.

Tiny example. Instead of totalEuros >= 60 typed in two classes, one object holds the rule and both classes ask it:

DeliveryPolicy policy = new DeliveryPolicy(60, 5);   // the ONLY place 60 and 5 appear
banner.message(55);     // asks policy.isFree(55)
checkout.deliveryFee(55); // asks policy.feeFor(55)

The name. This is DRY, "Don't Repeat Yourself." It comes from Andy Hunt and Dave Thomas's book The Pragmatic Programmer (1999). Their exact words: "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system." In plain words: one clear, official home for each fact. The one place that holds a fact is often called its single source of truth.

DRY is about knowledge, not text. This is the most common mix-up about DRY.

  • Two lines can look different and still repeat one fact. total >= 60 in one class and total < 60 in another are the same rule.
  • Two lines can look identical and still be different facts. That is accidental duplication from Lesson 05, and merging it is a mistake.

So the test is not "do these look alike?" It is "if one changes, must the other change too?"

KISS: the simplest design that fully does the job

What it says. Many designs may fully solve the problem. Choose the one with the fewest parts, and the fewest ideas a reader must keep in their head. Every extra part must earn its place.

Why it exists. Every part is something to read, test and get wrong. Extra machinery also hides things. The engine's deciding order was hidden in the order its rules were added. So the first person to add to it got it wrong.

Tiny example. The whole greeting rule, in deciding order, read from top to bottom:

if (hour < 12) { return "Good morning"; }
if (hour < 18) { return "Good afternoon"; }
if (hour < 22) { return "Good evening"; }
return "Good night";

The name. This is KISS, "Keep It Simple, Stupid." It is a saying usually credited to Kelly Johnson, an engineer who designed aeroplanes. Many people soften it to "Keep It Short and Simple."

Simple is not the same as short. It is not the same as clever either. return h < 12 ? "Good morning" : h < 18 ? "Good afternoon" : … is shorter. But a reader has to untangle it before trusting it.

Here is a useful test for "simple": can a newcomer predict the output by reading the code once, top to bottom? The four ifs pass. The engine fails, because you must know the order the rules were added to answer.

YAGNI: don't build it until it is really needed

What it says. Don't add a feature, option or extension point because you think it might be needed one day. Add it on the day a real need arrives.

Why it exists. A guessed feature costs you now:

  • It must be written, tested and read.
  • Callers must deal with it. Every caller of ListPrinter picks three knobs.
  • It rots while nobody uses it.
  • And the guess is often wrong. The real request ("tick items off") was not one of the three guesses.

When the real need comes, you build it with real information. That beats a year-old guess.

Tiny example. new ShoppingList().print(items) does exactly what the app uses: a dash per item, and nothing else.

The name. This is YAGNI, "You Aren't Gonna Need It." ("Gonna" is casual English for "going to.") It comes from Extreme Programming (XP). XP is a way of building software in very small steps, with constant testing and feedback. Kent Beck and Ron Jeffries made it popular in the late 1990s. You already met YAGNI's idea as take the first bullet in Lesson 06: don't build a variation point until the second real variant arrives.

An honest limit. YAGNI is about features, never about quality. Tests, clear names, error handling and code that is easy to change are needed today, not "later." YAGNI works because the code stays easy to change. That is what lets you add the feature cheaply when the real need arrives.

DRY says "one home for each rule." YAGNI says "don't build what isn't needed." Does DeliveryPolicy break YAGNI?

No. It was built for a need that is already here: two screens use one rule, and there was a real bug when they drifted apart. YAGNI warns against parts built for imagined needs.

Notice also what DeliveryPolicy does not have: no interface, no different policy per country, and no settings file. Those would break YAGNI until someone asks for them.

The Law of Demeter: talk only to your friends

What it says. A method should call methods only on objects it knows directly. These are its friends. It should never call methods on objects it got from a friend. Those are strangers. To be exact, a method m of object O may call methods on:

  1. O itself (this);
  2. m's own parameters;
  3. objects that m creates with new;
  4. O's own fields.

An object that one of those friends returns to you is a stranger. Don't call methods on it.

Why it exists. Each step into a stranger couples you to how your friend is built inside. Here is the paperboy's story again:

  1. The paperboy's friend was the customer (a parameter).
  2. But his code called methods on the customer's wallet, which is a stranger.
  3. When the customer's insides changed (the jar), the paperboy broke.

With the rule followed, a change inside Customer stays inside Customer.

Tiny example. customer.getWallet().take(2) breaks the rule, because take is called on what getWallet() returned. customer.pay(2) follows it, because pay is called on a parameter.

The name. This is the Law of Demeter. It is named after the Demeter research project at Northeastern University (in the USA), where Ian Holland proposed it in 1987. It is also called the principle of least knowledge. A chain of calls like a.getB().getC().doD() looks like a line of railway carriages, joined dot by dot. One crash spreads down the whole line, so it is nicknamed a train wreck.

The usual cure has its own name. Don't ask an object for its insides and do the work yourself. Instead, tell it what you want, and let it do the work. This is called Tell, Don't Ask. customer.pay(2) tells. customer.getWallet().getCash() asks. It is encapsulation seen from the caller's side: the customer's money is the customer's business.

It is not a dot-counting rule. Many people think "more than one dot in a line breaks the law." It does not. The law is about reaching into the structure of other objects, not about how many dots a line has. Two common cases are fine, as the list below shows.

  • Calls that hand back the object you are already talking to. text.append("a").append("b") in the hub's HouseReport has many dots. But each append returns the same StringBuilder. It is still your friend, so you never meet a stranger.
  • Stable value types. Strictly speaking, device.getName().equals(name) calls a method on a returned String. But String is a stable JDK value. It will never grow a coin jar. This is the same judgement Lesson 09 made about depending on stable things.
In Paperboy.collect(Customer customer, int price), which of these may it call under the Law of Demeter: customer.pay(price), this.toString(), customer.getWallet().take(price), new Receipt(price).print()?
  • customer.pay(price): yes, a parameter.
  • this.toString(): yes, the object itself.
  • new Receipt(price).print(): yes, an object the method created.
  • customer.getWallet().take(price): no. take is called on what a friend returned, which is a stranger.

Composition over inheritance, revisited as a principle

In Lesson 03 you met the Gang of Four's advice, favor composition over inheritance, through a bug. A counting playlist extended Playlist. It double-counted when its parent's insides changed (the fragile base class problem). Another counting playlist held a playlist (composition) and passed calls on to it (delegation). It was safe. Now SOLID explains why the cure works so well:

PrincipleWhat inheritance doesWhat composition does
L (Lesson 07)Promises that every subclass can stand in for its parent, including every inherited method. Easy to break by accident.A wrapper signs only the interface it chooses. So it promises only what it can keep.
O (Lesson 06)To add a feature to many classes you need a subclass of each one (class explosion).One wrapper adds a feature to any implementation, with no edits (the hub's LoggedDevice).
D (Lesson 09)The parent is fixed when the code is compiled, and you cannot inject a different one.The held object is any implementation, chosen at the composition root.
S (Lesson 05)Parent and child share one object, so their jobs blur together.Each part is its own object with one job.
Demeter (this lesson)The child depends on the parent's insides (self-use), which is reaching into a structure.The wrapper uses only the held object's public contract (black-box reuse).

"Favor" still does not mean "always." Inheritance is the right tool for a true is-a relationship with a small parent that rarely changes, which you own and designed to be extended. The hub's SwitchableDevice, shared by Light and Thermostat, is exactly that. It stays.

DRY · com.katas.dry

Saved: katas/src/main/java/com/katas/dry/DeliveryPolicy.java

// The DRY way (Lesson 11): the rule gets one home.
package com.katas.dry;

// The ONE place that knows the free-delivery rule: the threshold and the fee
// are written here and nowhere else (DRY: every piece of knowledge has a single
// home). Changing the shop's policy is now one edit, and every screen that
// asks this object follows automatically.
public class DeliveryPolicy {

    // From this basket value (in EUR) delivery is free.
    private final int freeFromEuros;

    // The fee (in EUR) charged below that value.
    private final int feeEuros;

    // The shop chooses the numbers once, when the policy is built.
    public DeliveryPolicy(int freeFromEuros, int feeEuros) {
        // Remember the threshold.
        this.freeFromEuros = freeFromEuros;
        // Remember the fee.
        this.feeEuros = feeEuros;
    }

    // Is delivery free for a basket worth totalEuros? The comparison is written once.
    public boolean isFree(int totalEuros) {
        // The single copy of the rule.
        return totalEuros >= freeFromEuros;
    }

    // How many EUR the shopper must still add for free delivery (0 if already free).
    public int missing(int totalEuros) {
        // Reuse isFree rather than repeating the comparison.
        return isFree(totalEuros) ? 0 : freeFromEuros - totalEuros;
    }

    // The delivery fee to charge for a basket worth totalEuros.
    public int feeFor(int totalEuros) {
        // Reuse isFree again: one rule, asked three ways.
        return isFree(totalEuros) ? 0 : feeEuros;
    }
}
  • Saved: CartBanner.java and Checkout.java each take the policy in their constructor. The banner keeps only the wording: "Free delivery!" or "Add " + policy.missing(total) + " EUR for free delivery". The checkout returns policy.feeFor(total). Neither class contains a number.
  • Saved: Main.java runs the naive pair first. Then it builds new DeliveryPolicy(60, 5) once, and hands the same object to both screens.
  1. Naive: the banner compares 55 with its own 50 and celebrates. The checkout compares 55 with its own 60 and charges 5.
  2. DRY, 55 EUR: banner.message(55) calls policy.isFree(55). That is false, because 55 is less than 60. It then calls policy.missing(55). That calls isFree again and returns 60 − 55 = 5. checkout.deliveryFee(55) calls policy.feeFor(55), which returns the fee, 5.
  3. DRY, 60 EUR: isFree(60) is true, so the banner says "Free delivery!" and feeFor returns 0.

KISS · com.katas.kiss

// The KISS way (Lesson 11): the simplest code that does the whole job.
package com.katas.kiss;

// Chooses a greeting by the hour. The whole rule, in its deciding order, fits
// on one screen: four lines, read top to bottom. The "Good night" requirement
// was one new line, placed where its order is plain to see.
public class Greeter {

    // The greeting for an hour of the day (0-23).
    public String greet(int hour) {
        // Before noon.
        if (hour < 12) {
            // Morning.
            return "Good morning";
        }
        // Noon until 17:59.
        if (hour < 18) {
            // Afternoon.
            return "Good afternoon";
        }
        // 18:00 until 21:59.
        if (hour < 22) {
            // Evening.
            return "Good evening";
        }
        // Everything later: the requirement added in this lesson.
        return "Good night";
    }
}

The over-built version is naive/GreetingEngine.java. It holds a GreetingRule interface and four rule classes, all written inside it (nested), plus a list of rules, addRule, and a loop. That is about 140 lines, compared with about 30 here.

  1. Naive: the constructor registers Morning, Afternoon and Evening, and addRule appends Night as the fourth rule.
  2. engine.greet(9): MorningRule.appliesTo(9) is true, so the answer is "Good morning".
  3. engine.greet(23): Morning says no, and Afternoon says no. Then EveningRule.appliesTo(23) (23 ≥ 18) says yes. The loop returns "Good evening" and never reaches NightRule.
  4. Simple: greet(23) fails the first three tests and reaches return "Good night".

YAGNI · com.katas.yagni

Saved: katas/src/main/java/com/katas/yagni/ShoppingList.java

// The YAGNI way (Lesson 11): build what is needed today, and nothing more.
package com.katas.yagni;

// The JDK's list interface.
import java.util.List;

// Prints a shopping list the one way the app actually uses: a dash per item.
// No formats, no numbering, no columns. When a real new need arrives, it is
// added then, shaped by that real need instead of by a guess.
public class ShoppingList {

    // Turn the items into printable text, one dashed line each.
    public String print(List<String> items) {
        // StringBuilder: a growable piece of text.
        StringBuilder text = new StringBuilder();
        // Every item in order.
        for (String item : items) {
            // A dash, the item, and a line break.
            text.append("- ").append(item).append("\n");
        }
        // The finished text.
        return text.toString();
    }
}
  1. Naive, ("plain", false, 1): the columns check passes, and the HTML checks fail. Each item gets the marker "- ", because numbered is false.
  2. Naive, two columns: the constructor accepts it without complaint. print throws at its first line. Main catches the exception and prints the refusal.
  3. YAGNI: one loop with no choices to make, giving the same two lines.

Law of Demeter · com.katas.demeter

Saved: katas/src/main/java/com/katas/demeter/Customer.java

// The Law of Demeter way (Lesson 11): the customer pays; nobody reaches inside.
package com.katas.demeter;

// A newspaper customer that is ASKED to pay and decides for itself where the
// money comes from. Its wallet and coin jar are private and never handed out,
// so adding the jar changed this class only: no caller had to hear about it.
public class Customer {

    // The money the customer carries.
    private final Wallet wallet;

    // Spare money in a jar by the door.
    private final Wallet coinJar;

    // A customer with some cash in the wallet and some in the jar.
    public Customer(int walletCash, int jarCash) {
        // Build the wallet (this object's own field: a friend).
        this.wallet = new Wallet(walletCash);
        // Build the jar (also a friend).
        this.coinJar = new Wallet(jarCash);
    }

    // Pay an amount if possible. Returns true if paid, false if not.
    public boolean pay(int amount) {
        // First choice: the wallet.
        if (wallet.has(amount)) {
            // Take it from there.
            wallet.take(amount);
            // Paid.
            return true;
        }
        // Second choice: the jar by the door.
        if (coinJar.has(amount)) {
            // Take it from there.
            coinJar.take(amount);
            // Paid.
            return true;
        }
        // Neither holds enough: decline, and nothing is taken.
        return false;
    }

    // Total money left, as a plain number (for the demo and tests).
    public int moneyLeft() {
        // Add the two amounts.
        return wallet.cash() + coinJar.cash();
    }
}

Saved: katas/src/main/java/com/katas/demeter/Paperboy.java

// The Law of Demeter way (Lesson 11): the paperboy talks only to its friend.
package com.katas.demeter;

// Collects the weekly newspaper money by ASKING the customer to pay. It calls
// a method on its parameter (a friend) and never on anything the customer
// holds (a stranger), so it never needs to know about wallets or jars.
public class Paperboy {

    // Collect the price from a customer; returns the EUR actually collected.
    public int collect(Customer customer, int price) {
        // One call on a friend. How the customer pays is the customer's business.
        return customer.pay(price) ? price : 0;
    }
}

Saved: Wallet.java now guards its own rule. It has has(amount), and a take(amount) that throws an exception instead of going below zero (an invariant). cash() returns a plain number. The naive wallet's take did no check at all, because it trusted the paperboy to look first.

  1. Naive: customer.getWallet() returns the wallet object itself. .getCash() on it gives 1, which is less than 2, so the method returns 0. The jar is never looked at.
  2. Demeter: paperboy.collect(customer, 2) calls customer.pay(2). Inside, wallet.has(2) is false (1 < 2), and coinJar.has(2) is true. So coinJar.take(2) leaves 8 in the jar, and pay returns true. collect returns 2.
  3. moneyLeft() = 1 + 8 = 9.

5Applied to the Smart Home Hub

Reading the hub against the four companions turned up one real train wreck, in our own Main, written in Lesson 10:

hub.lockables().get(0).unlock();   // reach into the hub's list, by POSITION

Here is what that line does:

  1. Main asks the hub for its list of locks.
  2. It asks the list for item 0.
  3. It calls unlock on that stranger.

It works only because the front door happens to be the first lock. Add a back door before it in HomeSetup, and the wrong door opens, with no error at all. The cure is Tell, Don't Ask: tell the hub which lock to open, by name. That is the same way turnOff(name) already works for switchables.

That cure raised a DRY question straight away. The hub already had a loop in switchableNamed that says "find a device by its exact name, or fail loudly." A second, almost identical loop for locks would repeat the same knowledge. Say the lookup rule ever changes, for example to ignore upper and lower case. Then both copies must change together. So this is real duplication, not accidental duplication, and it gets one home.

A new Java tool: the generic method

What it is. A method with a type placeholder: a blank where a type name goes. Java fills in the blank fresh each time the method is called. Think of a form with "___" for a name: the same form works for anyone.

Why it exists. The two lookups are the same loop over two list types: List<Switchable> and List<Lockable>. Without a placeholder, you would have two bad choices:

  • write two copies of the loop; or
  • write one method that returns a plain Device, which every caller must convert back to the type it wanted.

Tiny example. One body of code does both jobs. findNamed(switchables, …) hands back a Switchable. findNamed(lockables, …) hands back a Lockable.

The name. This is a generic method. Three parts to know:

  • <T extends Device>, written before the return type, declares the placeholder. The placeholder T is called a type parameter.
  • The words extends Device are a bound (a limit): T may be any type that is a Device. That is why the body is allowed to call getName().
  • You have used generics since List<String> in Lesson 03. List itself is a generic type, and you fill its placeholder with String or Device.

    }

    // The ONE copy of the hub's "find a device by its exact name" rule (DRY),
    // shared by switchableNamed and unlock. A GENERIC method: <T extends Device>
    // is a type placeholder, so the same code searches a List<Switchable> and
    // hands back a Switchable, or a List<Lockable> and hands back a Lockable.
    private static <T extends Device> T findNamed(List<T> devices, String name, String kind) {
        // Check each device in turn...
        for (T device : devices) {
            // ...and return the first whose name matches (getName comes from Device).
            if (device.getName().equals(name)) {
                // Found it.
                return device;
            }
        }
        // No match: refuse loudly, naming the kind and what was asked for.
        throw new IllegalArgumentException("No " + kind + " device named: " + name);
    }

(static here means the helper needs no particular hub object. It uses only its parameters.)

6In the wild

  • DRY in the JDK: java.util.AbstractList writes indexOf, equals, hashCode and its iterator once. It builds them on two methods that each list supplies: get(index) and size(). Every list built on it shares that one copy instead of typing it again. (We will meet this shape again as a named pattern in Lesson 26.)
  • Demeter's paperboy: this lesson's kata borrows its story from a well-known short paper by David Bock: The Paperboy, The Wallet, and The Law of Demeter. It is worth reading. Check the exact title when you search for it.
  • Composition over inheritance: Joshua Bloch's Effective Java has an item named "Favor composition over inheritance." It is Item 18 in the third edition, but check the number in your copy. It shows the same double-counting bug as Lesson 03, using a HashSet subclass. It also points to two inheritance mistakes the JDK itself is stuck with: java.util.Stack extends Vector and java.util.Properties extends Hashtable.
  • KISS and YAGNI are about what is missing, so you will not find them in a class. You will find them in how teams work. Extreme Programming made YAGNI a team rule. Code review is where most YAGNI arguments happen ("who asked for this option?").

In interviews, "DRY versus the wrong abstraction" is a favourite discussion question. Good answers mention three things:

  • the rule of three;
  • the difference between knowledge and text;
  • being willing to un-merge (split back apart) a shared helper that has grown flags.

Section 7 covers all three.

7How each gets abused

Each companion principle is a brake on some kind of excess. And each one becomes an excess itself when it is pushed too far.

DRY abused: the wrong abstraction

Here is how it happens, step by step:

  1. A beginner sees two blocks that look alike, and merges them into one shared helper.
  2. Then the two callers' needs drift apart.
  3. The helper grows a flag (a true/false parameter that switches behaviour) for each difference: format(text, true, false, null).
  4. Now every change puts both callers at risk.

That is the very coupling DRY was meant to remove. A helper like this is called the wrong abstraction. Sandi Metz, a well-known teacher of design, said it well: "duplication is far cheaper than the wrong abstraction." Two habits help:

  • The rule of three: put up with a second copy. Merge on the third, when you can finally see what really repeats. (Martin Fowler credits the rule to Don Roberts in his book Refactoring.)
  • Un-merge without shame. If a shared helper has grown flags, copy it back into its callers, delete the flags, and see what is really shared.

KISS abused: "simple" as an excuse

"Keep it simple" is sometimes used to refuse any structure: "just put it all in Main." But a 600-line method is not simple. It is easy to start, and hard to read, test and change.

KISS means the simplest design that fully does the job, including the changes you already know are coming. Sometimes the problem really is complex (five house modes, four channels). Then the SOLID structure is the simple answer, because the other choice is a tangle.

Clever one-liners are the other abuse. Short code that the next reader cannot predict is not simple.

YAGNI abused: refusing to think ahead

YAGNI does not mean "never plan." It does not mean "skip tests and error handling, we don't need them yet." Build the features you need today, but keep the code easy to change: tests, clear names, small classes. Then tomorrow's feature is cheap.

YAGNI also does not apply to things that are very costly to change later. Two examples:

  • a public API: the set of classes and methods that other people's programs call (API means Application Programming Interface). Once others depend on it, changing it breaks their code.
  • a stored data format, like the layout of saved files.

Those deserve real thought before you start.

Demeter abused: the middle man

Followed without thinking, the law produces forwarding methods for everything: customer.getWalletCashInEuros(), house.getHallThermostatSensorReading(). Some classes end up with methods that mostly just pass calls on to something they hold. That smell is called a middle man.

The cure is not more forwarding. Ask what the caller actually wants done (pay, regulate). Then give the friend a method that does it. Also, the law does not apply to chains of calls on one object (like append(…).append(…)), or to plain data and stable values (see Section 3).

Composition abused: forwarding for its own sake

Say you replace a working, true is-a with a wrapper that forwards ten methods. That cures no pain. It is needless complexity in the other direction. "Favor" means "when in doubt," and SwitchableDevice is not in doubt.

Relatives and look-alikes

  • DRY vs SRP (Lesson 05): SRP decides when code that looks alike must stay apart (different actors, accidental duplication). DRY decides when code that looks different must merge (one fact). They are two halves of one question: "must these change together?"
  • YAGNI vs OCP (Lesson 06): they agree. OCP tells you how to make a variation point. YAGNI tells you to wait for the second real variant before you make one.
  • KISS vs SOLID: SOLID adds parts so that change stays local. KISS asks every part to justify itself. Lesson 10's tensions table is where they meet.
  • Demeter vs ISP (Lesson 08): both make a client know less. ISP narrows which methods it can see. Demeter narrows which objects it talks to.
  • Demeter vs Tell, Don't Ask: Demeter is the rule ("don't talk to strangers"). Tell, Don't Ask is the usual way to follow it ("ask your friend to do it").
  • Composition vs the wrapper patterns ahead: Decorator, Proxy and Adapter (Lessons 18–22) are named forms of composition, each built for one purpose. You tell them apart by their purpose, not by their shape.

8Key takeaways

  • DRY is about knowledge, not text. Each fact gets one home. The test for merging is "if one changes, must the other change too?" It is never "do they look alike?"
  • KISS means the simplest design that fully does the job. Simple means few parts and nothing hidden. That is not the same as short or clever.
  • YAGNI means building features when a real need arrives. It never means skimping on the tests and clarity that make adding them later cheap.
  • The Law of Demeter says: call methods only on yourself, your parameters, what you create, and your own fields. The cure for a train wreck is to tell your friend what you want done.
  • SOLID backs composition over inheritance. Wrappers keep only the promises they choose, add behaviour without edits, and can be injected. Inheritance stays right for a true is-a with a small, stable parent.

Five new entries in the pattern catalog, bringing it to ten:

  • DRY: one home per piece of knowledge. The "Do NOT" field warns about accidental duplication and the wrong abstraction.
  • KISS: the simplest design that fully does the job. It warns against "simple" used as an excuse.
  • YAGNI: build features when the real need arrives. It warns that YAGNI never excuses skipping quality.
  • Law of Demeter: talk only to your friends. It warns against middle men and dot-counting.
  • Favor composition over inheritance: the formal entry Lesson 03 promised, now with its SOLID backing.

11Key words

Companion principles
Short, practical rules that travel with SOLID: DRY, KISS, YAGNI and the Law of Demeter.
DRY (Don't Repeat Yourself)
Every piece of knowledge (a rule, a meaningful number, a format) is written in exactly one place.
Single source of truth
The one place in the code that holds a fact, which every other part asks.
Rule of three
Put up with a second copy; merge on the third, when you can see what really repeats.
Flag
A true/false parameter that switches a method's behaviour.
Wrong abstraction
A shared helper that merged look-alike code and then grew flags for each caller's differences.
KISS (Keep It Simple)
Of the designs that fully do the job, choose the one with the fewest parts and nothing hidden.
YAGNI (You Aren't Gonna Need It)
Don't build a feature or option until a real need for it arrives. Never an excuse to skip quality.
Extreme Programming (XP)
A way of building software in very small steps with constant testing and feedback.
Public API
The classes and methods other people's programs call; costly to change later.
Law of Demeter
A method calls methods only on itself, its parameters, objects it creates and its own fields.
Friend / stranger
A friend is this, a parameter, a created object or a field; anything a friend returns is a stranger.
Train wreck (message chain)
A chain of calls reaching through objects, like a.getB().getC().doD().
Tell, Don't Ask
Tell an object what you want done (customer.pay(2)) instead of taking its insides and doing it yourself.
Middle man
A class whose methods mostly just pass calls on to an object it holds.
Generic method / type parameter / bound
A method with a type placeholder (T) filled in at each call; extends Device limits what T may be.

12Quick recap

  • DRY: one home per fact; merge only when one change must change the other.
  • KISS: the simplest design that fully does the job, with nothing hidden.
  • YAGNI: build features when the real need arrives, but never skip tests or clarity.
  • Law of Demeter: talk only to your friends; tell them what to do instead of reaching inside.
  • Each rule becomes a problem when pushed too far; composition is favoured, not required.
