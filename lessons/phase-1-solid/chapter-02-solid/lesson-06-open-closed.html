O — Open/Closed Principle

Add new behaviour by adding new code, not by editing code that already works. The growing if-else chain is the classic violation, and an interface is the cure.

Kata package: com.katas.ocp (wrong way in com.katas.ocp.naive).
Smart Home Hub: created routines/Routine.java, AllOn.java, AllOff.java, KeepOnly.java, RoutinesTest.java; modified home/Hub.java (startUp() → run(Routine)), HubTest.java, Main.java.
Prerequisites: Lesson 05; interfaces and polymorphism from Lesson 01 and Lesson 02.

1The pain

The most common shape of rot in real code is not exotic. It is an if-else chain that grows one branch at a time.

A shop quotes shipping prices. Each method (Standard, Express, Overnight) has its own price formula and its own delivery time. So the quoter checks the method's name:

private int cost(String method, int weightKg) {
    if (method.equals("Standard"))       return 5 + weightKg;
    else if (method.equals("Express"))   return 10 + weightKg * 2;
    else if (method.equals("Overnight")) return 25 + weightKg * 3;
    throw new IllegalArgumentException("Unknown method: " + method);
}
private int days(String method) {
    if (method.equals("Standard"))       return 5;      // the SAME ladder, again
    else if (method.equals("Express"))   return 2;
    else if (method.equals("Overnight")) return 1;
    throw new IllegalArgumentException("Unknown method: " + method);
}

Then marketing announces drone delivery. To support it, you must open a class that works. You must find every ladder that checks the method's name. Here there are two. In a real system there are often a dozen, spread across files. You add a branch to each, and re-test everything those ladders touch. Forget one ladder, and the quote fails halfway through. Next month it is "eco shipping," and the same surgery happens again. The class is never finished.

Predicted symptom, until both ladders are edited

Naive: Express: 20 (2-day delivery)
Naive refused: Unknown method: Drone

The pain, named: a class that must be edited for every new variant. It is the "rigidity" smell from Lesson 04, and the repeated ladder is "needless repetition." Each edit to working code is a fresh chance to break the variants that already worked.

2Real-world analogy

A wall socket. The electrician wires the socket once and closes up the wall. Since then you have plugged in a lamp, a phone charger and a vacuum cleaner. You have even plugged in things that had not been invented when the house was built. Nobody opened the wall for any of them. The socket is closed: its wiring is finished. The house is open: new appliances keep working. What makes that possible is the agreed plug shape.

3The principle explained

3.1 The paradox, untangled

In 1988 Bertrand Meyer wrote that software modules should be "open for extension, but closed for modification." It sounds like a contradiction. How can something change without being changed? The trick is that the two words talk about different things:

  • Open for extension: the behaviour can grow. The system can learn to do new things.
  • Closed for modification: the source code of the existing class does not have to be edited for that to happen. It is finished, tested, and left alone.

So behaviour grows by adding new code, never by editing old code. That is the Open/Closed Principle (OCP), the "O" in SOLID.

3.2 How it is achieved: a variation point

Look at what the naive ladders really hold: the same three questions (name, cost, delivery time), answered differently for each method. Everything that varies sits behind those three questions. So we write them down as a contract. Each method answers them in its own class:

public interface ShippingMethod {
    String name();
    int cost(int weightKg);
    int deliveryDays();
}

Some places in a design will keep getting new variants. You put an interface there so the new variants can plug in. Such a place is called a variation point. The quoter now asks the method object, instead of checking its name: method.cost(weightKg). Polymorphism picks the right formula at run time. That is the job the if-else chain used to do by hand.

3.3 One place still changes, and that is fine

Something must still say "we offer drone delivery now." That happens where objects are created and wired together: List.of(new StandardShipping(), …, new DroneShipping()) in Main. This place, where concrete objects are created and wired together, is called the assembly point (in the hub, also Main). OCP does not promise that nothing changes. It promises that the logic (the quoting, the hub's work) stays closed. New variants touch only the assembly point and their own new file. Later lessons show ways to shrink even that one line.

Change requestNaive: files editedOCP: files edited
Add drone deliveryShippingQuoter (both ladders)New DroneShipping + one line in Main
Change Express's priceShippingQuoter (and re-test every method in it)ExpressShipping only
Add a third question, e.g. "is it tracked?"A third ladder in ShippingQuoterThe interface and every implementation (see the note below)

The last row is the honest limit. OCP closes code against one kind of change: here, "new shipping methods." A different kind of change is "new questions about every method." For that one, the interface itself must change, and every implementation with it. No design is closed against everything. Choosing which changes to close against is the real skill (Section 7).

After the refactoring, a new requirement arrives: "Express gets 10% off on Mondays." Which classes change?

Only ExpressShipping, because its price rule lives there and nowhere else. ShippingQuoter doesn't care how a cost is worked out, only that cost() returns one. (If the discount had to apply to every method, that would be a new variation point worth thinking about. One way is a wrapper around any ShippingMethod, like the ones from Lesson 03.)

3.4 Why OCP is the engine behind most patterns

Meyer's original idea got openness through inheritance: extend a finished class and override parts of it. Lessons 02–03 showed the costs of that. Robert C. Martin restated OCP around interfaces. That is the version used here. The shape is: closed code above, a contract in the middle, new classes below. Once you see it, you will find it in most of the patterns ahead. Each one is a ready-made variation point for one kind of change:

  • Swapping one algorithm for another, chosen at run time (Lesson 25).
  • Adding behaviour by wrapping, the LoggedDevice shape (Lesson 19).
  • Letting any number of listeners react to an event without the event's source knowing them (Lesson 27).
  • Turning requests into objects so they can be queued and undone (Lesson 28). The hub's routines are heading there.
  • Choosing which class to create without the caller naming it (Lessons 14–15). This shrinks the assembly-point line above.

Each answers the same question: "where will new variants arrive, and how do we let them in without editing what works?"

4The kata

Package com.katas.ocp. Saved: katas/src/main/java/com/katas/ocp/ShippingMethod.java is the contract shown in 3.2. Saved: StandardShipping.java, ExpressShipping.java, OvernightShipping.java each answer the three questions for one method. Here are the closed quoter and the method added later:

Saved: katas/src/main/java/com/katas/ocp/ShippingQuoter.java

// The RIGHT WAY, part 2: the CLOSED code.
package com.katas.ocp;

// The JDK's growable list.
import java.util.ArrayList;
// The JDK's list interface.
import java.util.List;

// Quotes any shipping method it is given. It names no concrete method and
// contains no if-else on method names, so new methods never require
// editing it. It is closed for modification, and open for extension
// through the ShippingMethod contract.
public class ShippingQuoter {

    // One line of text for a customer, e.g. "Express: 20 (2-day delivery)".
    public String quote(ShippingMethod method, int weightKg) {
        // Ask the method itself: no ladder, no knowledge of which method it is.
        return method.name() + ": " + method.cost(weightKg) + " (" + method.deliveryDays() + "-day delivery)";
    }

    // Quote every method on offer, in the order given.
    public List<String> quoteAll(List<ShippingMethod> methods, int weightKg) {
        // Collect one line per method.
        List<String> lines = new ArrayList<>();
        // The same call for every method, whatever it is.
        for (ShippingMethod method : methods) {
            // Reuse the single-quote rule.
            lines.add(quote(method, weightKg));
        }
        // An unmodifiable copy for the caller.
        return List.copyOf(lines);
    }
}

Saved: katas/src/main/java/com/katas/ocp/DroneShipping.java

// ADDED LATER: the new requirement "offer drone delivery".
package com.katas.ocp;

// This whole feature is ONE NEW FILE. ShippingQuoter, ShippingMethod and
// the other three methods were not opened, edited, or re-tested.
// That is "open for extension, closed for modification".
public class DroneShipping implements ShippingMethod {

    // The customer-facing name.
    @Override
    public String name() {
        // Shown in the quote.
        return "Drone";
    }

    // 15 plus 4 per kilo: drones charge more for weight.
    @Override
    public int cost(int weightKg) {
        // The drone formula.
        return 15 + weightKg * 4;
    }

    // One day.
    @Override
    public int deliveryDays() {
        // The drone delivery time.
        return 1;
    }
}

Saved: katas/src/main/java/com/katas/ocp/Main.java

// The runnable demo for Lesson 06's kata.
package com.katas.ocp;

// List.of to build the list of methods on offer.
import java.util.List;

// Shows the naive quoter refusing the new "Drone" method, then the
// open/closed quoter handling it without a single edit.
public class Main {

    // The JVM starts here when you run this class.
    public static void main(String[] args) {
        // NAIVE: it only knows the names written into its ladders.
        com.katas.ocp.naive.ShippingQuoter naive = new com.katas.ocp.naive.ShippingQuoter();
        // A known method works.
        System.out.println("Naive: " + naive.quote("Express", 5));
        // try: the new method will be refused by throwing.
        try {
            // "Drone" is in neither ladder.
            System.out.println("Naive: " + naive.quote("Drone", 5));
        } catch (IllegalArgumentException e) {
            // Supporting it would mean editing BOTH ladders.
            System.out.println("Naive refused: " + e.getMessage());
        }

        // OPEN/CLOSED: the methods on offer are chosen HERE, as objects.
        List<ShippingMethod> offered = List.of(new StandardShipping(), new ExpressShipping(),
                new OvernightShipping(), new DroneShipping());
        // The quoter has never heard of Drone, and does not need to.
        for (String line : new ShippingQuoter().quoteAll(offered, 5)) {
            // One line per method.
            System.out.println("OCP: " + line);
        }
    }
}

What happens when it runs

  1. The naive quote for "Express": cost walks its ladder to the second branch (10 + 5 × 2 = 20), and days walks its own ladder to 2.
  2. The naive quote for "Drone": the string is built left to right, so cost runs first. It falls through every branch and throws. The catch prints the message.
  3. The list offered holds four method objects. quoteAll loops over them, calling the same quote for each.
  4. For each object, method.cost(5) is dispatched to that object's own class: 5 + 5 = 10, 10 + 10 = 20, 25 + 15 = 40, 15 + 20 = 35. Its deliveryDays() is dispatched the same way.
  5. Drone is quoted exactly like the others. The quoter's code never mentions it.

5Applied to the Smart Home Hub

The pain, arriving in the hub

The homeowner loves the hub, and wants modes. "Everything on" in the morning. "Away" when the house is empty. "Goodnight" with only the thermostat running. Next month it will be "movie night," then "holiday." The tempting code is Section 1's ladder again, inside Hub:

public void applyMode(String mode) {
    if (mode.equals("morning")) { /* all on */ }
    else if (mode.equals("away")) { /* all off */ }
    else if (mode.equals("goodnight")) { /* all off except the thermostat */ }
    // ...one more branch, and one more edit to Hub, for every mode ever invented
}

The modes are a clear variation point. New ones are certain to keep arriving, and it is the homeowner who asks for them, not the hub's maintainer. So the hub gets a contract for "a mode," and then it is closed.

Saved: smarthome/src/main/java/com/smarthome/routines/Routine.java

// House "modes" live in their own package: they are what keeps changing.
package com.smarthome.routines;

// Routines work on devices through the contract only.
import com.smarthome.devices.Device;

// The JDK's list interface.
import java.util.List;

// THE VARIATION POINT: one thing a homeowner can ask the house to do. The
// hub runs any Routine without knowing which one it is, so a new mode is a
// new class, never an edit to the hub.
public interface Routine {

    // Apply this routine to every device in the house.
    void applyTo(List<Device> devices);
}

Saved: smarthome/src/main/java/com/smarthome/routines/KeepOnly.java

// One routine: keep a chosen few devices on, everything else off.
package com.smarthome.routines;

// The device contract.
import com.smarthome.devices.Device;

// The JDK's list interface.
import java.util.List;

// e.g. "Goodnight": keep only the thermostat running. Which devices to keep
// is chosen by whoever creates the routine, so one class covers many modes.
public class KeepOnly implements Routine {

    // The names of the devices that should stay (or be switched) on.
    private final List<String> namesToKeepOn;

    // The caller decides which devices stay on.
    public KeepOnly(List<String> namesToKeepOn) {
        // An unmodifiable copy, so the routine cannot change after creation.
        this.namesToKeepOn = List.copyOf(namesToKeepOn);
    }

    // Kept devices on, all others off, switching only what must change.
    @Override
    public void applyTo(List<Device> devices) {
        // Visit every device.
        for (Device device : devices) {
            // Is this one on the keep list?
            boolean keep = namesToKeepOn.contains(device.getName());
            // Kept but off: switch it on.
            if (keep && !device.isOn()) {
                // On, in its own way.
                device.turnOn();
            }
            // Not kept but on: switch it off.
            if (!keep && device.isOn()) {
                // Off, in its own way.
                device.turnOff();
            }
        }
    }
}

(&& means "and": both conditions must be true. ! means "not.")

Saved: routines/AllOn.java and routines/AllOff.java are the same shape, without the keep-list. AllOn switches on every device that is off, and AllOff switches off every device that is on. All three switch only what must change, so the activity log never records a light being "switched on" when it was already on.

6In the wild

Sorting in the JDK is closed; ordering is open. List.sort contains a finished, tuned sorting algorithm that nobody edits. What it does not know is what "before" means for your objects. That question sits behind a contract, java.util.Comparator. To sort a new way, you supply a new comparator and never touch the sort:

List<String> names = new ArrayList<>(List.of("Cara", "Ade", "Bo"));
names.sort(Comparator.naturalOrder());   // [Ade, Bo, Cara]
names.sort(Comparator.reverseOrder());   // [Cara, Bo, Ade]

Same sort, new behaviour, zero edits to the JDK. It is ShippingQuoter and ShippingMethod at world scale. (Writing your own comparators uses a short syntax. The Strategy lesson, Lesson 25, explains it properly.)

Plugin systems are OCP made into products. Browser extensions, IDE plugins and payment-provider add-ons all add behaviour to a host program that is closed. You cannot edit Chrome's source to add your extension. In code review, watch for a change that adds "one more else if" to a ladder that already has ten branches. That is the moment to suggest a variation point.

7When NOT to use it

The over-application trap

Every interface is a bet that variants will arrive there. Bet everywhere "just in case," and the code fills up with junk. You get interfaces with only one implementation. You dig through three layers to find the one real class. You get abstractions shaped by guesses that turned out wrong. Building flexibility for a future that never comes is the needless-complexity smell from Lesson 04. It is sometimes called speculative generality. You cannot close code against every possible change, so choose which ones.

  • Wait for real evidence. A common rule: write the simple version first. Then the second variant arrives, and you feel the ladder starting. That is the moment to add the variation point, because now you know what really varies. Martin calls this "taking the first bullet."
  • A small, fixed set needs no interface. The days of the week, the four card suits, "on/off" will not grow. A plain if or switch over them is clearer than four classes. (Modern Java even lets the compiler check that such a switch covers every case. Lesson 40 shows how.)
  • One local if-else is not a violation. The smell is the repeated ladder: the same branches in several places, all growing every time a variant is added.

The cost it always charges

More classes and files. Indirection: "what does Express cost?" means opening ExpressShipping, not reading one method. And a loss of overview. With a ladder, every variant's rule sits on one screen. With OCP, they are spread across files. For small, stable sets, that is a real loss. That is why the set must be growing to make OCP worth it.

Relatives and look-alikes

  • SRP (Lesson 05) decides where code lives (one actor per class). OCP decides how it grows (by adding, not editing). They pull together: each ShippingMethod class is also one responsibility.
  • Liskov Substitution (Lesson 07) is OCP's safety rule. Adding DroneShipping is safe only if it truly keeps the contract the quoter relies on. A new class that breaks the contract breaks the "closed" code that trusted it.
  • Dependency Inversion (Lesson 09) is the same arrow-direction idea, seen from higher up. The high-level code (quoter, hub) and the details (methods, routines) both depend on the contract.

8Key takeaways

  • The Open/Closed Principle says code should be open for extension but closed for modification. New behaviour arrives as new code. The source of what already works is left alone.
  • The classic violation is a growing if-else (or switch) on a type name, repeated in several places. Every new variant forces edits to working code.
  • The cure is a variation point. An interface captures what varies, each variant gets its own class, and polymorphism replaces the ladder. Only the assembly point and the new file change.
  • No design is closed against every change. OCP protects against one chosen kind. Choose it from real evidence (usually the second variant), not from guesses.
  • Most patterns ahead are ready-made variation points for one kind of change. That makes OCP the engine behind them. Like them, it always costs extra classes and indirection.

9Challenge

A ticket system prices tickets with two ladders on the customer type:

public int price(String customer, int basePrice) {
    if (customer.equals("Regular")) return basePrice;
    else if (customer.equals("Senior")) return basePrice / 2;
    throw new IllegalArgumentException(customer);
}
public String label(String customer) {
    if (customer.equals("Regular")) return "Standard fare";
    else if (customer.equals("Senior")) return "Senior fare";
    throw new IllegalArgumentException(customer);
}

(a) A Student type is coming (30% off, label "Student fare"). The business says more types will follow. Redesign it with OCP. List exactly which files change when Student is added. (b) Predict the output of quoting a base price of 20 for all three types. (c) Would you still do this if the business promised there would only ever be Regular and Senior?

Click to reveal the answer

(a) The two ladders ask the same two questions (price and label), so those questions become the variation point:

// The variation point: everything that differs per customer type.
public interface Fare { int price(int basePrice); String label(); }

public class RegularFare implements Fare {
    public int price(int basePrice) { return basePrice; }
    public String label() { return "Standard fare"; }
}
public class SeniorFare implements Fare {
    public int price(int basePrice) { return basePrice / 2; }
    public String label() { return "Senior fare"; }
}
// ADDED LATER, as one new file:
public class StudentFare implements Fare {
    public int price(int basePrice) { return basePrice * 70 / 100; }
    public String label() { return "Student fare"; }
}

// The CLOSED code: no names, no ladder.
public class TicketPricer {
    public String quote(Fare fare, int basePrice) { return fare.label() + ": " + fare.price(basePrice); }
}

Adding Student changes one new file (StudentFare) plus the assembly point. That is wherever fare objects are chosen, for example the screen where the customer picks their type. TicketPricer, Fare, RegularFare and SeniorFare are untouched. (Note basePrice * 70 / 100. Multiplying first keeps whole-number maths exact for 20 → 14. Writing basePrice * (70 / 100) would give 0, because 70 / 100 is 0 in whole-number division.)

(b)

Prediction — quoting 20 for Regular, Senior, Student

Standard fare: 20
Senior fare: 10
Student fare: 14

(c) Probably not. There are two fixed variants in one small file, and no growth is expected. A single, readable if/else is the simpler design. The interface would be speculative generality. The trigger to refactor is the moment a third type actually arrives. That is also the cheapest moment, because you will know what really varies. If you type the redesign in a scratch package, run it and compare with (b). The machine is the judge.

  • Intent: extend behaviour by adding code, not by editing working code.
  • Pain: a class edited for every new variant; repeated if-else ladders on a type name.
