Getting Your Machine Ready

The JDK builds, the JVM runs, Maven drives the build, Git keeps the history. By the end, two Maven projects compile and their tests pass.

1The pain

Before we talk about design at all, we need a workshop that builds the same way every time, on every machine. Here is what life looks like without one.

Imagine you write one small Java file, Main.java. You translate it into something runnable by hand, then run it. It works. Easy.

# translate Main.java into Main.class, then run it
javac Main.java
java Main
Hello!

Now a new requirement arrives: "add an automatic check that the code works." That check needs an outside library called JUnit (you will meet it properly in Section 4). You try the same trick:

javac SmokeTest.java
SmokeTest.java:3: error: package org.junit.jupiter.api does not exist
import org.junit.jupiter.api.Test;
                            ^

Now you must find the library on the internet and download the right version. You must tell the translator where it is. Then you must find every test by hand and run each one. Then a friend clones your code. Their machine has a different Java version and a different copy of the library, and the code breaks for them but not for you. Every developer has heard the sad sentence: "but it works on my machine."

The pain has a name: a manual, unrepeatable build. The cure is three tools, each pinned to an exact version. The JDK is a fixed Java toolbox. Maven is a build tool: one command fetches libraries and runs tests. Git keeps the history, so nothing is ever lost. This lesson installs all three and proves they work.

If your machine is already set up from an earlier run of this course, skim Sections 2 and 3, then run the checks in Section 4. The checks are the part that matters.

3The concepts explained

3.1 How Java runs: from your text to a running program

A computer cannot run the text you type. It first has to be translated. Translating human-readable code into a form a machine can run is called compiling, and the program that does it is a compiler. Java's compiler is called javac.

Most compilers translate straight into the raw instructions of one kind of computer. Then the result only runs on that kind of computer. Java does something smarter. javac translates into a halfway language: not human text, and not raw machine instructions either. It is stored in .class files. For example, javac Main.java produces Main.class. This halfway language is called bytecode.

Bytecode needs a program to run it. That program reads the bytecode and carries out each instruction on whatever computer it is installed on. Windows has one, macOS has one, Linux has one. So you compile once, and the same Main.class runs everywhere. A program that acts like a computer inside your computer is called a virtual machine, and this one is the JVM (Java Virtual Machine).

3.2 The JDK: the whole toolbox

To build Java you need the compiler. To run Java you need the JVM plus Java's ready-made building blocks: text, lists, maps, files, and so on. Those ready-made blocks are called the standard library. One download gives you all of it, and that bundle is called the JDK (Java Development Kit).

The JDK has two halves. The tools half builds programs (javac, plus the java command that starts the JVM). The runtime half runs them: the JVM plus the standard library. That runtime half used to be downloaded on its own, under the name JRE (Java Runtime Environment). You will still see the word, but today you simply install the JDK.

Java releases a new version every six months. Most versions get fixes for only a short time. Every few years, one version is promised fixes for many years, so teams can stand on it safely. Such a version is called an LTS (Long-Term Support) release. We pin Java 21, an LTS release, for the whole course. Pinning one version means every prediction in these pages stays true for you.

Install it. Any JDK 21 build works. A popular free one is Eclipse Temurin 21 from adoptium.net. On Windows, the installer has an option to set JAVA_HOME and the PATH (both explained in 3.3). Tick both. Then open a new terminal and check:

java -version
javac -version

Prediction — your exact numbers and vendor text will differ

3.3 PATH and JAVA_HOME: how your terminal finds Java

When you type java, how does the terminal know which program you mean? Your computer keeps a few named settings that every program can read. For example, one setting holds your user name, and another says where temporary files go. These named settings are called environment variables.

One environment variable lists folders, in order. When you type a command, the terminal looks in the first folder, then the second, and so on, and runs the first match it finds. That list is called the PATH. If an old Java 17 folder comes before your Java 21 folder in the PATH, then typing java runs Java 17.

Maven does not rely on the PATH alone. It first looks for an environment variable that names one JDK folder directly, for example C:\Program Files\Eclipse Adoptium\jdk-21…. If that variable is set, Maven uses that JDK. If it is not set, Maven falls back to the java it finds on the PATH. That variable is called JAVA_HOME.

So the two can disagree. java -version can say 21 while Maven quietly compiles with 17, or the other way round. Try every combination below.

3.4 Maven: the foreman

You could call javac by hand for every file, download libraries by hand, and run tests by hand. That is the pain from Section 1. A program that does all of it from one command is called a build tool. Ours is Maven. One command compiles your code, downloads the libraries you asked for, runs your tests, and reports the result.

A few words Maven uses constantly, one at a time:

  • Your project often needs code that someone else wrote and published, like JUnit for tests. You do not copy it in by hand. You write down its name and version, and Maven downloads it. An outside library your project uses is called a dependency.
  • Maven needs a work order for each project: its name, its Java version, its dependencies, and its extra tools. That work order is one file, pom.xml. It is called the POM (Project Object Model).
  • Every published library needs a unique address so Maven can fetch exactly the right one. The address has three parts: who owns it (groupId), its name (artifactId), and its version. For example, org.junit.jupiter : junit-jupiter : 5.14.4. These three parts are the coordinates, and the published, versioned thing they point to is called an artifact.
  • Maven itself only knows the order of the steps. The real work in each step is done by small add-on tools, for example "the thing that runs tests." These add-ons are called plugins. We pin three: the compiler plugin (built in), Surefire (runs tests), and exec (runs a main method).
  • Downloaded artifacts are saved once in a folder in your home directory, ~/.m2/repository, and reused by every project after that. This folder is called the local repository. It is why only your first build is slow.

Install Maven (3.9.x) from maven.apache.org. Unzip it, add its bin folder to your PATH, open a new terminal, and check:

mvn -version

Maven home: …

The line that matters is Java version: 21. That is the JDK Maven will compile with (see 3.3).

3.5 An IDE: where you will type

Plain text editors know nothing about Java. A smarter editor colours your code, spots typos as you type, suggests method names, and runs tests with a click. Such an editor is called an IDE (Integrated Development Environment). Pick either IntelliJ IDEA Community Edition (free, the smoothest for Java) or VS Code with the "Extension Pack for Java." Every command in this course is a terminal command, so nothing depends on which one you choose.

3.6 Git and GitHub: the photo album and the safe

  • Some tools save the history of your files as a series of snapshots, so you can always go back. Such a tool is called a version-control tool. Ours is Git.
  • The folder Git watches, together with its whole saved history, is called a repository (or repo).
  • One saved snapshot, with a short message saying what changed (for example, "lesson 00 – setup"), is called a commit.
  • GitHub is a website that keeps a copy of your repository online, so a broken laptop never loses your work. That online copy is called a remote. Sending your new commits up to it is called a push.

Install Git from git-scm.com and check it with git --version (prediction: git version 2.xx.x). Create a free GitHub account and one empty repository named design-patterns-learning. Do not let GitHub add a README or .gitignore. We write those ourselves.

4.3 katas/pom.xml: read it slowly, it teaches how Maven thinks

Saved: katas/pom.xml

<?xml version="1.0" encoding="UTF-8"?>
<!-- The line above says "this is an XML file, stored as UTF-8 text". -->
<!-- This is the build file for the KATAS project: one tiny, frozen example -->
<!-- per pattern. Maven reads THIS file to know how to compile and test. -->

<!-- <project> wraps everything. The xmlns lines name the official POM -->
<!-- vocabulary, so Maven and your IDE can check every tag below is valid. -->
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">

    <!-- The version of the POM *language* (not of our project). Always 4.0.0. -->
    <modelVersion>4.0.0</modelVersion>

    <!-- The coordinates: the project's unique address in the Java world. -->
    <!-- groupId = who owns it (a reverse-domain-style name we chose). -->
    <groupId>com.katas</groupId>
    <!-- artifactId = this particular project's name. -->
    <artifactId>design-pattern-katas</artifactId>
    <!-- version = our own version number for this project. -->
    <version>1.0.0</version>
    <!-- packaging = bundle the compiled classes into one .jar file. -->
    <packaging>jar</packaging>

    <!-- Properties: named settings, reused below as ${name}. Pinning them -->
    <!-- here once means every lesson builds against the SAME versions. -->
    <properties>
        <!-- Compile the Java 21 language AND produce Java 21 bytecode. -->
        <maven.compiler.release>21</maven.compiler.release>
        <!-- Read source files as UTF-8 so special characters never corrupt. -->
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <!-- The one JUnit 5 version pinned for the whole course. -->
        <junit.version>5.14.4</junit.version>
        <!-- The class `mvn compile exec:java` runs when you name none. A -->
        <!-- property (not plugin config) so -Dexec.mainClass=... can override -->
        <!-- it: that is how each kata's own Main demo is picked later. -->
        <exec.mainClass>com.katas.Main</exec.mainClass>
    </properties>

    <!-- Dependencies: outside libraries Maven downloads for us. -->
    <dependencies>
        <!-- JUnit 5 ("Jupiter"), our testing library. This one artifact -->
        <!-- pulls in everything needed to write and run tests. -->
        <dependency>
            <!-- JUnit's owner name... -->
            <groupId>org.junit.jupiter</groupId>
            <!-- ...its project name... -->
            <artifactId>junit-jupiter</artifactId>
            <!-- ...and the pinned version, read from the property above. -->
            <version>${junit.version}</version>
            <!-- test scope: available to tests only, never shipped in the jar. -->
            <scope>test</scope>
        </dependency>
    </dependencies>

    <!-- Build settings: which plugins (Maven's add-on tools) to use. -->
    <build>
        <plugins>
            <!-- Surefire RUNS the tests during `mvn test`. A modern 3.x -->
            <!-- version is needed to find JUnit 5 tests reliably. -->
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
                <version>3.5.5</version>
            </plugin>
            <!-- The exec plugin powers `mvn compile exec:java`: it runs a -->
            <!-- class's main method with our compiled classes on hand. -->
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.6.1</version>
            </plugin>
        </plugins>
    </build>

</project>

Read top to bottom, the POM answers four questions. Who am I? The coordinates. Which versions? The properties: Java 21 and JUnit 5.14.4, pinned once. What do I need? One dependency, JUnit, in test scope, so it helps the tests but never ships with the program. Which tools run the steps? Surefire and exec. Saved: smarthome/pom.xml is the same file with com.smarthome coordinates and com.smarthome.Main as its default main class. On purpose, JUnit is the only dependency in either project. There is no framework, so every pattern is seen bare.

The versions JUnit 5.14.4 and Surefire 3.5.5 are the ones pinned at the course's first setup. exec-maven-plugin 3.6.1 was newly pinned for this restart. If Maven reports it cannot find that version, tell me what it says, and we will pin the version your Maven can find.

4.4 The four Java files

Every Java program needs a starting point, a method the JVM knows to call first. It must be spelled exactly public static void main(String[] args), or the JVM will not recognise it. This is the main method. (The words public and static get their full story in Lesson 01 and beyond. For now: "callable from outside" and "no object needed.")

Saved: katas/src/main/java/com/katas/Main.java

// Declares the package (folder-path namespace) this class lives in. The folders
// on disk (com/katas) must match this line exactly, or Java will not find it.
package com.katas;

// A public class is one visible to code in other packages. The file name
// (Main.java) must match the class name (Main) exactly in Java.
public class Main {

    // main is the special method the Java runtime calls first when the program
    // starts. Its signature MUST be exactly this for the JVM to recognise it:
    // public (callable from outside), static (no object needed to call it),
    // void (returns nothing), named main, taking an array of String arguments.
    public static void main(String[] args) {
        // Print one line to the console so we can SEE the toolchain works:
        // if this text appears, Java compiled and ran our code successfully.
        System.out.println("Katas project is ready.");
    }
}

Saved: smarthome/src/main/java/com/smarthome/Main.java

// The package (namespace) for the Smart Home Hub's entry point. The folder
// path com/smarthome on disk must mirror this line exactly.
package com.smarthome;

// The application's top-level class. File name Main.java matches class Main.
public class Main {

    // The JVM's starting point: same required signature as any Java program.
    public static void main(String[] args) {
        // A friendly startup banner. Later lessons will replace this with real
        // hub behaviour (creating devices, running scenes). For now it simply
        // proves the Smart Home project compiles and runs.
        System.out.println("Smart Home Hub is starting up...");
    }
}

Now the tests. Some small pieces of code check other code automatically, so a mistake shows up the moment you run them. Such a check is called a unit test. The library that finds and runs unit tests and reports pass or fail is JUnit. Two more words appear in the file below:

  • A tag stuck onto code is an annotation. Tools read it, but Java itself ignores it. @Test tells JUnit "run this method as a test."
  • An assertion is a line inside a test that says what must be true. If it is not true, the test fails. assertEquals(4, 2 + 2) fails if the two values differ.

Our first tests check nothing real. They only prove that the machinery works: the compiler, Maven, JUnit and Surefire. The name comes from electronics: you switch a new device on and check that no smoke comes out. A test like this is called a smoke test.

Saved: katas/src/test/java/com/katas/SmokeTest.java

// Same package as the code under test. Test sources live in src/test/java,
// but share the package name so tests can reach package-visible members.
package com.katas;

// Import the @Test annotation: the marker that tells JUnit "run this method
// as a test". An annotation is a tag attached to code that tools can read.
import org.junit.jupiter.api.Test;
// Import the assertion helper. assertEquals(expected, actual) fails the test
// if the two values are not equal. A "static import" lets us write the method
// name directly (assertEquals) instead of Assertions.assertEquals.
import static org.junit.jupiter.api.Assertions.assertEquals;

// A "smoke test" is the simplest possible test: it does not check real logic,
// it just confirms the build-and-test machinery itself is wired up correctly.
// (The name comes from switching on a device and checking no smoke comes out.)
public class SmokeTest {

    // @Test marks this method as one JUnit should execute. No return value; a
    // test passes if it finishes without an assertion throwing an error.
    @Test
    void toolchain_is_wired_up() {
        // Assert that 2 + 2 equals 4. This is trivially true, so the test
        // passes ONLY if Maven, JUnit, and the compiler are all working.
        assertEquals(4, 2 + 2);
    }
}

Saved: smarthome/src/test/java/com/smarthome/SmokeTest.java

The hub's smoke test is the same idea, using assertTrue(true): a condition that is always true. It passes the moment the machinery works.

4.5 What mvn test does, step by step

  1. You type mvn test inside the katas/ folder. Maven looks for pom.xml in the current folder. That is why the folder matters.
  2. Maven reads the POM and learns three things: Java 21, one dependency (JUnit 5.14.4), and two pinned plugins.
  3. For each library and plugin, Maven checks ~/.m2/repository. The very first time they are missing, so Maven downloads them and you see many Downloading… lines. Every later run finds them in the cache.
  4. The compiler plugin runs javac on everything under src/main/java. It writes bytecode (Main.class) into target/classes.
  5. It does the same for src/test/java, writing SmokeTest.class into target/test-classes. JUnit is available here because of its test scope.
  6. Surefire looks through the compiled test classes, finds every method marked @Test, and asks JUnit to run each one. toolchain_is_wired_up() runs: 2 + 2 is 4, so the assertion holds and the test passes.
  7. Surefire counts the results: 1 run, 0 failures, 0 errors, 0 skipped.
  8. Nothing failed, so Maven prints BUILD SUCCESS.

You run mvn test and it ends with BUILD SUCCESS, but the report says Tests run: 0. Is everything fine?

No. Zero tests ran, so nothing was checked. The green build looks fine, but it hides that. There are three usual causes. The test file is in the wrong folder. 5The two code homes, and the Smart Home Hub

This course keeps code in two homes, on purpose, because they do two different jobs.

A kata is a small practice exercise you can repeat until it becomes second nature (the word comes from martial arts). Here it means one tiny, self-contained example per pattern, in its own package, for example com.katas.strategy. Each kata holds the wrong-way version (in a sub-package called naive), the right-way version, a small main demo, and a test. Once its lesson is done, a kata is frozen: never edited again. You can always go back and see a pattern in its smallest, purest form.

The Smart Home Hub is the opposite: one real, living application that grows lesson by lesson. It controls lights, thermostats, locks, cameras and speakers, reacts to sensors, runs scenes and schedules, and plugs in third-party devices. A pattern goes into the hub only when the hub really needs it. Today the hub is just its banner line. In Lesson 01 it gets its first real code: a Device contract and two devices.

Keeping the wrong-way code beside the right-way code is a teaching device. In a real codebase you delete the naive version once it is refactored, because Git's history already remembers it.

6In the wild

The three-part address you just wrote is how the whole Java world shares code. The free public store of open-source Java libraries is called Maven Central. Every library in it is fetched by exactly these coordinates: org.junit.jupiter : junit-jupiter : 5.14.4 is the line our POM used. Gradle, the other big Java build tool, reads the very same coordinates from the very same store. Learn coordinates once, and you can pull any open-source Java library into any project.

On a real team, nobody trusts "it passed on my laptop." Every push to GitHub starts a clean server. The server gets the code and runs the same mvn test. This setup is called continuous integration (CI). Pinned versions are what make that server's result match yours. That is the professional cure for "works on my machine," and it rests on exactly what you set up today.

7Gotchas and common mistakes

  • 'mvn' is not recognized / command not found. The tool's bin folder is not on the PATH, or the terminal was opened before you changed it. PATH changes only reach terminals opened afterwards, so open a new one.
  • release version 21 not supported. Maven is using an older JDK, usually because JAVA_HOME points at it. Re-run the simulation in 3.3, then fix JAVA_HOME.
  • there is no POM in this directory. You ran Maven in the wrong folder. Each project (katas/, smarthome/) has its own POM, and Maven only looks in the current folder. The repo root has no POM.
  • PowerShell and -D options. Later lessons run a chosen kata with -Dexec.mainClass=com.katas.x.Main. PowerShell splits that argument at the dot unless you wrap it in quotes. Always write mvn compile exec:java "-Dexec.mainClass=com.katas.x.Main". The quotes do no harm in other terminals.
  • Committing build output. If target/ ever appears in git status, your .gitignore is missing or misnamed. Compiled bytecode never belongs in Git.

8Key takeaways

  • The JDK builds, the JVM runs, and Maven drives the whole build. javac turns source into bytecode, the JVM runs it on any operating system, and Maven does every step from one pom.xml.
  • Versions are pinned on purpose (Java 21 LTS, JUnit 5.14.4, Surefire 3.5.5, exec 3.6.1). That keeps the code and its predicted output the same on every machine and in every lesson.
  • The PATH decides which java your terminal runs. JAVA_HOME, when set, decides which JDK Maven uses. Both must point at JDK 21.
  • A smoke test checks the machinery, not the logic. A green test on day one means the compiler, Maven, JUnit and Surefire all work. Always read the Tests run: count.

Maven tests neither project. It fails before doing any work, because Maven only reads the pom.xml in the current folder, and the repo root has none:

Prediction

[ERROR] The goal you specified requires a project to execute but there is no POM in this directory (…\design-patterns-learning). Please verify you invoked Maven from the correct directory.
[INFO] BUILD FAILURE

The habit: always cd into the project first (cd katas, then mvn test). Every command in this course names its folder for this reason.

Why the layout? The two projects do different jobs. Katas are frozen exhibits, and the hub keeps changing. Keeping them as separate Maven projects means a change to the hub can never break a kata, and the other way round. Maven can build several projects at once from a parent POM (a "multi-module" build). We skip that on purpose: it would add machinery the course does not need. You will see that judgment again and again: do not add structure until a real pain asks for it.
