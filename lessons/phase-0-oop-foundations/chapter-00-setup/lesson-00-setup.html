1The pain

Before we talk about design, we need a good workshop. It must build our code the same way every time, on every computer. Here is what life looks like without one.

1.1 One file is easy

Imagine you write one small Java file, Main.java. You turn it into something the computer can run, by hand. Then you run it. It works. Easy.

# translate Main.java into Main.class, then run it
javac Main.java
java Main
Hello!

1.2 Then the project grows

Now a new request arrives: "add an automatic check that the code works." That check needs a library. A library is a bundle of ready-made code that someone else wrote so that others can use it. The library we need is called JUnit. (You will meet it properly in Section 4.) You try the same trick as before:

javac SmokeTest.java
SmokeTest.java:3: error: package org.junit.jupiter.api does not exist
import org.junit.jupiter.api.Test;
                            ^

The computer does not know where JUnit is. So now the jobs pile up:

  1. You find the library on the internet and download the right version.
  2. You tell the translator where you saved it.
  3. You find every test by hand and run each one.

Then a friend copies your code onto their computer. Their computer has a different Java version. It also has a different copy of the library. The code breaks for them, but not for you. Every developer has heard this sad sentence: "but it works on my machine."

1.3 The name of the pain, and the cure

This pain has a name: a manual, unrepeatable build. "Manual" means you do every step by hand. "Unrepeatable" means you cannot be sure it happens the same way twice.

The cure is three tools. We pin each one to an exact version. To pin a version means to lock it: we always use that one version, and it never changes by itself. Here are the three tools:

  • The JDK is Java's toolbox. It turns your code into a program and runs it.
  • Maven is a build tool. With one command, it downloads libraries and runs tests.
  • Git keeps the history of your files, so you never lose work.

This lesson installs all three and proves that they work.

Maybe your computer is already set up from an earlier run of this course. If so, skim Sections 2 and 3. Then run the checks in Section 4. The checks are the part that matters.

3The concepts explained

3.1 How Java runs: from your text to a running program

A computer cannot run the text you type. Someone must first translate it into a form the machine understands. This translating step is called compiling. The program that does it is called a compiler. Java's compiler is called javac.

Most compilers translate straight into the raw instructions of one kind of computer. Then the result runs only on that kind of computer. Java does something smarter. javac translates into a halfway language. It is not human text, and it is not raw machine instructions either. Java stores it in .class files. For example, javac Main.java produces Main.class. This halfway language is called bytecode.

Bytecode needs a program to run it. That program reads the bytecode. Then it carries out each instruction on the computer it is installed on. Windows has one, macOS has one, and Linux has one. So you compile once, and the same Main.class runs everywhere. A program that acts like a computer inside your computer is called a virtual machine. Java's one is called the JVM (Java Virtual Machine).

Here are the steps in order:

  1. You write Main.java. It is plain text.
  2. javac compiles it into Main.class. That file holds bytecode.
  3. The JVM reads Main.class and runs it, on any operating system.

3.2 The JDK: the whole toolbox

To build Java, you need the compiler. To run Java, you need the JVM. You also need Java's ready-made building blocks, for things like text, lists and files. Those ready-made blocks come with Java, and they are called the standard library. One download gives you all of it. That bundle is called the JDK (Java Development Kit).

The JDK has two halves:

  • The tools half builds programs. It holds javac, plus the java command that starts the JVM.
  • The runtime half runs programs. It holds the JVM plus the standard library. "Runtime" means "while the program is running."

People used to download the runtime half on its own, under the name JRE (Java Runtime Environment). You will still see that word. Today you simply install the JDK.

JDK, JRE, JVM: three names that sound alike. Think of boxes inside boxes. The JVM is the smallest box: it only runs bytecode. The JRE is the JVM plus the standard library. The JDK is the biggest box: the JRE plus the tools that build code. You install the biggest box, the JDK, and get all three.

3.3 Which Java version, and why we pin it

Java brings out a new version every six months. Most versions get fixes for only a short time. But every few years, one version gets fixes for many years. Teams can rely on that version safely. Such a version is called an LTS (Long-Term Support) release. We pin Java 21, an LTS release, for the whole course. Because we all use the same version, every prediction in these pages stays true for you.

Install it. Any JDK 21 build works. A popular free one is Eclipse Temurin 21 from adoptium.net. On Windows, the installer offers to set two settings, JAVA_HOME and the PATH. (Section 3.4 explains both.) Tick both boxes.

Next you need a terminal. A terminal is a window where you type commands as text, instead of clicking. On Windows it is usually PowerShell. Open a new terminal and check that Java is installed:

java -version
javac -version

3.4 PATH and JAVA_HOME: how your terminal finds Java

When you type java, how does the terminal know which program you mean? The answer starts with a few named settings. Your computer keeps them, and every program can read them. For example, one setting holds your user name. Another says where temporary files go. These named settings are called environment variables.

One environment variable holds a list of folders, in order. When you type a command, the terminal searches these folders one by one:

  1. It looks in the first folder for a program with that name.
  2. If it finds none, it looks in the second folder, and so on.
  3. It runs the first match it finds, and stops looking.

That list of folders is called the PATH. Suppose an old Java 17 folder comes before your Java 21 folder in the PATH. Then typing java runs Java 17.

Maven does not rely on the PATH alone. First, it looks for an environment variable that names one JDK folder directly, for example C:\Program Files\Eclipse Adoptium\jdk-21…. If that variable is set, Maven uses that JDK. If it is not set, Maven falls back to the java it finds on the PATH. That variable is called JAVA_HOME.

So the two settings can disagree. java -version can say 21 while Maven quietly compiles with 17. It can also happen the other way round. Try every combination below.

3.5 Maven: the foreman

You could do every job by hand. You could call javac for every file, download libraries yourself, and run each test yourself. That is the pain from Section 1. A program that does all of these jobs from one command is called a build tool. Ours is called Maven. One Maven command does four things:

  1. It downloads the libraries you asked for.
  2. It compiles your code.
  3. It runs your tests.
  4. It reports the result.

Maven uses a few words all the time. Here they are, one at a time:

  • Your project often needs a library, like JUnit for tests. You do not copy it in by hand. You write down its name and version, and Maven downloads it for you. A library your project needs is called a dependency.
  • Maven needs a work order for each project. The work order lists the project's name, its Java version, its dependencies, and its extra tools. That work order is one file, pom.xml. It is called the POM (Project Object Model).
  • Every published library needs a unique address, so Maven can fetch exactly the right one. The address has three parts: who owns it (groupId), its name (artifactId), and its version. For example: org.junit.jupiter : junit-jupiter : 5.14.4. These three parts are called the coordinates. The published thing they point to is called an artifact.
  • Maven itself only knows the order of the steps. Small add-on tools do the real work in each step. For example, one add-on runs the tests. These add-ons are called plugins. We pin three: the compiler plugin (built in), Surefire (runs tests), and exec (runs a main method).
  • Maven saves each downloaded artifact once, in a folder in your home folder: ~/.m2/repository. Every project reuses it after that. This folder is called the local repository. It is the reason only your first build is slow.

Install Maven (version 3.9.x) from maven.apache.org. Follow these steps:

  1. Unzip the download.
  2. Add its bin folder to your PATH. (bin is the folder that holds Maven's programs.)
  3. Open a new terminal, and check:
mvn -version

3.6 An IDE: where you will type

Plain text editors know nothing about Java. A smarter editor does more. It colours your code. It spots typing mistakes as you type. It suggests method names. It runs tests with a click. Such an editor is called an IDE (Integrated Development Environment). Pick one of these two:

  • IntelliJ IDEA Community Edition: free, and the smoothest for Java.
  • VS Code with the "Extension Pack for Java."

Every command in this course is a terminal command. So nothing depends on which IDE you choose.

3.7 Git and GitHub: the photo album and the safe

  • Some tools save the history of your files as a series of snapshots. Then you can always go back to an older one. Such a tool is called a version-control tool. Ours is Git.
  • The folder Git watches, together with its whole saved history, is called a repository (or repo).
  • One saved snapshot, with a short message saying what changed (for example, "lesson 00 – setup"), is called a commit.
  • GitHub is a website that keeps a copy of your repository online, so a broken laptop never loses your work. That online copy is called a remote. Sending your new commits up to it is called a push.

Install Git from git-scm.com. Check it with git --version (prediction: git version 2.xx.x). Then create a free GitHub account. On GitHub, create one empty repository named design-patterns-learning. Do not let GitHub add a README or a .gitignore file. We write those ourselves.

4.3 katas/pom.xml: read it slowly, it teaches how Maven thinks

The POM is written in XML. XML is a text format that wraps each piece of data in named tags. A tag opens with <name> and closes with </name>. For example, <version>1.0.0</version> means "the version is 1.0.0." Tags can sit inside other tags, like folders inside folders. Lines between <!-- and --> are comments: notes for humans that Maven skips.

Saved: katas/pom.xml

<?xml version="1.0" encoding="UTF-8"?>
<!-- The line above says "this is an XML file, stored as UTF-8 text". -->
<!-- This is the build file for the KATAS project: one tiny, frozen example -->
<!-- per pattern. Maven reads THIS file to know how to compile and test. -->

<!-- <project> wraps everything. The xmlns lines name the official POM -->
<!-- vocabulary, so Maven and your IDE can check every tag below is valid. -->
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">

    <!-- The version of the POM *language* (not of our project). Always 4.0.0. -->
    <modelVersion>4.0.0</modelVersion>

    <!-- The coordinates: the project's unique address in the Java world. -->
    <!-- groupId = who owns it (a reverse-domain-style name we chose). -->
    <groupId>com.katas</groupId>
    <!-- artifactId = this particular project's name. -->
    <artifactId>design-pattern-katas</artifactId>
    <!-- version = our own version number for this project. -->
    <version>1.0.0</version>
    <!-- packaging = bundle the compiled classes into one .jar file. -->
    <packaging>jar</packaging>

    <!-- Properties: named settings, reused below as ${name}. Pinning them -->
    <!-- here once means every lesson builds against the SAME versions. -->
    <properties>
        <!-- Compile the Java 21 language AND produce Java 21 bytecode. -->
        <maven.compiler.release>21</maven.compiler.release>
        <!-- Read source files as UTF-8 so special characters never corrupt. -->
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <!-- The one JUnit 5 version pinned for the whole course. -->
        <junit.version>5.14.4</junit.version>
        <!-- The class `mvn compile exec:java` runs when you name none. A -->
        <!-- property (not plugin config) so -Dexec.mainClass=... can override -->
        <!-- it: that is how each kata's own Main demo is picked later. -->
        <exec.mainClass>com.katas.Main</exec.mainClass>
    </properties>

    <!-- Dependencies: outside libraries Maven downloads for us. -->
    <dependencies>
        <!-- JUnit 5 ("Jupiter"), our testing library. This one artifact -->
        <!-- pulls in everything needed to write and run tests. -->
        <dependency>
            <!-- JUnit's owner name... -->
            <groupId>org.junit.jupiter</groupId>
            <!-- ...its project name... -->
            <artifactId>junit-jupiter</artifactId>
            <!-- ...and the pinned version, read from the property above. -->
            <version>${junit.version}</version>
            <!-- test scope: available to tests only, never shipped in the jar. -->
            <scope>test</scope>
        </dependency>
    </dependencies>

    <!-- Build settings: which plugins (Maven's add-on tools) to use. -->
    <build>
        <plugins>
            <!-- Surefire RUNS the tests during `mvn test`. A modern 3.x -->
            <!-- version is needed to find JUnit 5 tests reliably. -->
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
                <version>3.5.5</version>
            </plugin>
            <!-- The exec plugin powers `mvn compile exec:java`: it runs a -->
            <!-- class's main method with our compiled classes on hand. -->
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.6.1</version>
            </plugin>
        </plugins>
    </build>

</project>

Read from top to bottom, the POM answers four questions:

  1. Who am I? The coordinates.
  2. Which versions? The properties: Java 21 and JUnit 5.14.4, pinned once.
  3. What do I need? One dependency, JUnit. Its test scope means it helps the tests but never ships with the program.
  4. Which tools run the steps? Surefire and exec.

Saved: smarthome/pom.xml. It is the same file, with com.smarthome coordinates and com.smarthome.Main as its default main class. On purpose, JUnit is the only dependency in either project. We use no framework (a big library that runs your code for you and hides some of the work). So you see every pattern bare, with nothing hidden.

We pinned JUnit 5.14.4 and Surefire 3.5.5 at the course's first setup. We pinned exec-maven-plugin 3.6.1 new for this restart. If Maven says it cannot find that version, tell me what it says. Then we will pin a version your Maven can find.

4.4 The four Java files

Every Java program needs a starting point. That is a method the JVM knows to call first. (A method is a named block of code; Lesson 01 explains it fully.) You must spell it exactly public static void main(String[] args). Otherwise the JVM will not recognise it. This is the main method. The words public and static get their full story in Lesson 01 and later. For now, read them as "callable from outside" and "no object needed."

Saved: katas/src/main/java/com/katas/Main.java

// Declares the package (folder-path namespace) this class lives in. The folders
// on disk (com/katas) must match this line exactly, or Java will not find it.
package com.katas;

// A public class is one visible to code in other packages. The file name
// (Main.java) must match the class name (Main) exactly in Java.
public class Main {

    // main is the special method the Java runtime calls first when the program
    // starts. Its signature MUST be exactly this for the JVM to recognise it:
    // public (callable from outside), static (no object needed to call it),
    // void (returns nothing), named main, taking an array of String arguments.
    public static void main(String[] args) {
        // Print one line to the console so we can SEE the toolchain works:
        // if this text appears, Java compiled and ran our code successfully.
        System.out.println("Katas project is ready.");
    }
}

Saved: smarthome/src/main/java/com/smarthome/Main.java

// The package (namespace) for the Smart Home Hub's entry point. The folder
// path com/smarthome on disk must mirror this line exactly.
package com.smarthome;

// The application's top-level class. File name Main.java matches class Main.
public class Main {

    // The JVM's starting point: same required signature as any Java program.
    public static void main(String[] args) {
        // A friendly startup banner. Later lessons will replace this with real
        // hub behaviour (creating devices, running scenes). For now it simply
        // proves the Smart Home project compiles and runs.
        System.out.println("Smart Home Hub is starting up...");
    }
}

Now the tests. A test is a small piece of code that checks other code automatically. If something is wrong, you find out the moment you run it. A small check like this, for one piece of code, is called a unit test. JUnit is the library that finds your unit tests, runs them, and reports pass or fail. Two more words appear in the file below:

  • A tag stuck onto code is called an annotation. It starts with @. Tools read it, but Java itself ignores it. @Test tells JUnit "run this method as a test."
  • An assertion is a line inside a test that says what must be true. If it is not true, the test fails. For example, assertEquals(4, 2 + 2) fails if the two values differ.

Our first tests check nothing real. They only prove that the machinery works: the compiler, Maven, JUnit and Surefire. The name comes from electronics. You switch on a new device and check that no smoke comes out. A test like this is called a smoke test.

Saved: katas/src/test/java/com/katas/SmokeTest.java

// Same package as the code under test. Test sources live in src/test/java,
// but share the package name so tests can reach package-visible members.
package com.katas;

// Import the @Test annotation: the marker that tells JUnit "run this method
// as a test". An annotation is a tag attached to code that tools can read.
import org.junit.jupiter.api.Test;
// Import the assertion helper. assertEquals(expected, actual) fails the test
// if the two values are not equal. A "static import" lets us write the method
// name directly (assertEquals) instead of Assertions.assertEquals.
import static org.junit.jupiter.api.Assertions.assertEquals;

// A "smoke test" is the simplest possible test: it does not check real logic,
// it just confirms the build-and-test machinery itself is wired up correctly.
// (The name comes from switching on a device and checking no smoke comes out.)
public class SmokeTest {

    // @Test marks this method as one JUnit should execute. No return value; a
    // test passes if it finishes without an assertion throwing an error.
    @Test
    void toolchain_is_wired_up() {
        // Assert that 2 + 2 equals 4. This is trivially true, so the test
        // passes ONLY if Maven, JUnit, and the compiler are all working.
        assertEquals(4, 2 + 2);
    }
}

Saved: smarthome/src/test/java/com/smarthome/SmokeTest.java

The hub's smoke test is the same idea, using assertTrue(true): a condition that is always true. It passes the moment the machinery works.

4.5 What mvn test does, step by step

  1. You type mvn test inside the katas/ folder. Maven looks for pom.xml in the current folder. That is why the folder matters.
  2. Maven reads the POM and learns three things: Java 21, one dependency (JUnit 5.14.4), and two pinned plugins.
  3. For each library and plugin, Maven checks ~/.m2/repository. The very first time they are missing, so Maven downloads them and you see many Downloading… lines. Every later run finds them in the cache.
  4. The compiler plugin runs javac on everything under src/main/java. It writes bytecode (Main.class) into target/classes.
  5. It does the same for src/test/java, writing SmokeTest.class into target/test-classes. JUnit is available here because of its test scope.
  6. Surefire looks through the compiled test classes, finds every method marked @Test, and asks JUnit to run each one. toolchain_is_wired_up() runs: 2 + 2 is 4, so the assertion holds and the test passes.
  7. Surefire counts the results: 1 run, 0 failures, 0 errors, 0 skipped.
  8. Nothing failed, so Maven prints BUILD SUCCESS.

You run mvn test and it ends with BUILD SUCCESS, but the report says Tests run: 0. Is everything fine?

No. Zero tests ran, so nothing was checked. The green build looks fine, but it hides that. There are three usual causes:

  • The test file is in the wrong folder.
  • Its package line does not match its folders.
  • An old Surefire cannot see JUnit 5 tests.

Always read the Tests run: count, not just the last line.

5The two code homes, and the Smart Home Hub

This course keeps code in two homes. We do this on purpose, because the two homes do two different jobs.

5.1 The katas: small, frozen examples

A kata is a small practice exercise that you repeat until it feels natural. The word comes from martial arts. In this course, a kata is one tiny example for one pattern. It lives in its own package, for example com.katas.strategy. Each kata holds four things:

  1. The wrong-way version. It sits in a sub-package called naive. ("Naive" means a simple first try that does not see the problems coming.)
  2. The right-way version.
  3. A small main demo you can run.
  4. A test.

Once its lesson is done, a kata is frozen: we never edit it again. So you can always go back and see a pattern in its smallest, purest form.

5.2 The Smart Home Hub: one real, growing project

The Smart Home Hub is the opposite. It is one real application that grows lesson by lesson. Over the course, it will do all of this:

  • control lights, thermostats, locks, cameras and speakers;
  • react to sensors, such as a thermometer;
  • run scenes and schedules;
  • plug in devices made by other companies.

A pattern goes into the hub only when the hub really needs it. Today the hub is just one banner line. In Lesson 01 it gets its first real code: a Device contract and two devices.

We keep the wrong-way code next to the right-way code to help you learn. In a real project you delete the naive version once you have improved it. Git's history already remembers it.

6In the wild

The three-part address you just wrote is how the whole Java world shares code. Many libraries are open source: their code is public, and anyone may use it for free. There is a free public store of open-source Java libraries called Maven Central. Maven fetches every library in it by exactly these coordinates. For example, our POM used org.junit.jupiter : junit-jupiter : 5.14.4.

Gradle, the other big Java build tool, reads the very same coordinates from the very same store. So once you learn coordinates, you can pull any open-source Java library into any project.

On a real team, nobody trusts "it passed on my laptop." Instead, every push to GitHub starts a clean server. The server gets the code and runs the same mvn test. This setup is called continuous integration (CI). Pinned versions make that server's result match yours. That is how professionals cure "works on my machine." It rests on exactly what you set up today.

7Gotchas and common mistakes

  • 'mvn' is not recognized / command not found. Two possible causes. The tool's bin folder is not on the PATH. Or you opened the terminal before you changed the PATH. PATH changes only reach terminals opened afterwards, so open a new one.
  • release version 21 not supported. Maven is using an older JDK. Usually JAVA_HOME points at it. Try the simulation in 3.4 again, then fix JAVA_HOME.
  • there is no POM in this directory. You ran Maven in the wrong folder. Each project (katas/, smarthome/) has its own POM. Maven only looks in the current folder. The repo's top folder has no POM.
  • PowerShell and -D options. Later lessons run a chosen kata with -Dexec.mainClass=com.katas.x.Main. PowerShell splits that text at the dot, unless you wrap it in quotes. So always write mvn compile exec:java "-Dexec.mainClass=com.katas.x.Main". The quotes do no harm in other terminals.
  • Committing build output. Does target/ ever appear in git status? Then your .gitignore is missing or has the wrong name. Compiled bytecode never belongs in Git.

8Key takeaways

  • The JDK builds, the JVM runs, and Maven drives the whole build. javac turns your code into bytecode. The JVM runs that bytecode on any operating system. Maven does every step from one pom.xml.
  • We pin every version on purpose: Java 21 LTS, JUnit 5.14.4, Surefire 3.5.5, exec 3.6.1. This keeps the code and its predicted output the same on every computer and in every lesson.
  • The PATH decides which java your terminal runs. JAVA_HOME, when it is set, decides which JDK Maven uses. Both must point at JDK 21.
  • A smoke test checks the machinery, not the logic. A passing test on day one means the compiler, Maven, JUnit and Surefire all work. Always read the Tests run: count.
  • The course has two code homes. Frozen katas show each pattern alone. The growing Smart Home Hub shows patterns working together. .gitignore keeps the course-control files on your computer only, so git add . is always safe.

11Key words

Compiler / compiling
The program that translates the code you type into a form the machine can run. Java's compiler is javac.
Bytecode
Java's halfway language, stored in .class files. It is not human text and not raw machine code; the JVM reads it.
JVM
Java Virtual Machine: the program that runs bytecode. Each operating system has its own.
Standard library
Java's ready-made building blocks (text, lists, files…) that come with every JDK.
JDK
Java Development Kit: the whole toolbox. Tools that build Java, plus the runtime that runs it.
JRE
Java Runtime Environment: the old name for the runtime half alone (JVM + standard library).
LTS
Long-Term Support: a Java version that gets fixes for many years. Java 21 is one.
Pin (a version)
Lock a tool to one exact version, so it never changes by itself.
Terminal
A window where you type commands as text. On Windows, usually PowerShell.
Environment variable
A named setting your computer keeps, which any program can read.
PATH
The list of folders the terminal searches, in order, when you type a command. The first match wins.
JAVA_HOME
A setting that names one JDK folder. Maven uses it when it is set.
Library
A bundle of ready-made code that someone wrote for others to use.
Build tool
A program that downloads libraries, compiles code and runs tests from one command.
Maven
The build tool this course uses. It follows the work order in pom.xml.
Dependency
A library your project needs. You list it in the POM, and Maven downloads it.
POM
Project Object Model: the file pom.xml, Maven's work order for one project.
XML
A text format that wraps each piece of data in named tags, like <version>1.0.0</version>.
Coordinates
A library's three-part address: owner (groupId), name (artifactId), version.
Artifact
One published, versioned thing (usually a library) found by its coordinates.
Plugin
A small add-on tool that does the real work of one Maven step.
Surefire
The Maven plugin that finds and runs the tests.
Local repository
The folder ~/.m2/repository, where Maven keeps every download for reuse.
IDE
Integrated Development Environment: a code editor that understands Java.
Version control / Git
Saving the history of your files as snapshots, so you can go back. Git is our tool for it.
Repository (repo)
The folder Git watches, together with its whole saved history.
Commit
One saved snapshot in Git, with a message about what changed.
Remote / push
A copy of your repo on another computer (here, GitHub). Pushing sends your new commits there.
.gitignore
The file that lists what Git must never save.
.gitattributes
The file that makes Git store one line-ending style, so Windows and Linux agree.
Package
The name a Java class lives under, like com.katas. It matches the class's folders.
main method
The exact starting point the JVM calls first: public static void main(String[] args).
Unit test
A small automatic check that one piece of code does what it should.
JUnit
The library that finds and runs unit tests and reports pass or fail.
Annotation
A tag that starts with @ and is stuck onto code for tools to read, like @Test.
Assertion
A line in a test that says what must be true. If it is false, the test fails.
Smoke test
The simplest test. It proves the tools work, not any real logic.
Kata
A small practice exercise. Here: one tiny, frozen example per pattern.
Open source / Maven Central
Code that is public and free to use. Maven Central is the free public store of such Java libraries.
Continuous integration (CI)
A clean server that runs the same build and tests on every push.
