3The story so far

  1. Lesson 00: the hub was one banner line and a smoke test, proving the workshop works.
  2. Lesson 01: it gained a Device contract and two devices. One loop switched everything on without knowing any concrete class, and the thermostat refused bad targets at the door.
  3. Lesson 02: the two devices had copied the same fields and four methods, so that code moved into an abstract parent. We also fixed a trap our own constructor had been hiding. Behaviour was unchanged, and the untouched tests proved it: our first refactoring.
  4. Lesson 03: a new requirement, an activity log for every device. Inheritance would have meant a Logging* subclass per device. Instead, one wrapper logs any device. It is chosen when the hub is put together, and no device class changed.
  5. Lesson 04: no code changed. We drew the hub, traced its main call, and measured it. Every class passed the cohesion test except one: Main keeps piling up jobs. That is where the next phase begins.

6Ideas that come back

  • "Program to an interface" becomes the Dependency Inversion Principle (Lesson 09). It is also the reason almost every pattern diagram has a violet contract box at its centre.
  • Cohesion becomes a rule, the Single Responsibility Principle (Lesson 05), starting with the hub's Main.
  • The wrapper ("implements X, holds an X") returns as a named structural pattern in Lesson 19. Its cousins come in Lessons 18 and 22. You tell them apart by their purpose, not their shape.
  • "Is-a" safety, meaning when a subclass can truly stand in for its parent, becomes the Liskov Substitution Principle (Lesson 07).
  • The parent calling a child's filled-in step (Animal.introduce() calling speak(); AbstractList) returns as a named behavioral pattern in Lesson 26.

7Self-check

What makes a field-plus-setter pair "encapsulation in name only"?

A setter that stores any value without checking the invariant is just a public field with extra steps. Encapsulation means every path to the data checks the rule, including the constructor (Lesson 01).

Animal a = new Dog("Rex"); Which picks the method for a.speak(), and which picks it for vet.examine(a)?

a.speak() is overriding. The JVM decides at run time, from the actual object (Dog). vet.examine(a) is overloading. The compiler decides from the declared type (Animal), so the general check-up runs (Lesson 02).

Why did the inheritance-based counter double-count, but the composed one did not?

With extends there is one object. So the internal add() calls in Playlist.addAll land in the child's override. With composition there are two objects. So the inner playlist's calls stay inside it (Lesson 03).

Give the one-sentence test for cohesion, and the cheapest sign of loose coupling in a sequence diagram.

Cohesion: describe the class in one sentence without "and." Coupling: few arrows leave each lifeline. The ones that do point at contracts or parameters (Lesson 04).

The hub kept AbstractDevice even after "favor composition." Why is that not a contradiction?

"Favor" is not "always." AbstractDevice is a true is-a. It has a small, stable core that we own and designed for extension. The optional, combinable feature (logging) is the part that was composed. Replacing working inheritance with forwarding code would cure no pain. That would be needless complexity.

8Boss challenge

A garden-watering module arrived from another team. It "works." First, find every problem, using this chapter's words. Then predict what new Garden().water() prints today. Then redesign it to meet three goals:

  • The flow rate can never be invalid.
  • Logging can be added to any sprinkler without a subclass.
  • A test can check what was logged without reading the console.

public class Sprinkler {
    public int litresPerMinute;
    public boolean running;
    public void start() { running = true; }
    public void startZones(int zones) { for (int i = 0; i < zones; i++) { start(); } }
}

public class LoggingSprinkler extends Sprinkler {
    @Override public void start() { System.out.println("Sprinkler started"); super.start(); }

    }
}

public class Garden {
    private final LoggingSprinkler sprinkler = new LoggingSprinkler();
    public void water() { sprinkler.litresPerMinute = -5; sprinkler.startZones(2); }
}

The two "Sprinkler started" lines exist only by accident. Sprinkler.startZones happens to call start() (self-use). Dynamic dispatch then sends those calls into the child's override. If the parent author changes that loop, the log changes too.

A redesign

// The contract: what Garden needs from any sprinkler.
public interface Sprinkler { void start(); boolean isRunning(); }

// The contract for "write a log line", so tests can record instead of print.
public interface Log { void write(String line); }

// The real sprinkler: data private, invariant guarded from birth.
public class GardenSprinkler implements Sprinkler {
    private final int litresPerMinute;
    private boolean running;
    public GardenSprinkler(int litresPerMinute) {
        if (litresPerMinute <= 0) { throw new IllegalArgumentException("Flow must be positive: " + litresPerMinute); }
        this.litresPerMinute = litresPerMinute;
    }
    @Override public void start() { running = true; }
    @Override public boolean isRunning() { return running; }
}

// Logging by composition: IS a Sprinkler, HAS a Sprinkler and a Log.
public class LoggedSprinkler implements Sprinkler {
    private final Sprinkler inner;
    private final Log log;
    public LoggedSprinkler(Sprinkler inner, Log log) { this.inner = inner; this.log = log; }
    @Override public void start() { inner.start(); log.write("Sprinkler started"); }
    @Override public boolean isRunning() { return inner.isRunning(); }
}

// Garden knows only the contract; the caller decides which sprinklers.
public class Garden {
    private final List<Sprinkler> zones;
    public Garden(List<Sprinkler> zones) { this.zones = List.copyOf(zones); }
    public void water() { for (Sprinkler zone : zones) { zone.start(); } }
}

Notice that "zones" stopped being a method on the sprinkler. A garden has several sprinklers, one per zone. That is a cohesion fix: the sprinkler sprinkles, and the garden organises. With no startZones calling start, there is no self-use for anything to depend on.

           «interface» Sprinkler  <- - - - - - - - - - - - - - - - -.
             ^                ^                                   :
   implements:                :implements                          :
             :                :                                   :
     GardenSprinkler     LoggedSprinkler ---inner---> Sprinkler    :
                              |                                    :
                              '---log---> «interface» Log <- - ConsoleLog / RecordingLog
   Garden <>---zones *---> Sprinkler        (aggregation: zones are handed in)

Assembly, for example in a main: new Garden(List.of(new LoggedSprinkler(new GardenSprinkler(12), consoleLog), new LoggedSprinkler(new GardenSprinkler(8), consoleLog))).water();

One line per zone that actually started. That stays true however the classes are refactored inside. A test passes a RecordingLog (like RecordingNotifier in Lesson 04) and asserts the list of lines. new GardenSprinkler(-5) now throws, so the invariant can no longer be broken from outside. If you code this up in a scratch package, run it and compare with the predictions. The machine is the judge.
