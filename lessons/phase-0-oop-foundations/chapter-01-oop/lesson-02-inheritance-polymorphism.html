Inheritance and Polymorphism

Write shared code once in a parent class, and let each child fill in only what differs. Then watch exactly how the JVM decides which method a call really runs.

Kata package: com.katas.inheritance (wrong way in com.katas.inheritance.naive).
Smart Home Hub: created devices/AbstractDevice.java, devices/AbstractDeviceTest.java; modified devices/Light.java, devices/Thermostat.java. Main and DeviceTest unchanged.
Prerequisites: Lesson 01 — Objects, Encapsulation, and Interfaces.

1The pain

An interface shares a promise. It cannot share code. Watch what happens when two classes need the same code.

We write a Dog and a Cat. Each needs a name, a constructor, a getter, and an introduce() method. So we write Dog, copy it, rename it Cat, and change one word:

public class Dog {                              public class Cat {
    private final String name;                   private final String name;
    public Dog(String name) { … }              public Cat(String name) { … }
    public String getName() { … }             public String getName() { … }
    public String introduce() {               public String introduce() {
        return "I am " + name                       return "I am " + name
             + " and I say Woof";                      + " and I say Meow";
    }                                              }
}                                              }

Now the requirement changes: "introductions must also say the animal's age." You find Dog.introduce() and fix it. Did you remember Cat? What about Parrot, Hamster and the eight others copied since? Every copy must be found and edited in exactly the same way. Miss one, and the program quietly disagrees with itself.

Predicted symptom, after a fix applied to only one copy

I am Rex, age 3, and I say Woof
I am Tom and I say Meow          <- the copy nobody remembered

The pain, named: duplicated code. One change means editing many places, which is called shotgun surgery. And our own hub already has it: Light and Thermostat from Lesson 01 both carry an identical name field, on field, and four identical methods.

2Real-world analogy

A restaurant chain. Head office writes one operations manual: how to greet guests, take orders, handle payment. Every branch follows it without rewriting it. But one page says "local menu: each branch must write its own." A branch may also replace a standard page with its own version. When you phone the chain's number, whichever branch picks up handles your call in its own way.

And one more desk: a front office with two forms, "General enquiry" and "Dog enquiry." The clerk picks the form by reading the label on the envelope, before opening it. A dog in an envelope labelled "animal" gets the general form.

3The concepts explained

3.1 Inheritance: write it once in a parent

Dogs and cats share a name and an introduction; only the sound differs. So we write the shared parts once, in a class called Animal. Then Dog says "I am an Animal, plus my sound." Writing class Dog extends Animal makes every Dog object automatically have all of Animal's fields and methods, as if they were written inside Dog. A class receiving everything from another class this way is called inheritance.

The class that gives is the superclass (or parent). The class that receives is the subclass (or child). The test for whether inheritance makes sense is one sentence: "a Dog is an Animal." If that sentence sounds true in plain English, the relationship is called is-a, and inheritance may fit. "A Thermostat is a Light" sounds wrong, so Thermostat must never extend Light, even though both switch on and off.

Two details about building a child object:

  • A Dog object contains an Animal part, and that part must be set up first. The child's constructor does this by calling the parent's constructor on its first line, with super(name). The word super means "my parent's version."
  • Animal's name field is private, so even Dog's own code cannot touch it directly. It uses getName() like everybody else. Encapsulation holds even inside a family. If a parent wants something usable by its children but not by the outside world, it marks it with a third access keyword. That keyword means "this class, its subclasses, and its package," and it is called protected. Animal's constructor is protected: only subclasses need to call it.

3.2 Abstract classes: a parent with a blank to fill in

Animal.introduce() needs a sound, but "an animal" in general has no sound. We want to say: "every animal has a speak() method, and every real kind of animal must write its own." Marking a method abstract gives it a signature and no body: public abstract String speak();. That is an abstract method. A class holding one is incomplete, so it must itself be marked abstract, and new Animal("x") will not compile. A class that cannot be built directly, and exists only to be extended, is called an abstract class. Any subclass that does not fill in every blank will not compile either.

Since Java 8 an interface can carry a method with a body, marked default. That blurs the "promise only" row a little. Interfaces still cannot hold per-object fields or constructors, though, so the table's main lines stand. We will meet default methods properly when a pattern needs them.

3.3 Every class has a parent: Object

A class that names no parent still has one. Java gives every class a silent extends Object. Object is the root of every class tree, and it hands everyone a few methods. The one you will meet first turns any object into text. System.out.println(x) calls it automatically: it is toString(). Its default answer is the class name, an @, and a hex number, like Cat@1b6d3586. That is why classes often supply their own.

3.4 Overriding: a child replaces a parent's method

A subclass can write a method with exactly the same name and parameters as one it inherited. For its objects, that new version replaces the parent's. Writing a same-signature method in a subclass to replace the inherited one is called overriding. You met @Override in Lesson 01, fulfilling an interface's promise; it works the same here. Mark every override with it, so a misspelling becomes a compile error instead of a silent new method (Section 7). Inside an override, super.speak() still reaches the parent's version. Puppy uses this: "Yip (learning to " + super.speak() + ")".

3.5 Polymorphism, traced: how the JVM picks the method

Lesson 01 promised to show how one call runs different code. Take Animal animal = new Puppy("Bit"); animal.introduce();. Two different types are in play, and keeping them apart is the whole trick:

  • The type written on the variable, here Animal. It is fixed when you write the code and is all the compiler can see. It is called the declared type (or static type).
  • The class the object was really built from, here Puppy. It is known only while the program runs. It is called the actual type (or runtime type).

A variable of a parent type can hold any child object, because a Puppy is an Animal. The opposite fails: Dog d = new Cat("Tom") does not compile.

  1. Compile time. The compiler looks only at the declared type. Does Animal have an introduce()? Yes, so the line compiles. (If you called a method that only Puppy has, it would not compile, because the compiler cannot know the object is a Puppy.)
  2. Run time. The JVM asks the object what it really is: a Puppy. It looks for introduce() starting at Puppy. It is not there. Next is Dog: not there. Next is Animal: found. It runs Animal.introduce().
  3. Inside it, speak() really means this.speak(), and this is still the Puppy. So the search starts again at Puppy, where speak() is found. Code written in the parent ends up running the child's method.
  4. Puppy's speak() calls super.speak(). super starts the search at the parent of the class where this code is written: Dog. That gives "Woof".
  5. The results flow back: "I am Bit and I say Yip (learning to Woof)".

Choosing which method body runs from the object's actual type, while the program runs, is called dynamic dispatch. It is the machinery under polymorphism.

The "walk up the chain" is the honest model of the result. For speed, the real JVM builds a lookup table per class ahead of time (often called a vtable), so it does not literally search on every call. You never see the table; you only see that the result always matches the walk.

3.6 Overloading: same name, different parameters, chosen early

A class may also hold two methods with the same name but different parameter types. Our Vet has examine(Animal a) and examine(Dog d). Several same-named methods in one class, told apart by their parameters, are called overloading. The catch: the compiler picks between overloads, using only the declared types of the arguments. The actual object is never consulted.

Dog rex = new Dog("Rex");
Animal sameRex = rex;              // the very same object
vet.examine(rex);       // "Dog check-up for Rex"     (declared Dog)
vet.examine(sameRex);   // "General check-up for Rex" (declared Animal!)

3.7 What inheritance silently costs

Inheritance removed the duplication in a few lines. It also quietly signed a long contract:

  • Tight coupling. The child depends on the parent's insides, not just its promises. Change how the parent's methods call each other, and a child can break without being touched. This is so common it has a name, the fragile base class problem, and Lesson 03 breaks one in front of you.
  • One parent only. Java allows extends just once. A device that is "both a Recorder and a Camera" cannot extend both.
  • Fixed when you write the code. A Light is a Light forever. You cannot swap in different behaviour while the program runs.
  • Everything comes along. The child inherits every public method, wanted or not. A child that must refuse some of them is a warning sign; Lesson 07 names it.
  • Deep trees are hard to read. To understand Puppy.introduce() you open three files. Every extra level adds another.

None of these makes inheritance wrong. It is the right tool when the is-a sentence is true, the shared code really is shared, and you control both parent and child. It just is not free. Lesson 03 shows the alternative that avoids most of these costs.

Saved: katas/src/main/java/com/katas/inheritance/Animal.java

// The RIGHT-WAY version: the shared parts written once, in a parent class.
package com.katas.inheritance;

// abstract: Animal is an incomplete class. It holds everything every animal
// shares, but it cannot be built on its own (new Animal(...) will not
// compile), because it does not know what sound to make.
public abstract class Animal {

    // Written ONCE here; every subclass object carries its own copy of it.
    // private: even subclasses must use getName() to read it.
    private final String name;

    // protected: callable from subclasses (and this package), not from the
    // outside world. Only a subclass constructor, via super(name), uses it.
    protected Animal(String name) {
        // Store the name for whichever animal is being built.
        this.name = name;
    }

    // Shared behaviour: every animal reports its name the same way.
    public String getName() {
        // Hand back the private name.
        return name;
    }

    // Shared behaviour that DEPENDS on a part each subclass supplies. When it
    // calls speak(), the JVM runs the speak() of the ACTUAL object (a Dog,
    // a Cat, a Puppy), even though this code lives in Animal.
    public String introduce() {
        // One introduction, written once, for every kind of animal.
        return "I am " + name + " and I say " + speak();
    }

    // abstract method: a promise with no body. Every concrete subclass MUST
    // override it, or that subclass will not compile.
    public abstract String speak();

    // Every Java class silently extends Object, which has a toString() that
    // println uses. We override it so printing an animal shows something
    // readable instead of the default "ClassName@hexnumber".
    @Override
    public String toString() {
        // getClass().getSimpleName() is the ACTUAL class's short name, so a
        // Puppy prints as "Puppy Bit" even though this code lives in Animal.
        return getClass().getSimpleName() + " " + name;
    }
}

Saved: katas/src/main/java/com/katas/inheritance/Dog.java

// A concrete animal: it fills in the one missing piece.
package com.katas.inheritance;

// "extends Animal": a Dog IS an Animal. It inherits the name field,
// getName(), introduce() and toString(), and supplies only what differs.
public class Dog extends Animal {

    // A subclass constructor must first build the Animal part of itself.
    public Dog(String name) {
        // super(name) runs Animal's constructor. It must be the first line;
        // without it this would not compile, because Animal has no
        // constructor that takes no arguments.
        super(name);
    }

    // Overrides Animal's abstract speak(): this is the dog-specific part.
    @Override
    public String speak() {
        // The only thing a Dog needs to say for itself.
        return "Woof";
    }
}

// A third level: Puppy extends Dog, which extends Animal.
package com.katas.inheritance;

// A Puppy IS a Dog (and therefore also an Animal). It exists to show the
// JVM's method lookup walking up more than one level, and super.speak().
public class Puppy extends Dog {

    // Build the Dog part (which in turn builds the Animal part).
    public Puppy(String name) {
        // Calls Dog's constructor, which calls Animal's.
        super(name);
    }

    // Overrides Dog's speak(). A Puppy's speak() replaces Dog's for Puppy
    // objects, but can still reach the parent version with super.speak().
    @Override
    public String speak() {
        // super.speak() runs DOG's speak(), giving "Woof".
        return "Yip (learning to " + super.speak() + ")";
    }
}

Saved: katas/src/main/java/com/katas/inheritance/Vet.java

// Demonstrates OVERLOADING, and the classic trap that comes with it.
package com.katas.inheritance;

// A vet with two methods of the SAME name but DIFFERENT parameter types.
// Which one runs is decided by the COMPILER, from the declared type of the
// argument, not by the JVM from the actual object.
public class Vet {

    // Version 1: accepts any Animal.
    public String examine(Animal animal) {
        // The general check-up.
        return "General check-up for " + animal.getName();
    }

    // Version 2: same name, but a more specific parameter type (Dog).
    public String examine(Dog dog) {
        // The dog-specific check-up.
        return "Dog check-up for " + dog.getName();
    }
}

Saved: katas/src/main/java/com/katas/inheritance/Main.java

// The runnable demo for Lesson 02's kata.
package com.katas.inheritance;

// Shows overriding (decided at run time by the actual object) and then
// overloading (decided at compile time by the declared type).
public class Main {

    // The JVM starts here when you run this class.
    public static void main(String[] args) {
        // PART 1 - polymorphism through a parent class. The array's declared
        // element type is Animal; the actual objects are three different classes.
        Animal[] animals = { new Dog("Rex"), new Cat("Tom"), new Puppy("Bit") };
        // One loop, one call site, three behaviours.
        for (Animal animal : animals) {
            // introduce() lives only in Animal, but its speak() call runs the
            // ACTUAL object's speak(): Dog's, Cat's, then Puppy's.
            System.out.println(animal.introduce());
        }
        // println calls toString(); Animal's override uses the actual class name.
        System.out.println(animals[2]);

        // PART 2 - overloading. ONE dog object, referred to by two variables
        // with two different DECLARED types.
        Vet vet = new Vet();
        // Declared type Dog.
        Dog rex = new Dog("Rex");
        // Declared type Animal, but the very same object (a Dog is an Animal).
        Animal sameRex = rex;
        // The compiler sees a Dog argument, so it picks examine(Dog).
        System.out.println(vet.examine(rex));
        // The compiler sees an Animal argument, so it picks examine(Animal),
        // even though the object is a Dog. THIS is the classic trap.
        System.out.println(vet.examine(sameRex));
    }
}

What happens when it runs

  1. Three objects are built. Each child constructor calls super(name) first, so every object's Animal part gets its name. Puppy("Bit") goes Puppy → Dog → Animal.
  2. Pass 1: animal is the Dog. introduce() is found in Animal; inside it, speak() is found in Dog, giving I am Rex and I say Woof.
  3. Pass 2: the Cat. Same Animal code, Cat's speak(), giving I am Tom and I say Meow.
  4. Pass 3: the Puppy. Same Animal code; speak() is found in Puppy, which calls super.speak() in Dog. The result is I am Bit and I say Yip (learning to Woof).
  5. println(animals[2]) calls toString(). It is found in Animal, where getClass().getSimpleName() asks the object its real class: Puppy Bit.
  6. vet.examine(rex): the argument's declared type is Dog, so the compiler already chose examine(Dog), giving Dog check-up for Rex.
  7. vet.examine(sameRex): same object, declared Animal, so the compiler chose examine(Animal), giving General check-up for Rex.

5Applied to the Smart Home Hub

The hub has the exact pain from Section 1. Light and Thermostat each carry their own name and on fields and identical getName/turnOn/turnOff/isOn methods. With locks, cameras and speakers on the way, that is six-plus copies waiting to drift apart. "A light is a device" is true, and we control every class, so an abstract parent genuinely fits.

One new word first. We are about to change how the hub's code is arranged without changing what it does: same output, same test results. Improving a program's internal structure while keeping its behaviour exactly the same is called refactoring. The tests are what make it safe. DeviceTest from Lesson 01 is not edited at all, and it must still pass. That is the proof that behaviour did not change.

Saved: smarthome/src/main/java/com/smarthome/devices/AbstractDevice.java

// Shared device code lives beside the Device contract it partly fulfils.
package com.smarthome.devices;

// The parts EVERY device had copied (a name, an on/off state, and the four
// methods around them), written once. abstract: it cannot be built on its
// own, because it does not know how to describe itself; status() is left
// for each concrete device to supply.
public abstract class AbstractDevice implements Device {

    // The device's name, set once. private: subclasses read it via getName().
    private final String name;

    // Whether the device is on. Starts false for every device.
    private boolean on;

    // protected: only subclasses (and this package) can call it, through
    // super(name). Outside code cannot build an "abstract device".
    protected AbstractDevice(String name) {
        // Store the name for whichever device is being built.
        this.name = name;
    }

    // Fulfils Device.getName() once, for every device.
    @Override
    public String getName() {
        // Hand back the private name.
        return name;
    }

    // Fulfils Device.turnOn() once, for every device.
    @Override
    public void turnOn() {
        // Remember that the device is on.
        on = true;
    }

    // Fulfils Device.turnOff() once, for every device.
    @Override
    public void turnOff() {
        // Remember that the device is off.
        on = false;
    }

    // Fulfils Device.isOn() once, for every device.
    @Override
    public boolean isOn() {
        // Report the current state.
        return on;
    }

    // status() is deliberately NOT written here. Because this class is
    // abstract, it may leave a Device method unfulfilled; every concrete
    // subclass is then forced by the compiler to supply its own.
}

Saved: smarthome/src/main/java/com/smarthome/devices/Light.java (modified)

// Same package as the Device contract and its shared parent.
package com.smarthome.devices;

// The simplest device. "extends AbstractDevice": a Light IS an
// AbstractDevice, so it inherits the name, the on/off state, and
// getName/turnOn/turnOff/isOn. It still IS a Device too, through its parent.
public class Light extends AbstractDevice {

    // Build a light with its name.
    public Light(String name) {
        // Hand the name to AbstractDevice's constructor, which stores it.
        super(name);
    }

    // The one thing a light must say for itself.
    @Override
    public String status() {
        // Inherited getName() and isOn() replace the old private fields;
        // e.g. "Living Room Light: ON".
        return getName() + ": " + (isOn() ? "ON" : "OFF");
    }
}

Saved: smarthome/src/main/java/com/smarthome/devices/Thermostat.java (modified)

Thermostat now extends AbstractDevice, drops its own name/on fields and the four shared methods, and builds its status from getName() and isOn(). It also fixes a trap that was hiding in our Lesson 01 code. The constructor used to call the public setTargetCelsius(...). Now that classes have children, a subclass could override that method, and the override would run before the subclass's own fields were set up (Section 7). So the rule moves into a private static helper that no subclass can override, and both doors call it:

    public Thermostat(String name, int targetCelsius) {
        // Build the AbstractDevice part first (name, on/off state).
        super(name);
        // Use the PRIVATE check, not the public setter: a constructor should
        // never call a method a subclass could override (see Lesson 02).
        this.targetCelsius = checkedTarget(targetCelsius);
    }

    // Change the target, but only to a sensible value.
    public void setTargetCelsius(int targetCelsius) {
        // The same single rule as the constructor uses.
        this.targetCelsius = checkedTarget(targetCelsius);
    }

    // The invariant, written once. private and static: it cannot be
    // overridden, and it needs no object, so it is safe to call anywhere,
    // including from the constructor.
    private static int checkedTarget(int targetCelsius) {
        // Refuse anything outside the allowed range...
        if (targetCelsius < MIN_CELSIUS || targetCelsius > MAX_CELSIUS) {
            // ...loudly, naming the bad value and the allowed range.
            throw new IllegalArgumentException("Target must be " + MIN_CELSIUS + "-" + MAX_CELSIUS
                    + "C, got " + targetCelsius);
        }
        // The value passed the check, so hand it back to be stored.
        return targetCelsius;
    }

    // The one Device method a thermostat must supply itself.
    @Override
    public String status() {
        // When on, say what it is aiming for; when off, just say OFF.
        return isOn() ? getName() + ": regulating to " + targetCelsius + "C" : getName() + ": OFF";
    }

// Same package as the device classes under test.
package com.smarthome.devices;

// The @Test marker.
import org.junit.jupiter.api.Test;

// Equality check.
import static org.junit.jupiter.api.Assertions.assertEquals;
// Fails unless the condition is false.
import static org.junit.jupiter.api.Assertions.assertFalse;
// Fails unless the condition is true.
import static org.junit.jupiter.api.Assertions.assertTrue;

// Proves the shared parent works for every subclass, and that calls through
// the parent type still run each subclass's own status().
class AbstractDeviceTest {

    // The inherited switching code behaves identically for every subclass.
    @Test
    void inheritedSwitchingWorksForEverySubclass() {
        // Two different subclasses, held through the shared parent type.
        AbstractDevice[] devices = { new Light("Hall Light"), new Thermostat("Hall", 21) };
        // Every device must run the SAME inherited code...
        for (AbstractDevice device : devices) {
            // ...on...
            device.turnOn();
            assertTrue(device.isOn());
            // ...and off again.
            device.turnOff();
            assertFalse(device.isOn());
        }
    }

    // Declared as the parent, the call still runs the child's override.
    @Test
    void callThroughTheParentTypeRunsTheSubclassStatus() {
        // Declared type AbstractDevice; actual object Thermostat.
        AbstractDevice device = new Thermostat("Hall", 21);
        // Inherited turnOn() from the parent...
        device.turnOn();
        // ...then Thermostat's own status(), chosen at run time.
        assertEquals("Hall: regulating to 21C", device.status());
    }
}

What this adds: a new device now only needs a constructor and a status(). The switching code exists once, so a fix to it reaches every device. Clients like Main notice nothing, because they never depended on how devices were built, only on the Device contract. That is Lesson 01's habit paying off.

  1. new Light("Living Room Light") runs Light's constructor, whose first line super(name) runs AbstractDevice's constructor and stores the name. on starts false.
  2. new Thermostat("Hall Thermostat", 21) runs super(name), then checkedTarget(21). 21 is within 5–30, so it is returned and stored.
  3. Loop pass one: device.turnOn() on the Light. Light defines no turnOn(), so the lookup reaches AbstractDevice and runs it. device.status() is found in Light: Living Room Light: ON.
  4. Pass two: the same inherited turnOn(), then Thermostat's own status(): Hall Thermostat: regulating to 21C.

6In the wild

The JDK uses exactly the hub's shape for its own lists. java.util.List is an interface with dozens of methods. java.util.AbstractList is an abstract class that implements almost all of them, including contains, indexOf, looping and more, in terms of just two abstract methods: get(int index) and size(). To make your own read-only list you extend AbstractList, fill in those two, and inherit everything else. That is Device → AbstractDevice → Light, at JDK scale. (The parent's code calling the child's filled-in steps is itself a famous pattern. It gets its own name in the Template Method lesson.)

And every class you have written already uses inheritance: each one silently extends Object. That is why println can call toString() on anything.

"What is the difference between overloading and overriding?" is one of the most common Java interview questions. The answer that impresses is the when: overloading is resolved by the compiler from declared types, and overriding is resolved by the JVM from the actual object. The Vet trap is the example to give.

7Gotchas and common mistakes

  • Overloads are chosen by the declared type. vet.examine(sameRex) runs the Animal version even though the object is a Dog (Section 3.6). If behaviour must depend on the actual object, use overriding, not overloading.
  • A misspelled override silently becomes a new method. Write public String tostring() (small s) without @Override. It compiles, nobody calls it, and println(cat) prints something like Cat@1b6d3586 (the number differs each run). With @Override, the compiler refuses: method does not override or implement a method from a supertype. Always write @Override.
  • Calling an overridable method from a constructor. The parent's constructor runs before the child's fields are set. If it calls a method the child overrides, the child's version runs against half-built fields: null text, zero numbers. Our Lesson 01 Thermostat did this; Section 5 fixed it with a private helper. In constructors, only call private, static, or final methods.
  • static methods and fields are not dispatched dynamically. Only ordinary methods take part in the actual-type lookup. A static method with the same signature in a child hides the parent's, and the declared type decides which one runs. So do not expect polymorphism from static.
  • Inheriting just to reuse code. "Thermostat extends Light, because both switch on and off" saves a few lines and breaks the is-a test. Every caller of Light would then also receive thermostats. If the sentence "X is a Y" sounds wrong, do not extend. Lesson 03 shows the better tool.

8Key takeaways

  • Inheritance (extends) lets a subclass receive a superclass's fields and methods, so shared code is written once. It fits only when "child is a parent" is true in plain English.
  • An abstract class is a parent with blanks (abstract methods) that every concrete child must fill in. Unlike an interface, it can hold fields, constructors and real code, but a class can extend only one.
  • The compiler checks a call against the declared type, and the JVM then runs the method found first when searching upward from the actual object's class. This is dynamic dispatch, the machinery of polymorphism.
  • Overriding (same signature in a child) is chosen at run time by the actual object, while overloading (same name, different parameters) is chosen at compile time by the declared types. Mixing them up causes the classic Vet trap.
  • Inheritance is never free. It couples child to parent internals, allows one parent only, is fixed at compile time, and hands down everything. Use it deliberately, mark every override with @Override, and never call overridable methods from a constructor.
