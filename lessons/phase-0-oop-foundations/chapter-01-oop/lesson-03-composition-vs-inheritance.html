Composition versus Inheritance

A subclass can break when only its parent changes. The cure is to build objects out of other objects, "has-a" instead of "is-a," and pass the work along.

Kata package: com.katas.composition (wrong way in com.katas.composition.naive).
Smart Home Hub: created activity/ActivityLog.java, activity/LoggedDevice.java, and their tests; modified Main.java. Devices untouched.
Prerequisites: Lesson 01, Lesson 02 — Inheritance and Polymorphism.

1The pain

Lesson 02 warned that a child depends on its parent's insides. Here is that warning coming true, in a class nobody touched.

A teammate owns a Playlist class. You need a playlist that also counts how many songs were ever added. Inheritance looks perfect: extend it, override the two adding methods, count, and call super.

public class CountingPlaylist extends Playlist {
    private int addedCount;
    @Override public void add(String song) {
        addedCount++;  super.add(song);
    }
    @Override public void addAll(List<String> newSongs) {
        addedCount += newSongs.size();  super.addAll(newSongs);
    }
}

You test it: add three songs with addAll, and the counter says 3. Shipped. A month later your teammate tidies their class. Playlist.addAll used to store each song directly; now it reuses its own add method, to avoid repeating itself:

// before                          // after
for (String song : newSongs) {     for (String song : newSongs) {
    songs.add(song);                    add(song);       // "cleaner"
}                                  }

Playlist still behaves exactly as before, and its own tests stay green. You changed nothing. But:

Predicted symptom

Inheritance: 3 songs in the list, counter says 6

The pain has a name: a subclass broken by a change made only to its parent is the fragile base class problem ("base class" is another word for superclass). It is not a careless-teammate problem. The tidy-up was a perfectly reasonable change to Playlist. The fault is the relationship: inheritance let a private detail of the parent ("does addAll call add?") become part of how the child behaves.

Full wrong-way code: katas/src/main/java/com/katas/composition/naive/Playlist.java and CountingPlaylist.java

2Real-world analogy

A hired driver versus a transplanted engine. To go faster, you could rebuild your car around a racing engine, welding your own parts to its insides. Now every change the engine maker makes inside the engine might break your welds. Or you could hire a driver with a fast car. You tell the driver where to go, the driver handles the rest, and you never look under their bonnet. If you want a different car tomorrow, you hire a different driver; nothing is welded.

In real lifeIn Java
Welding your parts onto the engine's insidesInheritance: the child is built into the parent's internals
Hiring a driverComposition: holding another object in a field
Telling the driver where to goDelegation: passing the call on to the held object
Never looking under their bonnetUsing only the held object's public contract
Hiring a different driver tomorrowSwapping the held object while the program runs

3The concepts explained

3.1 Why the subclass broke, step by step

Trace counting.addAll(["Intro", "Verse", "Outro"]) after the tidy-up. There is only one object here: a CountingPlaylist, which contains a Playlist part.

  1. CountingPlaylist.addAll runs: addedCount += 3 (counter: 3), then super.addAll(…).
  2. Playlist.addAll runs, using the parent's code. Its loop calls add("Intro").
  3. add(...) means this.add(...), and this is the CountingPlaylist. Dynamic dispatch searches from the actual class, so it finds CountingPlaylist's add: counter 4, then it stores the song.
  4. The same happens for "Verse" (counter 5) and "Outro" (counter 6).

When a class's methods call each other, that habit is called self-use. A parent's self-use is invisible from outside and can change at any time. Yet every subclass that overrides one of those methods gets pulled into it. Reusing a class by extending it, and so depending on how it works inside, is called white-box reuse: you can see into the box, and you end up depending on what you see.

3.2 The cure: hold an object, and pass the work along

Instead of being a playlist, the counter can have one. It keeps a real playlist in a private field. When asked to add songs, it counts and then hands the request to that playlist. Building an object out of other objects held in its fields is called composition, and the relationship is has-a ("a CountingPlaylist has a playlist"), as opposed to is-a. Handing a request on to the held object, so it does the real work, is called delegation.

public class CountingPlaylist implements SongList {
    private final SongList inner;                // HAS-A
    public void addAll(List<String> newSongs) {
        addedCount += newSongs.size();
        inner.addAll(newSongs);                    // DELEGATE
    }
}

Now trace the same call. There are two objects: the counter and the playlist inside it.

  1. counter.addAll: counter 3, then inner.addAll(…).
  2. Playlist.addAll runs on the inner object. Its loop calls add("Intro"), meaning this.add, and this is now the Playlist. The counter is a separate object that Playlist does not even know exists.
  3. Playlist's own add runs three times. Nothing comes back to the counter, which still says 3.

The playlist's self-use stays inside the playlist. The counter depends only on the public contract, not on how the playlist works inside. Reusing an object only through its public contract, without seeing inside, is called black-box reuse.

3.3 The contract makes the wrapper a stand-in

A CountingPlaylist that only has a playlist is no longer a playlist. Any code expecting a playlist would refuse it. The fix is Lesson 01's tool: a shared interface, SongList. Both Playlist and CountingPlaylist implement it. The counter is a SongList (so clients accept it) and holds a SongList (so it can wrap any of them). An object that keeps the same contract as the object it holds, and forwards calls to it, is called a wrapper. This "implements X and holds an X" shape is so useful that it returns as a named pattern in Lesson 19.

That shape gives composition two powers inheritance lacks:

  • Chosen while the program runs. new CountingPlaylist(new Playlist()) picks the inner object when the code runs. Tomorrow it can wrap a different SongList, with no new class.
  • Stackable. A wrapper is itself a SongList, so wrappers can wrap wrappers: new CountingPlaylist(new CountingPlaylist(new Playlist())). Features combine by stacking, not by writing a subclass for every combination.

3.4 The class explosion that composition avoids

Suppose the hub has 3 device kinds (light, thermostat, lock) and 2 optional features (logging, scheduling). With inheritance, every combination you might need is its own subclass: LoggingLight, ScheduledLight, LoggingScheduledLight, then the same three again for thermostats and for locks. Too many classes, caused by multiplying independent choices, is called a class explosion.

Inheritance (one subclass per combination)Composition (one wrapper per feature)
3 devices, 2 features3 × 3 = 9 extra classes2 wrappers
Add a 3rd feature3 × 7 = 21 extra classes3 wrappers
Add a 4th device+7 more classes0 new wrappers

(How the numbers come about: with 2 features there are 3 non-empty combinations, "just A," "just B," and "A and B." With 3 features there are 7. Multiply by the number of device kinds. Composition needs one wrapper per feature, whatever the number of devices.)

3.5 The rule, and where it comes from

In 1994 four authors (Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, soon nicknamed the "Gang of Four") wrote the book Design Patterns. Lesson 12 tells its story. Before their first pattern, they state two principles. The first you already know from Lesson 01: program to an interface, not an implementation. The second is this lesson: favor object composition over class inheritance. Note the word favor, not always. Inheritance still has its place (Section 7). But when in doubt, has-a is the safer default.

The composed CountingPlaylist wraps a Playlist whose addAll calls add. Why doesn't the counter double-count?

Because there are two separate objects. Inside the Playlist, add(song) means the Playlist's add, since this is the Playlist. The wrapper is a different object that the Playlist has no reference to, so its internal calls cannot reach the wrapper's add. Only calls made on the wrapper are counted.

4The kata

A few JDK pieces appear here. List<String> is the JDK's ordered-list interface. The part in angle brackets says what the list holds, here text; that feature gets its own story later. ArrayList is its everyday implementation. List.of("a", "b") builds a small list that can never be changed.

// The contract that lets a wrapper stand in for the real thing.
package com.katas.composition;

// The interface type for a batch of songs.
import java.util.List;

// What any song list can do. Both the real Playlist and the CountingPlaylist
// that wraps it keep this contract, so clients cannot tell them apart.
public interface SongList {

    // Add one song.
    void add(String song);

    // Add several songs.
    void addAll(List<String> newSongs);

    // How many songs are in the list.
    int size();
}

Saved: katas/src/main/java/com/katas/composition/Playlist.java

The real list: implements SongList, a private final List<String> songs = new ArrayList<>(), and an addAll that deliberately reuses add. It is the same "tidy" style that broke the inheritance version, kept to prove composition does not care.

Saved: katas/src/main/java/com/katas/composition/CountingPlaylist.java

// The RIGHT WAY: add a feature by HOLDING a song list, not by extending one.
package com.katas.composition;

// The interface type for a batch of songs.
import java.util.List;

// A CountingPlaylist HAS A SongList inside it (composition) and passes each
// request on to it (delegation), counting along the way. It never extends
// Playlist, so Playlist's internal habits cannot reach back into it.
public class CountingPlaylist implements SongList {

    // The object we wrap and forward to. Typed by the CONTRACT, so any
    // SongList works: a Playlist today, something else tomorrow.
    private final SongList inner;

    // How many songs have been added, ever.
    private int addedCount;

    // The wrapped list is handed in from outside, so the caller chooses it.
    public CountingPlaylist(SongList inner) {
        // Keep a reference to the object we will delegate to.
        this.inner = inner;
    }

    // Count one, then forward.
    @Override
    public void add(String song) {
        // One more song added.
        addedCount++;
        // Delegate the real work to the wrapped list.
        inner.add(song);
    }

    // Count the batch, then forward.
    @Override
    public void addAll(List<String> newSongs) {
        // The whole batch counted once.
        addedCount += newSongs.size();
        // inner.addAll runs Playlist's code; when THAT code calls add(), it
        // means Playlist's own add, not ours. Nothing comes back here, so
        // nothing is counted twice.
        inner.addAll(newSongs);
    }

    // Forward the question: we store nothing ourselves.
    @Override
    public int size() {
        // The wrapped list knows its own size.
        return inner.size();
    }

    // The one thing this wrapper adds.
    public int getAddedCount() {
        // After addAll of 3 songs this returns 3.
        return addedCount;
    }
}

5Applied to the Smart Home Hub

The new requirement: the hub must keep an activity log, a record of every time a device is switched on or off. And it must work for every device kind, present and future.

The inheritance mess this invites

The tempting first move uses Lesson 02's tool:

class LoggingLight extends Light {
    @Override public void turnOn()  { super.turnOn();  /* log it */ }
    @Override public void turnOff() { super.turnOff(); /* log it */ }
}
class LoggingThermostat extends Thermostat { /* the same two overrides, copied */ }
// ...and LoggingLock, LoggingCamera, then ScheduledLight, LoggingScheduledLight...

Every smell from this lesson is there. The logging code is copied once per device kind. Section 3.4's class explosion begins with the second feature. Each Logging* class is welded to its parent's internals; if AbstractDevice.turnOff ever reused turnOn, logs would double up exactly like the playlist counter. And the choice of whether a device is logged is fixed when the code is written. The other temptation, putting logging inside AbstractDevice.turnOn, forces every device to log, always, into some shared place, with no way to opt out.

The composition cure

Two small classes in a new activity package, and no device class changes at all:

Saved: smarthome/src/main/java/com/smarthome/activity/ActivityLog.java

// Activity tracking is its own responsibility, so it gets its own package.
package com.smarthome.activity;

// The JDK's growable list, used for the private storage.
import java.util.ArrayList;
// The JDK's list interface, used in the public method's return type.
import java.util.List;

// The hub's activity history: an ordered record of what happened.
// It knows nothing about devices; it just stores lines of text.
public class ActivityLog {

    // The entries, oldest first. private: the only way in is record().
    private final List<String> entries = new ArrayList<>();

    // Add one line to the end of the history.
    public void record(String entry) {
        // Append it to the internal list.
        entries.add(entry);
    }

    // Read the history. Returns a COPY that cannot be changed, so no caller
    // can quietly delete or rewrite history (encapsulation, Lesson 01).
    public List<String> entries() {
        // List.copyOf makes an unmodifiable snapshot of the current entries.
        return List.copyOf(entries);
    }
}

Why List.copyOf? Returning the private entries list itself would hand every caller a key to the vault: log.entries().clear() would erase history. List.copyOf returns a snapshot that refuses changes. Trying add on it throws UnsupportedOperationException, Java's standard "this object does not allow that" exception.

Saved: smarthome/src/main/java/com/smarthome/activity/LoggedDevice.java

// Lives with ActivityLog: it is the logging feature, not a kind of device.
package com.smarthome.activity;

// The contract this wrapper both keeps and holds.
import com.smarthome.devices.Device;

// Adds activity logging to ANY device by composition. A LoggedDevice IS a
// Device (it keeps the contract, so the hub cannot tell the difference) and
// HAS a Device inside it (the real one), to which it delegates every call.
// One class covers lights, thermostats, and every device kind still to come.
public class LoggedDevice implements Device {

    // The real device doing the real work. Typed by the contract, so any
    // device (even another wrapper) can be wrapped.
    private final Device inner;

    // Where switch events are written. Shared, so many devices can log to
    // one history in the order things actually happened.
    private final ActivityLog log;

    // Both parts are handed in from outside: the caller decides which
    // device gets logged, and to which log.
    public LoggedDevice(Device inner, ActivityLog log) {
        // Remember the device to delegate to.
        this.inner = inner;
        // Remember the log to write to.
        this.log = log;
    }

    // Pure delegation: the wrapper has no name of its own.
    @Override
    public String getName() {
        // Ask the real device.
        return inner.getName();
    }

    // Delegate, then record what the device now reports.
    @Override
    public void turnOn() {
        // The real device switches on, in its own way.
        inner.turnOn();
        // Record its own status line, e.g. "Hall Thermostat: regulating to 21C".
        log.record(inner.status());
    }

    // Delegate, then record.
    @Override
    public void turnOff() {
        // The real device switches off.
        inner.turnOff();
        // Record its status line, e.g. "Living Room Light: OFF".
        log.record(inner.status());
    }

    // Pure delegation.
    @Override
    public boolean isOn() {
        // The real device knows its own state.
        return inner.isOn();
    }

    // Pure delegation: logging must not change how a device describes itself.
    @Override
    public String status() {
        // Exactly the real device's status line.
        return inner.status();
    }
}

6In the wild

The JDK's own fragile base class. This lesson's playlist is a small copy of a famous real case. In Joshua Bloch's book Effective Java (the item "Favor composition over inheritance"), a counting subclass of java.util.HashSet overrides add and addAll, adds three elements, and reports six. The reason is the same as ours: HashSet inherits addAll from AbstractCollection, which loops and calls add. AbstractCollection's documentation describes that loop, but HashSet makes no promise to keep inheriting it. A future version could override addAll and silently "fix" the subclass's count, or break a different subclass. Depending on a parent's self-use is fragile in both directions. Bloch's fix is our fix: a wrapper class that holds a Set and forwards to it.

The JDK's own wrappers. Collections.unmodifiableList(list) returns an object that is a List, holds your list, forwards every read to it, and refuses every write. new BufferedReader(new FileReader("notes.txt")) wraps one reader in another to add buffering. That is the same "implements X, holds an X" shape as LoggedDevice, used across the whole java.io package (Lesson 19 traces it).

7When NOT to compose, and gotchas

Inheritance is still right sometimes

"Favor" composition does not mean "never extend." Our hub kept AbstractDevice on purpose, because it passes every check: the is-a sentence is true, the shared core (name, on/off) is stable, we own both parent and children, and children are meant to be written against it. Inheritance is fine when all of these hold: a true is-a, a parent designed for extension, both sides under your control, and a core that rarely changes. Rewriting AbstractDevice as a component "because composition is better" would add forwarding code for no pain cured. That is exactly the over-application this course warns against.

Gotchas

  • Composition costs forwarding code. LoggedDevice must forward all five Device methods, even the three it does not change. Bigger interfaces mean more boilerplate. Implementing the interface at least makes the compiler check that you forgot none.
  • The wrapper is a different object. wrapper == inner is false. Code that compares objects by identity, or that keeps a reference to the inner object and uses it directly, will skip the wrapper's behaviour. Hand out the wrapper, not the inner object.
  • The wrapper does not see the inner object's self-calls. That is what saved the counter, but it cuts both ways. If you wanted to intercept a call the inner object makes to itself, a wrapper cannot.
  • Leaking internals through a getter. Returning a private List directly lets callers change it; return a copy (List.copyOf) as ActivityLog does.
  • If you write a class others may extend, decide deliberately. Either document which methods call which (so subclasses can rely on it), or forbid extension by marking the class final. public final class Playlist means "cannot be extended" and would have made the fragile subclass impossible to write.
A teammate wants every device to be logged, always. Should logging move into AbstractDevice.turnOn/turnOff after all?

Even then, the wrapper is usually better. Logging inside AbstractDevice ties every device to a log object (where would it come from?), makes tests of a plain light produce log noise, and leaves devices outside that parent unlogged. "Always logged" is a decision about how the hub is assembled, so it belongs where devices are created: wrap every device in Main. The device classes stay simple, and the decision stays in one visible place.

8Key takeaways

  • The fragile base class problem is a subclass breaking when only its parent changes. It happens because inheritance makes the parent's self-use (which methods call which) part of the child's behaviour.
  • Composition means holding another object in a field (has-a), and delegation means passing calls on to it. Together they reuse an object only through its public contract, so its internal habits cannot reach you.
  • A wrapper keeps the same interface as the object it holds, so clients cannot tell it apart. Wrappers can be chosen while the program runs and stacked to combine features, which avoids the class explosion of one subclass per combination.
  • The Gang of Four's two founding principles are "program to an interface, not an implementation" and "favor object composition over class inheritance." Every pattern ahead builds on both.
  • "Favor" is not "always." Inheritance stays right for a true is-a with a stable core designed for extension, like AbstractDevice. Composition costs forwarding code and an extra object, so use it where a real pain asks for it.

package com.smarthome.activity;

import com.smarthome.devices.Device;

// IS a Device (keeps the contract) and HAS a Device (delegates to it).
public class SwitchCountingDevice implements Device {
    // The wrapped device: any Device, including another wrapper.
    private final Device inner;
    // How many times turnOn was called on THIS wrapper.
    private int onCount;

    public SwitchCountingDevice(Device inner) { this.inner = inner; }

    // The one method with extra behaviour: count, then delegate.
    @Override public void turnOn() { onCount++; inner.turnOn(); }

    // Everything else is pure forwarding.
    @Override public void turnOff() { inner.turnOff(); }
    @Override public String getName() { return inner.getName(); }
    @Override public boolean isOn() { return inner.isOn(); }
    @Override public String status() { return inner.status(); }

    // The feature this wrapper adds.
    public int getOnCount() { return onCount; }
}

Combining features: stack the wrappers, as in the snippet: counter → logger → light. Each call travels inward through every layer. No LoggedCountedLight class exists, and the same two wrappers combine with a thermostat, a lock, or anything else.

  1. turnOn(): the counter's onCount becomes 1. It delegates to the logger, which delegates to the Light (on), then records "Porch: ON".
  2. turnOff(): the counter only forwards. The logger switches the light off and records "Porch: OFF".
  3. turnOn(): onCount becomes 2, and the logger records "Porch: ON".
  4. status() is forwarded through both layers to the Light: "Porch: ON".

Prediction

2 switch-ons, 3 log entries
Porch: ON

The order of stacking is a real design choice. Here the counter is outermost, so it counts every turnOn before the logger even sees it; for these two features the order does not change the results.
