Objects, Encapsulation, and Interfaces

An object is data plus the behaviour that guards it. An interface is a promise about what an object can do. Together they are the foundation of every pattern in this course.

Kata package: com.katas.oopbasics (wrong way in com.katas.oopbasics.naive).
Smart Home Hub: created devices/Device.java, devices/Light.java, devices/Thermostat.java, devices/DeviceTest.java; modified Main.java.
Prerequisites: Lesson 00 — Getting Your Machine Ready.

  • What classes and objects are, and how to protect an object's data so its rules can never be broken.
  • What an interface is, and why code that uses only the interface keeps working when new classes arrive.
  • How the Smart Home Hub gets its first real code: a Device contract with a light and a thermostat.

1The pain

Here are two small pieces of code. Both work on day one. Both go wrong the moment someone else touches them.

1.1 Pain one: data with no guard

Here is a bank account. It even has a rule: withdraw never takes out more money than the account holds.

public class BankAccount {
    public int balance;                  // anyone can read AND write this

    public void withdraw(int amount) {
        if (amount <= balance) {          // the rule...
            balance = balance - amount;
        }                                  // ...and a silent "no" otherwise
    }
}

But the rule only protects code that chooses to call withdraw. Any other code can skip the rule and write the number directly:

leaky.balance = -500;   // no rule runs; nothing stops this

Predicted symptom

Naive account balance: -500

Now the account holds minus five hundred. Yet the bank's system promised that an account can never go below zero. The bug is not inside withdraw. The bug is that other code can walk around the rule. A real program has hundreds of files. You would have to search all of them to find the one that wrote that number.

1.2 Pain two: code stuck to one class

Someone writes a remote control that only works with a lamp:

void pressPower(Lamp lamp) { lamp.turnOn(); }

Now a fan arrives. pressPower cannot accept a fan. So you copy it as pressPower(Fan fan). Then a heater arrives, and you make another copy. Every new device means editing the remote. Every bug fix must be repeated in every copy.

1.3 Naming the two pains

  • The first pain is unguarded data. Any code can put an object into an impossible state.
  • The second pain is code tied to a concrete class. A concrete class is an ordinary class with real working code, like Lamp. The remote depends on which device it has. It should depend only on what a device can do.

This lesson cures both pains.

Full wrong-way code: katas/src/main/java/com/katas/oopbasics/naive/BankAccount.java

2Real-world analogy

We use two everyday pictures: a bank teller's window, and a wall socket.

  • The bank. At a bank, you never walk into the vault and count out your own cash. You go to the window and ask for an amount. The teller (the bank worker at the window) checks the rules before any money moves.
  • The wall socket. At home, a wall socket does not care what you plug into it. A lamp, a fan or a phone charger all work. Each one has the agreed plug shape, and that is all the socket needs.

3The concepts explained

3.1 Classes and objects

Programs deal with many things of the same kind: many accounts, many lamps. Writing separate code for each one would take forever. So you write one description of what every account looks like and can do. Then you build as many accounts as you need from it. It works like a cookie cutter and its cookies: one cutter, many cookies. The description is called a class. Each thing built from it is called an object. Another word for an object is an instance of that class.

BankAccount mine  = new BankAccount(100);   // one object
BankAccount yours = new BankAccount(250);   // another, with its own money

A class holds two kinds of things:

  • Data. Each account must remember its own balance. So the class declares a variable, and every object gets its own copy of it. A variable that lives inside an object is called a field. Above, mine and yours each have their own balance field.
  • Behaviour. An account must be able to do things, like hand out money. A named block of code that an object can run is called a method. For example: withdraw(30).

The constructor: how an object starts life

Every new object needs a sensible starting state. For example, an account must start with some opening balance. So Java runs a special block of code exactly once, at the moment new builds the object. This block has the same name as the class, and it returns nothing. It is called a constructor.

Inside a constructor (and inside methods), you will often see this.balance. The word this means "the object whose code is running right now." You need it when a parameter (a value handed into the method) has the same name as a field. this.balance = openingBalance means "my balance field gets the value that was handed in."

So what is an object, really? It is not just a bag of data. It is data plus the behaviour that guards that data, kept together in one place. The rest of this lesson makes the "guards" part true.

3.2 Encapsulation: hide the data, expose guarded behaviour

Java lets you choose who may touch each field and method. Two keywords do the choosing:

  • The keyword private means: only code inside the same class may read or change this field. Try account.balance = -500 from another class, and the compiler refuses: balance has private access in BankAccount.
  • The keyword public means: any code anywhere may use this method (or class). That is the teller's window.

Every object has rules that must stay true for its whole life. They must hold from the moment it is built until the program stops using it. Here are two examples:

  • For an account: "the balance is never negative."
  • For a thermostat: "the target is between 5 and 30 degrees."

A rule like this, one that must always be true, is called an invariant.

Now put the pieces together in three steps:

  1. Make the data private. Now nothing outside the class can touch it.
  2. Make every way of changing the data a public method that checks the invariant first.
  3. Make the constructor check the invariant too. It is also a way in.

Now nobody can walk around the rule, because there is no other way in. The data can only change in ways that follow the rules. Hiding an object's data behind guarded methods like this is called encapsulation.

Refusing loudly: exceptions

One question remains. What should withdraw(500) do when the account holds only 70? The naive version did nothing and said nothing. So the caller believed the money came out. That is a silent lie. The guarded version refuses loudly instead.

Java has a built-in way for a method to stop at once and report "I cannot do this, and here is why." The method creates an error object that carries a message. Then it hands that object back up to whoever called it. That error object is called an exception. Handing it back is called throwing it:

if (amount > balance) {
    throw new IllegalArgumentException("Insufficient funds: balance " + balance + ", requested " + amount);
}
balance = balance - amount;   // never reached when the throw happens

IllegalArgumentException is a ready-made exception from Java's standard library. It means "you gave me a value I cannot accept." Here is what happens to a thrown exception, step by step:

  1. The caller puts the risky call inside try { … }.
  2. If the call throws, Java skips the rest of the try block.
  3. Java jumps to the matching catch (IllegalArgumentException e) { … } block. There, e.getMessage() gives back the message text.
  4. If no code catches it, the program stops and prints the message.

Either way, nobody is left believing a lie.

Reading without writing: getters

Other code often needs to read the balance. So we add a small public method, getBalance(), that only returns the field's value. It gives read access without write access. A method like this is called a getter. (A method that changes one field, like setBalance, is called a setter.)

The guarded BankAccount has private int balance. If someone adds public void setBalance(int b) { balance = b; }, is the class still encapsulated?

Only in name. The field is still marked private, but setBalance(-500) is just balance = -500 with extra steps. Encapsulation is not about the keyword. It means every path to the data checks the invariant. A setter must check the rule (as Thermostat.setTargetCelsius does in Section 5), or it should not exist.

3.3 Interfaces: depend on what, not on which

Back to the remote from Section 1. All the remote needs is to switch a thing on. It does not care how a lamp lights up. It does not care how a fan spins. So we stop naming a class. Instead, we write down only the list of things a switchable thing must be able to do. We write no code for how:

public interface Switchable {
    void turnOn();
    void turnOff();
    boolean isOn();
    String describe();
}

A promise about what will be provided, with the how left open, is called a contract. Think of a job advert: it lists what the worker must do, not how they do it. In Java, a type that holds only a list of method promises, with no bodies, is called an interface.

A class signs the contract by writing implements Switchable after its name. The compiler checks this promise. The class must give a real body to every method the interface lists. Otherwise it will not compile. The real working code that keeps a contract is called an implementation. Lamp and Fan are two implementations of Switchable.

Above each of these methods you will see @Override. It is an annotation that says "this method keeps one that was promised." Why does that help? Say you misspell turnOn as turnon. Without @Override, Java quietly creates a second, unrelated method. With it, the compiler reports the mistake.

Now we can write the remote against the contract:

void pressPower(Switchable thing) { thing.turnOn(); }   // lamp, fan, heater: all fine

Code that uses an object is called that object's client. Here the remote is a client of Switchable. The remote names only the interface, never a concrete class. So a new device needs no change to the remote. You add a Heater implements Switchable, and the remote works with it on the first try. This habit is the most important one in the whole course. It has a name: program to an interface, not an implementation.

3.4 Polymorphism (a first look) and abstraction

Look at what thing.turnOn() does inside a loop over { new Lamp(), new Fan() }:

  1. You write the line only once.
  2. On the first pass, it runs Lamp's code.
  3. On the second pass, the very same line runs Fan's code.

Which code runs is not decided when you write the line. It is decided while the program runs, by the object that is actually there. Think of a single "play" button. It plays whatever disc is in the machine. So one call can behave in many ways, and the real object picks which way. This is called polymorphism (Greek for "many shapes"). It is the reward for programming to an interface. Lesson 02 traces, step by step, how the JVM picks the right method.

The interface also gives us one more idea. Switchable shows four simple operations. It hides everything messy behind them: wiring, motors, bulbs. Hiding complexity behind a small set of simple operations is called abstraction. A car's steering wheel is an abstraction: you turn it, and you never think about the parts underneath.

Encapsulation or abstraction? They sound alike, and both "hide" something. The difference is what they hide and why. Encapsulation hides data to protect a rule (the vault behind the teller). Abstraction hides complexity to make something easy to use (the steering wheel). Lesson 04 sharpens the difference.

A new Heater implements Switchable is added. Which of these must change: Switchable, Lamp, Fan, the loop in Main?

None of them. Heater is a new file that keeps the existing contract. The loop only says Switchable, so it works with a heater the moment one is put in the array. The only edit is adding new Heater() where the objects are created.

4The kata

The kata lives in the package com.katas.oopbasics. The wrong-way account from Section 1 is kept beside it in com.katas.oopbasics.naive.

Saved: katas/src/main/java/com/katas/oopbasics/BankAccount.java

// The RIGHT-WAY version: the same idea as naive.BankAccount, but encapsulated.
package com.katas.oopbasics;

// A bank account that guards its own data. Its invariant (the rule that must
// ALWAYS hold) is: the balance is never negative.
public class BankAccount {

    // private: only code inside THIS class can touch the balance. Every other
    // class must go through the public methods below, which enforce the rule.
    private int balance;

    // The constructor is the first guard: it refuses to build an account that
    // already breaks the invariant, so no broken account can ever exist.
    public BankAccount(int openingBalance) {
        // Reject a negative opening balance before storing anything.
        if (openingBalance < 0) {
            // throw stops the method right here and reports the problem to the
            // caller; the half-built object is thrown away and never used.
            throw new IllegalArgumentException("Opening balance cannot be negative: " + openingBalance);
        }
        // Safe to store: the invariant holds from the very first moment.
        this.balance = openingBalance;
    }

    // Add money. The only way the balance can grow.
    public void deposit(int amount) {
        // A deposit of zero or less makes no sense, so refuse it loudly.
        if (amount <= 0) {
            // Report the bad request instead of silently ignoring it.
            throw new IllegalArgumentException("Deposit must be positive: " + amount);
        }
        // The amount is valid, so apply it.
        balance = balance + amount;
    }

    // Take money out. The only way the balance can shrink.
    public void withdraw(int amount) {
        // A withdrawal of zero or less makes no sense either.
        if (amount <= 0) {
            // Refuse it, saying exactly what was wrong.
            throw new IllegalArgumentException("Withdrawal must be positive: " + amount);
        }
        // The rule that protects the invariant: never take more than is there.
        if (amount > balance) {
            // Refuse, and tell the caller both numbers so the cause is obvious.
            throw new IllegalArgumentException(
                    "Insufficient funds: balance " + balance + ", requested " + amount);
        }
        // Both checks passed, so the balance stays at zero or above.
        balance = balance - amount;
    }

    // Let other code READ the balance without being able to WRITE it.
    public int getBalance() {
        // Hand back a copy of the number; the field itself stays private.
        return balance;
    }
}

Saved: katas/src/main/java/com/katas/oopbasics/Switchable.java

// The contract every switchable thing in the kata promises to fulfil.
package com.katas.oopbasics;

// An interface lists WHAT a thing can do, never HOW. Any class that says
// "implements Switchable" must provide real code for all four methods,
// and the compiler checks that promise.
public interface Switchable {

    // Promise 1: it can be switched on. No body here: each class decides how.
    void turnOn();

    // Promise 2: it can be switched off.
    void turnOff();

    // Promise 3: it can say whether it is currently on.
    boolean isOn();

    // Promise 4: it can describe itself in one line of text.
    String describe();
}

Saved: katas/src/main/java/com/katas/oopbasics/Lamp.java

// One implementation of the Switchable contract.
package com.katas.oopbasics;

// "implements Switchable" is a promise the compiler checks: this class must
// supply all four methods the interface lists, or it will not compile.
public class Lamp implements Switchable {

    // The lamp's one piece of data. private, so only Lamp can change it.
    // Java sets a new boolean field to false, so every lamp starts off.
    private boolean on;

    // @Override says "this fulfils a method the interface promised". If the
    // name or parameters were misspelled, the compiler would report an error.
    @Override
    public void turnOn() {
        // For a lamp, switching on just means remembering that it is on.
        on = true;
    }

    // Fulfils the second promise.
    @Override
    public void turnOff() {
        // Remember that it is off again.
        on = false;
    }

    // Fulfils the third promise.
    @Override
    public boolean isOn() {
        // Report the current state without exposing the field itself.
        return on;
    }

    // Fulfils the fourth promise in a LAMP-specific way.
    @Override
    public String describe() {
        // A lamp glows or is dark. A Fan answers the same question differently.
        return "Lamp is " + (on ? "glowing" : "dark");
    }
}

(on ? "glowing" : "dark") is a short if/else that produces a value. Read it as: "if on is true, use "glowing"; otherwise use "dark"." It is called the conditional operator.

Saved: katas/src/main/java/com/katas/oopbasics/Fan.java

Fan has the same shape as Lamp. It has its own private on field and its own words: describe() returns "Fan is " + (on ? "spinning" : "still"). Neither class knows the other exists. They only share the contract.

Saved: katas/src/main/java/com/katas/oopbasics/Main.java

// The runnable demo for Lesson 01's kata.
package com.katas.oopbasics;

// Shows three things in order: the naive account being broken from outside,
// the guarded account refusing the same abuse, and one loop driving two
// different classes through one interface.
public class Main {

    // The JVM starts here when you run this class.
    public static void main(String[] args) {
        // PART 1 - the wrong way. Two classes share the name BankAccount, so we
        // write the naive one's FULL name (package + class) to pick it exactly.
        com.katas.oopbasics.naive.BankAccount leaky = new com.katas.oopbasics.naive.BankAccount(100);
        // Because balance is public, outside code can overwrite it directly,
        // skipping withdraw() and its rule entirely.
        leaky.balance = -500;
        // Prove the damage: the account is now in an impossible state.
        System.out.println("Naive account balance: " + leaky.balance);

        // PART 2 - the right way. Same starting money, guarded account.
        BankAccount safe = new BankAccount(100);
        // The only way to change the balance is through a method with rules.
        safe.withdraw(30);
        // 100 - 30 leaves 70.
        System.out.println("Guarded account balance: " + safe.getBalance());
        // try: run code that might throw an exception, so we can handle it here.
        try {
            // Asking for more than is there: withdraw() will refuse by throwing.
            safe.withdraw(500);
        } catch (IllegalArgumentException e) {
            // catch: the thrown exception lands here; print its message.
            System.out.println("Refused: " + e.getMessage());
        }
        // The refused withdrawal changed nothing: the invariant held.
        System.out.println("Balance still: " + safe.getBalance());

        // PART 3 - programming to an interface. The array's type is the
        // CONTRACT (Switchable), so it can hold any class that keeps it.
        Switchable[] things = { new Lamp(), new Fan() };
        // One loop, written once, that never mentions Lamp or Fan.
        for (Switchable thing : things) {
            // The same call; each object runs its OWN turnOn code.
            thing.turnOn();
            // The same call again; each object answers in its own words.
            System.out.println(thing.describe());
        }
    }
}

What happens when it runs

  1. new naive.BankAccount(100) runs the naive constructor, which stores 100 with no checks.
  2. leaky.balance = -500 writes the public field directly. No method runs, so no rule runs. The first line prints -500.
  3. new BankAccount(100) runs the guarded constructor. 100 is not negative, so it is stored.
  4. safe.withdraw(30): 30 is positive, and 30 is not more than 100, so the balance becomes 70. The second line prints 70.
  5. safe.withdraw(500) inside try: 500 is positive, but 500 > 70, so withdraw throws. The subtraction line never runs.
  6. The exception jumps straight to the matching catch, which prints Refused: plus the message built inside withdraw.
  7. getBalance() still returns 70. The refused call changed nothing: the invariant held.
  8. The array things holds a Lamp and a Fan. On loop pass one, thing is the lamp: turnOn() sets the lamp's own on to true, and describe() runs Lamp's code, giving Lamp is glowing.
  9. Pass two: thing is the fan. The same two lines now run Fan's code, giving Fan is spinning. That is polymorphism at work.

The tests

The tests below use one new tool: assertThrows(IllegalArgumentException.class, () -> account.withdraw(500)). It passes only if running the code throws that exception.

The piece () -> account.withdraw(500) is a small bundle of code. We do not run it ourselves. We hand it to assertThrows, so that it can run the code at the right moment and watch what happens. Such a bundle of code is called a lambda. Lambdas get their full story in the Strategy lesson. For now, read it as "the code to try."

Saved: katas/src/test/java/com/katas/oopbasics/BankAccountTest.java

// Tests live in the same package as the class they check.
package com.katas.oopbasics;

// The @Test marker that tells JUnit to run a method as a test.
import org.junit.jupiter.api.Test;

// assertEquals(expected, actual): fails the test if the two differ.
import static org.junit.jupiter.api.Assertions.assertEquals;
// assertThrows(type, code): fails the test UNLESS running the code throws
// an exception of that type.
import static org.junit.jupiter.api.Assertions.assertThrows;

// Proves the guarded BankAccount keeps its invariant: balance never negative.
class BankAccountTest {

    // The normal path: a valid withdrawal reduces the balance.
    @Test
    void withdrawReducesBalance() {
        // Start with 100.
        BankAccount account = new BankAccount(100);
        // Take 30 out through the guarded method.
        account.withdraw(30);
        // 100 - 30 = 70.
        assertEquals(70, account.getBalance());
    }

    // The other normal path: a valid deposit increases the balance.
    @Test
    void depositIncreasesBalance() {
        // Start with 100.
        BankAccount account = new BankAccount(100);
        // Put 50 in.
        account.deposit(50);
        // 100 + 50 = 150.
        assertEquals(150, account.getBalance());
    }

    // The guard that matters most: overdrawing is refused AND changes nothing.
    @Test
    void overdrawIsRefusedAndBalanceIsUnchanged() {
        // Start with 100.
        BankAccount account = new BankAccount(100);
        // () -> account.withdraw(500) is a small bundle of code handed to
        // assertThrows, which runs it and checks that it throws.
        assertThrows(IllegalArgumentException.class, () -> account.withdraw(500));
        // The refused request must leave the balance exactly as it was.
        assertEquals(100, account.getBalance());
    }

    // The constructor guard: a broken account can never be created.
    @Test
    void negativeOpeningBalanceIsRefused() {
        // Building an account with -1 must throw, so no object is ever made.
        assertThrows(IllegalArgumentException.class, () -> new BankAccount(-1));
    }

    // Nonsense amounts are refused instead of silently doing something odd.
    @Test
    void nonPositiveAmountsAreRefused() {
        // Start with 100.
        BankAccount account = new BankAccount(100);
        // A zero deposit must be refused.
        assertThrows(IllegalArgumentException.class, () -> account.deposit(0));
        // A negative withdrawal (which would ADD money) must be refused.
        assertThrows(IllegalArgumentException.class, () -> account.withdraw(-20));
        // Neither refused request changed anything.
        assertEquals(100, account.getBalance());
    }
}

5Applied to the Smart Home Hub

The hub's whole job is to control many kinds of device: lights today, and thermostats, locks and cameras later. Suppose the hub's code named Light and Thermostat everywhere. Then every new device would mean editing the hub. That is exactly pain two. So the hub's very first code is a contract. We add it because the hub really needs it, not just for practice.

Saved: smarthome/src/main/java/com/smarthome/devices/Device.java

// Device-related code lives in its own package, grouped by responsibility.
package com.smarthome.devices;

// THE hub's central contract: what every device, of any kind, promises it
// can do. The rest of the hub talks to devices ONLY through this interface,
// so new device kinds can be added without touching the code that uses them.
public interface Device {

    // Every device has a human-readable name, e.g. "Living Room Light".
    String getName();

    // Every device can be switched on (what "on" means is each device's business).
    void turnOn();

    // Every device can be switched off.
    void turnOff();

    // Every device can report whether it is currently on.
    boolean isOn();

    // Every device can summarise itself in one line for the hub to print.
    String status();
}

Saved: smarthome/src/main/java/com/smarthome/devices/Light.java

Light has the same shape as the kata's Lamp, plus a name. It has a private final String name and a private boolean on. Its status() returns text like "Living Room Light: ON".

The new word is final. A field marked final gets its value only once, in the constructor. It can never change after that. So nobody can rename a light by accident.

The thermostat is more interesting, because it has a real invariant to guard:

Saved: smarthome/src/main/java/com/smarthome/devices/Thermostat.java

// Same package as the Device contract it fulfils.
package com.smarthome.devices;

// A device with extra data (a target temperature) and an invariant to guard:
// the target always stays between MIN_CELSIUS and MAX_CELSIUS.
public class Thermostat implements Device {

    // static final: one fixed value shared by every thermostat (a constant).
    // The lowest target we accept, so pipes never freeze.
    private static final int MIN_CELSIUS = 5;

    // The highest target we accept, so nobody cooks the house by typo.
    private static final int MAX_CELSIUS = 30;

    // The thermostat's name, set once and never changed.
    private final String name;

    // Whether it is regulating. Starts false, like every device.
    private boolean on;

    // The temperature it aims for. private, so only the guarded methods below
    // can change it, and the invariant always holds.
    private int targetCelsius;

    // Build a thermostat with a name and a starting target.
    public Thermostat(String name, int targetCelsius) {
        // Remember the name.
        this.name = name;
        // Reuse the guarded setter, so the constructor obeys the SAME rule as
        // every later change; one rule, written once.
        setTargetCelsius(targetCelsius);
    }

    // Change the target, but only to a sensible value.
    public void setTargetCelsius(int targetCelsius) {
        // Refuse anything outside the allowed range...
        if (targetCelsius < MIN_CELSIUS || targetCelsius > MAX_CELSIUS) {
            // ...loudly, naming the bad value and the allowed range.
            throw new IllegalArgumentException("Target must be " + MIN_CELSIUS + "-" + MAX_CELSIUS
                    + "C, got " + targetCelsius);
        }
        // The value is valid, so store it.
        this.targetCelsius = targetCelsius;
    }

    // Read the target without being able to change it from outside.
    public int getTargetCelsius() {
        // Hand back a copy of the number.
        return targetCelsius;
    }

    // Fulfils the contract: report the name.
    @Override
    public String getName() {
        // Return the private name.
        return name;
    }

    // Fulfils the contract: start regulating.
    @Override
    public void turnOn() {
        // Remember that it is active.
        on = true;
    }

    // Fulfils the contract: stop regulating.
    @Override
    public void turnOff() {
        // Remember that it is idle.
        on = false;
    }

    // Fulfils the contract: report the state.
    @Override
    public boolean isOn() {
        // Return the current state.
        return on;
    }

    // Fulfils the contract in a thermostat-specific way.
    @Override
    public String status() {
        // When on, say what it is aiming for; when off, just say OFF.
        return on ? name + ": regulating to " + targetCelsius + "C" : name + ": OFF";
    }
}

Two new words appear here:

  • A field marked static belongs to the class itself, not to each object. So there is one shared copy instead of one copy per object.
  • A static final field is therefore one fixed value that every object shares. It is called a constant. By custom, we write constants in CAPITALS, like MIN_CELSIUS.

Also notice that the constructor calls setTargetCelsius. It does not copy the value itself. So the rule is written once, and it guards both doors: the constructor and the setter.

6In the wild

You will meet "program to an interface" in the first Java you ever read in a real project:

List<String> names = new ArrayList<>();   // the variable is typed by the CONTRACT
names.add("Ada");

java.util.List is an interface. It is a contract for "an ordered collection you can add to, read by position, and loop over." ArrayList and LinkedList are two implementations with very different insides. The variable's type says List. So you can switch implementations by changing one word on the right-hand side. None of the code that uses names notices. (The <String> part says "a list of text." That feature gets its own story later.)

The JDK is full of this shape. A few more examples:

  • Map (a lookup table from keys to values), implemented by HashMap;
  • Set (a collection with no duplicates), implemented by HashSet;
  • Runnable and Comparable, small contracts that many classes keep.

Teams check each other's code before it is accepted. This is called a code review. In code reviews, a field written as ArrayList<String> names = new ArrayList<>() often gets the comment "type it as List." In job interviews, "what is the difference between encapsulation and abstraction?" is a classic first question. Section 3.4 is your answer. One hides data to protect rules. The other hides complexity to make something easy to use.

7Gotchas and common mistakes

  • "Private field + getter + setter" is not automatically encapsulation. Many tools create a getter and a setter for every field, so people think that is the rule. But a setter with no check is a public field in disguise. Only add a setter if it guards the invariant. Often there should be none. (BankAccount has deposit and withdraw, not setBalance.)
  • Refusing silently. The naive withdraw did nothing when it could not do the job. So the caller believed it worked. When a request breaks the rules, throw an exception. Give it a message that names the bad value.
  • Forgetting that the constructor is a door too. Suppose every method checks the rule, but the constructor stores anything. Then an object can be born broken. Check the invariant in the constructor too. The best way is to reuse the same guarded method, as Thermostat does.
  • Typing variables by the concrete class out of habit. Lamp lamp = new Lamp() works, but it ties that code to Lamp. If you only use the contract's methods, give the variable the type Switchable.
  • An interface for everything. This is the opposite mistake: wrapping every class in an interface "just in case." An interface is worth it in two cases. Either there is a real second implementation. Or a client truly must not know which one it has (like the hub's loop). An interface with one implementation, and no second one ever coming, is just an extra file to read. Here the course's big theme appears for the first time: every abstraction costs something, so pay only when a real pain asks for it.

8Key takeaways

  • An object is data plus the behaviour that guards it. Fields hold the data. Methods are the only way to act on it. The constructor sets up a valid starting state.
  • Encapsulation means the fields are private and every way to change them is a guarded public method. Then an invariant (like "balance never negative") cannot be walked around.
  • When a request breaks the rules, refuse it loudly: throw an exception with a clear message. Never just do nothing.
  • An interface is a contract. It says what an object can do, never how. If client code uses only the interface, it works with every implementation, now and in the future.
  • Polymorphism means one call runs different code, depending on the actual object. It is the reward for programming to an interface. But an interface adds an extra layer, so add one only when a real second implementation or a real client need is there.

package com.smarthome.devices;

// A third device kind; it keeps the same Device contract.
public class Speaker implements Device {
    // The invariant's limits, as shared constants.
    private static final int MIN_VOLUME = 0;
    private static final int MAX_VOLUME = 100;
    // Name set once; state hidden.
    private final String name;
    private boolean on;
    private int volume;

    // The constructor reuses the guarded setter: one rule, two doors.
    public Speaker(String name, int volume) {
        this.name = name;
        setVolume(volume);
    }

    // The only way to change the volume, and it checks the range first.
    public void setVolume(int volume) {
        if (volume < MIN_VOLUME || volume > MAX_VOLUME) {
            throw new IllegalArgumentException("Volume must be 0-100, got " + volume);
        }
        this.volume = volume;
    }

    @Override public String getName() { return name; }
    @Override public void turnOn() { on = true; }
    @Override public void turnOff() { on = false; }
    @Override public boolean isOn() { return on; }

    // Speaker-specific words for the shared status() promise.
    @Override
    public String status() {
        return on ? name + ": playing at volume " + volume : name + ": OFF";
    }
}

Which existing files change? Only one line in one file: the array in Main gains new Speaker("Kitchen Speaker", 40) (and an import). Device, Light, Thermostat and the loop are untouched. That is the whole point of programming to an interface. (If your answer also changed the loop, look again: the loop only says Device.)

11Key words

Class
One description (like a cookie cutter) from which many objects of the same kind are built.
Object (instance)
One thing built from a class with new. It holds its own copy of the fields.
Field
A variable that lives inside an object, like balance.
Method
A named block of code an object can run, like withdraw(30).
Parameter
A value handed into a method or constructor when it is called.
Constructor
The special block that runs once when new builds an object, to give it a valid start.
this
Inside a class's code: "the object whose code is running right now."
private / public
private: only code in the same class may use it. public: any code may use it.
Invariant
A rule about an object that must always be true, like "balance is never negative."
Encapsulation
Hiding an object's data behind guarded methods, so it can only change by the rules.
Exception
An error object a method throws to say "I cannot do this, and here is why."
try / catch
try runs risky code; catch handles an exception if one is thrown.
Getter / setter
A small method that only reads one field (getter) or changes one field (setter).
Contract
A promise about what will be provided, with the how left open.
Interface
A Java type that is only a list of method promises, with no bodies: a contract in code.
Implementation
The real working code that keeps a contract. Lamp implements Switchable.
implements
The keyword by which a class promises to provide every method an interface lists.
@Override
An annotation meaning "this method keeps a promised one." The compiler catches misspellings.
Concrete class
An ordinary class with real working code, which you can build objects from.
Client
Any code that uses an object.
Program to an interface
Let client code name only the contract, never a concrete class, so new classes need no client changes.
Polymorphism
One call that runs different code, depending on the real object there at run time.
Abstraction
Hiding complexity behind a few simple operations, like a steering wheel.
Conditional operator
A short if/else that gives a value: on ? "ON" : "OFF".
Lambda
A small bundle of code handed to something else to run later, like () -> account.withdraw(500).
final field
A field that gets its value only once, in the constructor.
static / constant
static: one copy shared by the whole class. A static final field is a constant, written in CAPITALS.

12Quick recap

  • An object is data plus the methods that guard it; the constructor gives it a valid start.
  • Make fields private and check every change, so an invariant can never be broken.
  • When a request breaks a rule, throw an exception instead of failing silently.
  • An interface says what, not how; code that uses only the interface works with every implementation.
  • Add an interface only when a real second implementation or a real client need exists.
