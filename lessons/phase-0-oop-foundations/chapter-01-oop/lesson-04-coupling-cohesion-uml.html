Phase 0 · Chapter 01 · Lesson 04

Coupling, Cohesion, and Reading UML

The two measures every good design improves, the vocabulary of code rot, and the diagram language every pattern in this course is drawn in.

Kata package: com.katas.coupling (wrong way in com.katas.coupling.naive).
Smart Home Hub: no code changes; we read and measure the hub instead (Section 5 explains why).
Prerequisites: Lesson 01, Lesson 02, Lesson 03.

  • Two measures of good design: coupling (how much classes know about each other) and cohesion (how well a class sticks to one job).
  • The common names for "rotting" code, so you can spot and talk about problems.
  • How to read UML diagrams: the boxes, lines and arrowheads used in every lesson from now on.

1The pain

After three lessons, we keep saying one design is "better" than another. Better by what measure? And how do we show a design to a teammate without pasting every file?

1.1 One class doing everything

Here is a pizza shop's order code. It works:

public class OrderManager {
    public void add(String itemName, int quantity) {
        int price;
        if (itemName.equals("Margherita")) price = 9;        // the menu lives here...
        else if (itemName.equals("Pepperoni")) price = 11;
        else if (itemName.equals("Cola")) price = 3;
        else throw new IllegalArgumentException("Unknown item: " + itemName);
        total += price * quantity;                                  // ...and the order...
        itemCount += quantity;
    }
    public void placeOrder() {
        System.out.println("Order placed: " + itemCount + " items, total " + total);   // ...and the announcing
    }
}

1.2 Three ordinary requests

Now three ordinary requests arrive in one week:

  1. Add a dessert section to the menu.
  2. Announce orders by text message instead of on the screen.
  3. The test team asks: "can we check what placeOrder announced, without reading the console?" (The console is the text window where System.out.println prints.)

Every one of them lands on OrderManager:

  • The dessert means editing the ladder of if prices.
  • The text message means editing placeOrder.
  • The test cannot check the announcement at all, because the code always prints straight to System.out.

Three unrelated jobs live in one class, so every change touches it. And one of its jobs is stuck to one fixed output channel.

Predicted symptom

3 unrelated changes → 3 edits to the same class → 3 chances to break the other 2 jobs
1 test the team wants → impossible without capturing the console

1.3 What this lesson gives you

This lesson names the two measures this code fails. It has low cohesion and tight coupling (both explained in Section 3). It also gives the "rot" its proper names. And it teaches a picture language, UML, that shows a better design at a glance.

2Real-world analogy

A restaurant kitchen. A kitchen is split into stations: work areas, each with its own cook.

  • In a good kitchen, each station does one thing. The pastry station makes desserts, and the grill grills. That is cohesion.
  • Stations talk to each other only through order tickets, left at a shared counter. They never walk over and rearrange each other's fridges. That is loose coupling. Hire a new grill chef, and the pastry station never notices.
  • When the head chef explains the kitchen to a new cook, they don't show every pan. They sketch the stations and arrows on a whiteboard. That sketch is UML.

3The concepts explained

3.1 Coupling: how much one piece knows about another

If class A uses class B, then A knows something about B. It might know B's name, B's methods, or even B's insides. The more A knows, the more likely a change to B forces a change to A. In Lesson 01, the remote knew the exact class Lamp. So a fan forced a new remote method.

How strongly one piece of code depends on another is called coupling. You measure it by how often a change in one forces a change in the other. Little knowledge means loose coupling. A lot of knowledge means tight coupling. Think of two train carriages: tightly coupled carriages move together, whether you like it or not.

Coupling comes in degrees. You have already met every one of them in this course:

A knows about B…Example from the courseCoupling
B's private data, and changes it directlyleaky.balance = -500 (Lesson 01 naive)Tightest
How B's methods call each other insideCounting subclass vs Playlist's self-use (Lesson 03)Very tight

Only a value B passes in, used brieflycheckout.place(order) reads two numbersLoosest

Zero coupling is not the goal. Classes that work together must know something about each other. The goal is that each one knows as little as possible, through the narrowest door.

3.2 Cohesion: how well the insides of one piece belong together

Look inside a single class and ask: do all of its fields and methods serve one purpose? Compare two classes:

  • ActivityLog from Lesson 03 records entries and returns them, nothing else. Every line serves one purpose: "keep the history."
  • OrderManager mixes menu prices, order totals and console output. Those are three purposes, and they change for three different reasons.

How strongly the parts inside one class belong to a single, clear purpose is called cohesion. One purpose means high cohesion. A bag of unrelated jobs means low cohesion. Think of a toolbox drawer that holds only screwdrivers, versus a kitchen drawer full of random odds and ends.

The one-sentence test

Here is a quick test: describe the class in one sentence, without using "and."

  • "An Order keeps its lines and adds them up" passes. (Adding them up is part of keeping an order.)
  • "OrderManager knows prices and totals orders and prints announcements" fails three times.

Classes named Utils, Helper or Manager often fail this test. The vague name hides the fact that there is no single purpose.

Coupling or cohesion? They are easy to mix up. Coupling looks between classes: how much does one know about another? You want it low (loose). Cohesion looks inside one class: do its parts share one purpose? You want it high. A memory trick: coupling = "how tied am I to others," cohesion = "how together am I inside."

3.3 Why "loose coupling, high cohesion" is the goal of every pattern

Put the two together and you get the result that matters: a change stays local. That means a change touches only one small area. Here is why:

  • High cohesion means each kind of change has one obvious place to go.
  • Loose coupling means that change does not spread out to other classes.

In the improved kata, each change touches one small place. A new dessert is a new MenuItem. A text message is a new Notifier. The test plugs in a Notifier that records messages.

The price: indirection

Every principle and pattern ahead moves toward this goal, aimed at one kind of change. And every one charges the same price. It adds an extra interface or class between the caller and the work. That extra step is called indirection. Think of asking a receptionist to pass a message, instead of walking straight into someone's office.

The improved kata has nine small classes, where the naive one had one. That trade is worth it only when the changes really come. Section 7 says when they don't.

Lesson 03's LoggedDevice holds an ActivityLog (a concrete class) and a Device (an interface). Which link is tighter, and does it matter?

The link to ActivityLog is tighter. LoggedDevice names its exact class. So a different kind of log would mean editing LoggedDevice. The link to Device is loose, since any device fits.

Does it matter? Not yet. There is only one kind of log, and nobody has asked for another. Loosening it now would be indirection with no pain to cure. If a second kind of log ever appears, that is the moment to put an interface there.

3.4 The vocabulary of rot: smells

Bad design rarely announces itself. Instead, it shows up as small signs on the surface. For example: a long ladder of if-else, a class you dread opening, or a fix you keep having to repeat. Such a sign usually points to a deeper design problem. It is called a code smell. Like a real smell in a kitchen, it is a hint to investigate, not proof.

Robert C. Martin, a well-known writer on software design, gathered the bigger, design-wide smells into a list of seven design smells. You have met every one already:

RigidityHard to change: one change forces a cascade of othersEvery new device needing a new pressPower (Lesson 01)

ImmobilityA useful part can't be reused elsewhere, because it is tangled with the restOrderManager's prices can't be reused by a menu screen

Notice that "needless complexity" is on the list. Over-designing is rot too. From here on, every pattern lesson starts by naming the smell it cures.

3.5 Reading a UML class diagram

Teams need to talk about designs without pasting code. In the 1990s, people merged several competing diagram styles into one standard picture language for software. That language is called UML (Unified Modeling Language). It has many kinds of diagram, but two matter for this course:

  • A picture of the classes and how they are linked is called a class diagram.
  • A picture of which object calls which, in time order, is called a sequence diagram (see 3.6).

One box = one class

A class box has up to three compartments, stacked on top of each other:

  1. the class name;
  2. the fields;
  3. the methods.

Fields and methods together are called members. Each member starts with a symbol that says who may use it:

  • + means public.
  • - means private.
  • # means protected.
  • ~ means package-private. That is what you get when you write no access keyword at all. Only classes in the same package can use the member. OrderLine's constructor is package-private, so only Order (in the same package) creates lines.

Types come after a colon: - price : int means "a private field called price, of type int." + total() : int means "a public method total that returns an int."

Three more marks to know:

  • An italic name (often with «abstract» above it) means an abstract class.
  • «interface» above the name means an interface.
  • An underlined member is static.

Diagrams usually show only the members that matter to the point being made.

The six relationship lines

The lines say how classes know each other. Each line has its own style and arrowhead. Read each one as a sentence, and remember the code it comes from:

The arrow always points from the class that knows to the class that is known. Pizza knows its parent. But MenuItem has no idea which children exist. So the arrows show the direction of dependency. They also show which way a change can spread: a change at the arrowhead end can force a change at the tail end.

Numbers at the end of a line give the multiplicity: how many objects take part.

  • 1 means exactly one.
  • 0..1 means none or one.
  • * means any number.
  • 1..* means at least one.

Aggregation or composition? Both use a diamond at the "whole" end. Ask one question: who created the parts, and do they die with the whole? If the whole creates the parts and they die with it, that is composition (filled diamond), like a house and its rooms. If the parts were made elsewhere and can outlive the whole, that is aggregation (hollow diamond), like a team and its players.

The line between aggregation and plain association is famously blurry. The UML standard itself defines aggregation only loosely, and many teams never draw the hollow diamond. This course uses it only when "a whole gathering independent parts" is the point. Composition's filled diamond, on the other hand, is exact: the whole creates the parts, and they die with it.

Reading a whole diagram

Here is the improved kata as one diagram. Read it aloud, one line at a time, before you read the code in Section 4. If your sentences match the code, you can read UML.

In the diagram, why is the line from Checkout to Order dashed, but the line from Checkout to Notifier solid?

Checkout only receives an Order as a parameter of place, and forgets it afterwards. That is a dependency (dashed, "uses briefly"). But it keeps the Notifier in a field for its whole life. That is an association (solid, "holds a reference to"). Same class, two different strengths of knowing.

3.6 Reading a UML sequence diagram

A class diagram shows structure. It is like a frozen photo. It cannot show what happens when checkout.place(order) runs: who calls whom, and in what order. A sequence diagram can. It is more like a comic strip, read from top to bottom. Here are its parts:

  • Each object taking part gets a box at the top, written name : Class. A dashed line drops down from the box. That line is the object's lifeline. Time flows downward.
  • A solid arrow with a filled head is a message: one object calling a method on another, labelled with the call.
  • A dashed arrow back is a return, labelled with the value that comes back.
  • A thin bar on a lifeline shows when that object is busy running a method. It is called an activation.
  • A labelled box drawn around some messages, such as loop [each line], means "these repeat." It is called a frame. Other frames include alt (if/else) and opt (if).

Read it aloud, step by step:

  1. Main asks checkout to place the order.
  2. Checkout asks the order for its item count (3), then for its total.
  3. To work out the total, the order asks each line for its subtotal (18, then 3). It returns 21.
  4. Checkout sends one message to the notifier, and returns.

Notice what the picture proves: checkout's only arrows go to order and notifier. You can see low coupling: few arrows leave each lifeline.

4The kata

The kata lives in package com.katas.coupling. It splits the naive OrderManager into small classes. Each one does one job. They know each other only through the narrowest door. Here are the files, and the diagram arrow each one stands for:

  • Saved: katas/src/main/java/com/katas/coupling/MenuItem.java Abstract parent: private name and price, getters, abstract category().
  • Saved: katas/src/main/java/com/katas/coupling/Pizza.java and Drink.java: extends MenuItem, returning "pizza" / "drink". These are the inheritance lines.
  • Saved: katas/src/main/java/com/katas/coupling/Menu.java Receives a List<MenuItem> in its constructor and keeps a List.copyOf. find(name) returns the match or throws. The items were made elsewhere: aggregation.
  • Saved: katas/src/main/java/com/katas/coupling/Notifier.java and ConsoleNotifier.java: the one-method contract send(String), and the only class in the kata that touches System.out. This is the implementation line.

Saved: katas/src/main/java/com/katas/coupling/OrderLine.java

// One line of an order: "2 x Margherita".
package com.katas.coupling;

// An OrderLine HOLDS A REFERENCE to a MenuItem (it needs its price), but the
// item is not part of the line; it belongs to the menu. That plain "knows
// about" link is an ASSOCIATION in the diagram.
public class OrderLine {

    // Which item was ordered: the association.
    private final MenuItem item;

    // How many of it.
    private final int quantity;

    // Package-private constructor (no access keyword): only classes in this
    // package, in practice Order, can create lines.
    OrderLine(MenuItem item, int quantity) {
        // Refuse nonsense quantities, so every line is valid from birth.
        if (quantity <= 0) {
            // Loud refusal naming the bad value.
            throw new IllegalArgumentException("Quantity must be positive: " + quantity);
        }
        // Remember the item.
        this.item = item;
        // Remember the quantity.
        this.quantity = quantity;
    }

    // How many items this line contributes to the order.
    int quantity() {
        // Hand back the quantity.
        return quantity;
    }

    // This line's cost: price times quantity.
    int subtotal() {
        // Ask the associated item for its price.
        return item.getPrice() * quantity;
    }
}

Saved: katas/src/main/java/com/katas/coupling/Order.java

// An order: one job, keeping its lines and adding them up. High cohesion.
package com.katas.coupling;

// The JDK's growable list.
import java.util.ArrayList;
// The JDK's list interface.
import java.util.List;

// An Order CREATES its OrderLines itself and never hands them out, so the
// lines live and die with the order. That strong ownership is COMPOSITION
// in the diagram (the filled diamond).
public class Order {

    // The lines, created and owned by this order alone.
    private final List<OrderLine> lines = new ArrayList<>();

    // Add an item: the ORDER builds the line, so nobody else owns it.
    public void add(MenuItem item, int quantity) {
        // Create the part inside the whole.
        lines.add(new OrderLine(item, quantity));
    }

    // Total number of items across all lines.
    public int itemCount() {
        // Start from zero...
        int count = 0;
        // ...and add each line's quantity.
        for (OrderLine line : lines) {
            // Accumulate.
            count += line.quantity();
        }
        // The total item count.
        return count;
    }

    // Total price across all lines.
    public int total() {
        // Start from zero...
        int sum = 0;
        // ...and ask each line for its subtotal.
        for (OrderLine line : lines) {
            // Accumulate.
            sum += line.subtotal();
        }
        // The order's total.
        return sum;
    }
}

Saved: katas/src/main/java/com/katas/coupling/Checkout.java

// Placing an order: one job, announcing it. High cohesion.
package com.katas.coupling;

// Checkout HOLDS a Notifier for its whole life (an ASSOCIATION to an
// interface: loose coupling) and only BRIEFLY USES an Order passed into one
// method call (a DEPENDENCY: the weakest link of all).
public class Checkout {

    // The channel to announce on. Typed by the interface, handed in from
    // outside, so Checkout never knows or cares which channel it is.
    private final Notifier notifier;

    // The caller chooses the channel.
    public Checkout(Notifier notifier) {
        // Remember it.
        this.notifier = notifier;
    }

    // Announce an order. The Order is only a parameter: Checkout does not
    // keep it after this method returns.
    public void place(Order order) {
        // Ask the order for its numbers and send one message.
        notifier.send("Order placed: " + order.itemCount() + " items, total " + order.total());
    }
}

Saved: katas/src/main/java/com/katas/coupling/Main.java

// The runnable demo for Lesson 04's kata.
package com.katas.coupling;

// List.of for building the menu's item list.
import java.util.List;

// Builds the same order twice: once through the naive all-in-one class, once
// through the small cohesive classes. The output is identical; the structure
// is what differs, and that is what the lesson measures.
public class Main {

    // The JVM starts here when you run this class.
    public static void main(String[] args) {
        // NAIVE: one class does everything. Full name, because the class lives
        // in the naive sub-package.
        com.katas.coupling.naive.OrderManager manager = new com.katas.coupling.naive.OrderManager();
        // Two margheritas...
        manager.add("Margherita", 2);
        // ...and one cola...
        manager.add("Cola", 1);
        // ...announced straight to the console.
        manager.placeOrder();

        // COHESIVE AND LOOSELY COUPLED: each class does one job.
        // The items exist on their own, before any menu or order.
        MenuItem margherita = new Pizza("Margherita", 9);
        // A drink item.
        MenuItem cola = new Drink("Cola", 3);
        // The menu gathers existing items (aggregation).
        Menu menu = new Menu(List.of(margherita, cola));
        // A fresh order.
        Order order = new Order();
        // The order creates its own lines (composition).
        order.add(menu.find("Margherita"), 2);
        // A second line.
        order.add(menu.find("Cola"), 1);
        // The channel is chosen HERE, not inside Checkout.
        Checkout checkout = new Checkout(new ConsoleNotifier());
        // Same announcement as the naive version.
        checkout.place(order);
    }
}

What happens when it runs

  1. The naive OrderManager walks its if-else ladder twice (9 × 2, then 3 × 1). Its total is 21 with 3 items, and it prints straight to the console.
  2. The cohesive version builds two items, then a menu that gathers them, then an empty order.
  3. menu.find("Margherita") loops the menu's items and returns the pizza. order.add(pizza, 2) makes the order create an OrderLine. The same happens for the cola.
  4. new Checkout(new ConsoleNotifier()): the output channel is chosen in Main.
  5. checkout.place(order) runs exactly the sequence diagram in 3.6: item count 3, total 18 + 3 = 21, then one send, which ConsoleNotifier prints.

The tests: where loose coupling pays

Remember the test team's request from Section 1? With the naive class, it was impossible. Now Checkout depends only on the Notifier contract. So a test can hand it a stand-in that just remembers the messages:

Saved: katas/src/test/java/com/katas/coupling/RecordingNotifier.java

// A test-only helper, living under src/test so it never ships.
package com.katas.coupling;

// The JDK's growable list.
import java.util.ArrayList;
// The JDK's list interface.
import java.util.List;

// A Notifier that delivers nowhere: it just remembers every message, so a
// test can check exactly what Checkout "sent". This is possible ONLY because
// Checkout depends on the Notifier interface rather than on the console.
class RecordingNotifier implements Notifier {

    // Every message received, in order.
    private final List<String> messages = new ArrayList<>();

    // "Deliver" by remembering.
    @Override
    public void send(String message) {
        // Store it for the test to inspect.
        messages.add(message);
    }

    // What has been sent so far, as an unmodifiable snapshot.
    List<String> messages() {
        // A read-only copy.
        return List.copyOf(messages);
    }
}

Saved: katas/src/test/java/com/katas/coupling/CheckoutTest.java

    // Placing an order sends exactly one message with the right numbers.
    @Test
    void placingAnOrderSendsOneMessage() {
        // The recorder stands in for any real channel.
        RecordingNotifier notifier = new RecordingNotifier();
        // Checkout cannot tell it is talking to a recorder.
        Checkout checkout = new Checkout(notifier);
        // An order of 2 x 9 + 1 x 3.

        // Place it.
        checkout.place(order);
        // Exactly one message, with count 3 and total 21.

6In the wild

Loose coupling: JDBC

A database is a program that stores and finds large amounts of data. Java talks to databases through a part of the JDK called JDBC (Java Database Connectivity). It is loose coupling on a huge scale. Here is how it works:

  1. Your code calls DriverManager.getConnection(url). The url is text that says which database to reach.
  2. It gets back a java.sql.Connection. That type is an interface.
  3. The real class behind it comes from a driver: a library written by the database maker (PostgreSQL, MySQL, Oracle) that your project includes.

Your code knows only the interface. So switching databases changes the URL and the driver library, not the Java code of your queries. That is Checkout → Notifier again, with a database in place of the console.

High cohesion: Math

java.lang.Math holds only mathematical functions (max, abs, sqrt…). It has one purpose, which fits in one sentence. Compare it with the Utils class every project grows sooner or later. It holds date reading and text padding and file helpers. It is a bag of unrelated jobs that changes for every reason at once.

In design interviews, "draw the classes" means a UML class diagram. "Walk me through what happens when…" means a sequence diagram, even if no one says "UML." In code review, "this class does too much" is a cohesion complaint. "This is hard to test" is very often a coupling complaint. You now have the words for both.

7When NOT to, and gotchas

When not to decouple

Loose coupling costs indirection. Every interface is another file to read. It is another hop when you follow a bug through the code. So decouple (loosen the link) only at the joints that really change, or that tests need to swap (like Notifier). Do not decouple every class from every other "for flexibility."

Some things need no interface:

  • a small program you run once and throw away;
  • a class that will only ever have one obvious implementation;
  • a simple value like String.

Splitting a class into ten one-line classes does not raise cohesion either. It just scatters one purpose across ten files. That trap gets its own section in Lesson 05.

Gotchas

  • Arrow direction. Arrows point toward the thing depended on: child → parent, implementer → interface, user → used. Drawing them backwards reverses the meaning of the whole diagram.
  • Diamonds sit at the whole. Order ◆— OrderLine: the diamond touches the owner, not the part.
  • A diagram is not the code. Show only what matters to the point you are making. A diagram listing every getter is as hard to read as the code it replaced. But keep it honest: every arrow you do draw must exist in the code.
  • Sequence diagrams show one scenario. A scenario is one particular run of the program. The diagram in 3.6 is this order with two lines. A different order means a different run, even though the classes are the same.
  • Cohesion is not size. A big class can be cohesive (one deep purpose). A tiny class can be a bag of unrelated jobs. Use the one-sentence test, not the line count.

8Key takeaways

  • Coupling measures how much one class knows about another. Reaching into its data is the tightest. Using only an interface or a passed-in value is the loosest. Less knowledge means fewer ripples when things change.
  • Cohesion measures how well the parts inside one class serve a single purpose. If you cannot describe a class in one sentence without "and," it usually has low cohesion.
  • Loose coupling plus high cohesion keeps each change local. Every pattern ahead buys that at the price of indirection. That price is worth paying only where change really happens.
  • Design smells are the names for rot: rigidity, fragility, immobility, viscosity, needless complexity, needless repetition, opacity. Over-design is on that list too.
  • A UML class diagram shows structure through six relationship lines: inheritance, implementation, association, aggregation, composition, dependency. A sequence diagram shows the calls of one scenario in time order, top to bottom.

9Challenge

Read this code and answer two questions:

  1. Name every relationship it creates. For each one, give the UML line you would draw. Say which end gets the arrowhead or diamond.
  2. Which relationship is the tightest coupling? How would you loosen it if a test needed a fake gate?
class Car extends Vehicle { }
class Gate implements Openable { public void open() { } }

class Garage {
    private final List<Car> cars = new ArrayList<>();    // cars arrive via park()
    private final Gate gate = new Gate();                  // created right here
    public void park(Car car) { gate.open(); cars.add(car); }
    public void report(Printer printer) { printer.print(cars.size() + " cars"); }
}

(b) The tightest coupling is new Gate() inside Garage. Garage names a concrete class and creates it itself. So no other gate can ever be used. A test cannot swap in a fake gate (for example, one that records that open() was called). To loosen it, depend on the contract and let the caller choose, just like Checkout and Notifier:

private final Openable gate;                           // the contract, not the class
public Garage(Openable gate) { this.gate = gate; }      // the caller chooses

Notice how the diagram changes. The filled diamond to Gate becomes a plain association to the Openable interface. That is because Garage no longer creates or owns a specific gate. This exact move, "depend on an interface handed in from outside," becomes a named principle in Lesson 09.

11Key words

Coupling
How strongly one piece of code depends on another. Loose (low) is good.
Cohesion
How well the parts inside one class serve one clear purpose. High is good. Test: one sentence, no "and".
Console
The text window where System.out.println prints.
Indirection
An extra interface or class between a caller and the work: the price of looser coupling.
Decouple
Loosen the link between two pieces of code, usually by putting an interface between them.
Code smell
A sign on the surface of code that usually points to a deeper design problem. A hint, not proof.
Design smells
Seven names for design-wide rot: rigidity, fragility, immobility, viscosity, needless complexity, needless repetition, opacity.
UML
Unified Modeling Language: the standard picture language for software designs.
Class diagram
A UML picture of classes (name / fields / methods) and the lines that link them.
Members
The fields and methods of a class, taken together.
Visibility markers
+ public, - private, # protected, ~ package-private.
Package-private
The access you get with no keyword: only classes in the same package may use it.
Association
Solid line, open arrowhead: a class keeps a lasting reference to another (in a field).
Aggregation
Hollow diamond at the whole: the whole gathers parts made elsewhere, which can outlive it.
Composition (UML)
Filled diamond at the whole: the whole creates and owns its parts, which die with it.
Dependency (UML)
Dashed line, open arrowhead: a class uses another only briefly (a parameter or local variable).
Implementation (UML)
Dashed line, hollow triangle at the interface: "implements".
Multiplicity
Numbers at a line's end saying how many objects take part: 1, 0..1, *, 1..*.
Sequence diagram
A UML picture of one scenario's calls between objects, in time order from top to bottom.
Lifeline / message / return
An object's dashed timeline; a call (solid arrow, filled head); a value coming back (dashed arrow).
Activation / frame
The thin bar while a method runs; a labelled box (like loop) around repeated messages.
Scenario
One particular run of the program, with particular data.
Database / JDBC
A program that stores and finds lots of data; JDBC is the JDK's interface-based way to talk to one.

12Quick recap

  • Coupling is how much classes know about each other; keep it loose.
  • Cohesion is how well one class sticks to one job; keep it high (the one-sentence test).
  • Together they keep each change local, at the price of indirection.
  • Code smells are hints of rot, and over-design is a smell too.
  • UML class diagrams show structure with six kinds of line; sequence diagrams show calls in time order.
