Phase 0 · Chapter 01 · Lesson 04

Coupling, Cohesion, and Reading UML

The two measures every good design improves, the vocabulary of code rot, and the diagram language every pattern in this course is drawn in.

Kata package: com.katas.coupling (wrong way in com.katas.coupling.naive).
Smart Home Hub: no code changes; we read and measure the hub instead (Section 5 explains why).
Prerequisites: Lesson 01, Lesson 02, Lesson 03.

1The pain

Three lessons in, we keep saying one design is "better" than another. Better by what measure? And how do we show a design to a teammate without pasting every file?

Here is a pizza shop's order code. It works:

public class OrderManager {
    public void add(String itemName, int quantity) {
        int price;
        if (itemName.equals("Margherita")) price = 9;        // the menu lives here...
        else if (itemName.equals("Pepperoni")) price = 11;
        else if (itemName.equals("Cola")) price = 3;
        else throw new IllegalArgumentException("Unknown item: " + itemName);
        total += price * quantity;                                  // ...and the order...
        itemCount += quantity;
    }
    public void placeOrder() {
        System.out.println("Order placed: " + itemCount + " items, total " + total);   // ...and the announcing
    }
}

Now three ordinary requests arrive in one week. Add a dessert section. Announce orders by text message instead of on the screen. And the test team asks: "can we check what placeOrder announced, without reading the console?"

Every one of them lands on OrderManager. The dessert edits the price ladder. The text message edits placeOrder. The test cannot check the announcement at all, because it is welded to System.out. Three unrelated jobs live in one class, so every change touches it, and one of its jobs is glued to one specific output channel.

Predicted symptom

3 unrelated changes → 3 edits to the same class → 3 chances to break the other 2 jobs
1 test the team wants → impossible without capturing the console

This lesson names the two measures this code fails: it has low cohesion and tight coupling. It also gives the rot its proper vocabulary, and teaches the picture language (UML) for showing a better design at a glance.

Full wrong-way code: katas/src/main/java/com/katas/coupling/naive/OrderManager.java

2Real-world analogy

A restaurant kitchen. In a good kitchen each station does one thing: the pastry station makes desserts, the grill grills. That is cohesion. Stations talk to each other only through the order tickets at the pass, never by walking over and rearranging each other's fridges. That is loose coupling. Hire a new grill chef, and the pastry station never notices. And when the head chef explains the kitchen to a new hire, they don't walk them through every pan. They sketch the stations and arrows on a whiteboard. That sketch is UML.

3The concepts explained

3.1 Coupling: how much one piece knows about another

If class A uses class B, then A knows something about B: its name, its methods, maybe its insides. The more A knows, the more likely a change to B forces a change to A. In Lesson 01 the remote knew the exact class Lamp, so a fan forced a new remote method. How strongly one piece of code depends on another, measured by how many changes in one force changes in the other, is called coupling. Little knowledge is loose coupling; a lot is tight coupling.

Coupling comes in degrees. You have already met every one of them in this course:

A knows about B…Example from the courseCoupling
B's private data, and changes it directlyleaky.balance = -500 (Lesson 01 naive)Tightest
How B's methods call each other insideCounting subclass vs Playlist's self-use (Lesson 03)Very tight
B's exact concrete classpressPower(Lamp lamp); OrderManager → System.outTight
Only an interface B keepsThe hub's loop → Device; Checkout → NotifierLoose
Only a value B passes in, used brieflycheckout.place(order) reads two numbersLoosest

Zero coupling is not the goal. Classes that work together must know something about each other. The goal is that each knows as little as possible, through the narrowest door.

3.2 Cohesion: how well the insides of one piece belong together

Look inside a single class and ask: do all of its fields and methods serve one purpose? ActivityLog from Lesson 03 records and returns entries, nothing else; every line serves "keep the history." OrderManager mixes menu prices, order totals and console output, which are three purposes that change for three different reasons. How strongly the parts inside one class belong to a single, clear purpose is called cohesion. One purpose is high cohesion; a grab-bag is low cohesion.

A quick test: describe the class in one sentence without using "and." "An Order keeps its lines and adds them up" passes (adding up is keeping an order). "OrderManager knows prices and totals orders and prints announcements" fails three times. Classes named Utils, Helper or Manager often fail it; the vague name hides that there is no single purpose.

3.3 Why "loose coupling, high cohesion" is the goal of every pattern

Put the two together and you get the property that matters: a change stays local. High cohesion means each kind of change has one obvious place to go. Loose coupling means that change does not ripple out to other classes. In the cured kata, a new dessert is a new MenuItem, a text message is a new Notifier, and the test plugs in a recording Notifier. Each change touches one small place.

Every principle and pattern ahead is a specific move toward this goal, aimed at a specific kind of change. And every one has the same price: indirection, an extra interface or class between the caller and the work. The cured kata has nine small classes where the naive one had one. That trade is worth it only when the changes really come. Section 7 says when they don't.

Lesson 03's LoggedDevice holds an ActivityLog (a concrete class) and a Device (an interface). Which link is tighter, and does it matter?

The link to ActivityLog is tighter: LoggedDevice names its exact class, so a different kind of log would mean editing LoggedDevice. The link to Device is loose, since any device fits. Does it matter? Not yet. There is one kind of log, and no request to vary it. Loosening it now would be indirection with no pain to cure. If a second kind of log ever appears, that is the moment to put an interface there.

3.4 The vocabulary of rot: smells

Bad design rarely announces itself. It shows up as small signs on the surface: a long if-else ladder, a class you dread opening, a fix that keeps needing repeating. A surface sign in code that usually points to a deeper design problem is called a code smell. Like a real smell, it is a hint to investigate, not proof. Robert C. Martin collected the bigger, design-wide versions into seven design smells. You have met every one already:

SmellIn plain wordsWhere you saw it
RigidityHard to change: one change forces a cascade of othersEvery new device needing a new pressPower (Lesson 01)
FragilityA change breaks something in an unrelated placeThe counting subclass breaking when only Playlist changed (Lesson 03)
ImmobilityA useful part can't be reused elsewhere, because it is tangled with the restOrderManager's prices can't be reused by a menu screen
ViscosityDoing it the right way is harder than hackingEasier to add one more else if than to restructure the menu

Notice that "needless complexity" is on the list. Over-designing is rot too. From here on, every pattern lesson starts by naming the smell it cures.

3.5 Reading a UML class diagram

Teams need to talk about designs without pasting code. In the 1990s, several competing diagram styles were merged into one standard picture language for software. That language is UML (Unified Modeling Language). Of its many diagram kinds, two matter for this course. A picture of the classes and how they are linked is a class diagram. A picture of which object calls which, in time order, is a sequence diagram (3.6).

One box = one class

A class box has up to three stacked compartments: the name, then the fields, then the methods. Each member starts with a symbol for who may use it: + public, - private, # protected, ~ package-private. Package-private is Java's access level when you write no keyword: only classes in the same package can use the member. OrderLine's constructor uses it, so only Order can create lines. Types come after a colon: - price : int, + total() : int. Three more marks: an italic name (often with «abstract») means an abstract class; «interface» above the name means an interface; an underlined member is static. Diagrams usually show only the members that matter to the point being made.

The six relationship lines

The lines say how classes know each other. Each has its own line style and arrowhead. Read them as sentences, and remember the code each one comes from:

The arrow always points from the class that knows to the class that is known. Pizza knows its parent; MenuItem has no idea which children exist. So the arrows show the direction of dependency, and therefore which way a change can ripple: a change at the arrowhead end can force a change at the tail. Numbers at a line's end give the multiplicity, how many objects take part: 1 (exactly one), 0..1 (none or one), * (any number), 1..* (at least one).

Aggregation versus plain association is famously fuzzy. The UML standard itself leaves "shared aggregation" loosely defined, and many teams never draw the hollow diamond. This course uses it only when "a whole gathering independent parts" is the point. Composition's filled diamond, by contrast, is precise: the whole creates the parts and they die with it.

Reading a whole diagram

Here is the cured kata as one diagram. Read it aloud, one line at a time, before reading the code in Section 4. If the sentences match the code, you can read UML.

In the diagram, why is the line from Checkout to Order dashed, but the line from Checkout to Notifier solid?

Checkout only receives an Order as a parameter of place and forgets it afterwards, which is a dependency (dashed, "uses briefly"). It keeps the Notifier in a field for its whole life, which is an association (solid, "holds a reference to"). Same class, two different strengths of knowing.

3.6 Reading a UML sequence diagram

A class diagram shows structure, which is frozen. It cannot show what happens when checkout.place(order) runs: who calls whom, in what order. A sequence diagram can. Its parts:

  • Each object taking part gets a box at the top, written name : Class, with a dashed line dropping down from it. That line is the object's lifeline. Time flows downward.
  • A solid arrow with a filled head is a message: one object calling a method on another, labelled with the call.
  • A dashed arrow back is a return, labelled with the value that comes back.
  • A thin bar on a lifeline shows when that object is busy running a method. It is called an activation.
  • A labelled box drawn around some messages, such as loop [each line], means "these repeat." It is called a frame. Other frames include alt (if/else) and opt (if).

Read it aloud. Main asks checkout to place the order. Checkout asks the order for its item count (3), then its total. To work out the total, the order asks each line for its subtotal (18, then 3) and returns 21. Checkout then sends one message to the notifier, and returns. Notice what the picture proves: checkout's only arrows go to order and notifier. Low coupling is visible as few arrows leaving each lifeline.

4The kata

Package com.katas.coupling: the naive OrderManager split into small classes that each do one job and know each other through the narrowest door. Here are the files, and the diagram arrow each one stands for:

  • Saved: katas/src/main/java/com/katas/coupling/MenuItem.java Abstract parent: private name and price, getters, abstract category().
  • Saved: katas/src/main/java/com/katas/coupling/Pizza.java and Drink.java: extends MenuItem, returning "pizza" / "drink". These are the inheritance lines.
  • Saved: katas/src/main/java/com/katas/coupling/Menu.java Receives a List<MenuItem> in its constructor and keeps a List.copyOf; find(name) returns the match or throws. The items were made elsewhere: aggregation.
  • Saved: katas/src/main/java/com/katas/coupling/Notifier.java and ConsoleNotifier.java: the one-method contract send(String), and the only class in the kata that touches System.out. This is the implementation line.

Saved: katas/src/main/java/com/katas/coupling/OrderLine.java

// One line of an order: "2 x Margherita".
package com.katas.coupling;

// An OrderLine HOLDS A REFERENCE to a MenuItem (it needs its price), but the
// item is not part of the line; it belongs to the menu. That plain "knows
// about" link is an ASSOCIATION in the diagram.
public class OrderLine {

    // Which item was ordered: the association.
    private final MenuItem item;

    // How many of it.
    private final int quantity;

    // Package-private constructor (no access keyword): only classes in this
    // package, in practice Order, can create lines.
    OrderLine(MenuItem item, int quantity) {
        // Refuse nonsense quantities, so every line is valid from birth.
        if (quantity <= 0) {
            // Loud refusal naming the bad value.
            throw new IllegalArgumentException("Quantity must be positive: " + quantity);
        }
        // Remember the item.
        this.item = item;
        // Remember the quantity.
        this.quantity = quantity;
    }

    // How many items this line contributes to the order.
    int quantity() {
        // Hand back the quantity.
        return quantity;
    }

    // This line's cost: price times quantity.
    int subtotal() {
        // Ask the associated item for its price.
        return item.getPrice() * quantity;
    }
}

Saved: katas/src/main/java/com/katas/coupling/Order.java

// An order: one job, keeping its lines and adding them up. High cohesion.
package com.katas.coupling;

// The JDK's growable list.
import java.util.ArrayList;
// The JDK's list interface.
import java.util.List;

// An Order CREATES its OrderLines itself and never hands them out, so the
// lines live and die with the order. That strong ownership is COMPOSITION
// in the diagram (the filled diamond).
public class Order {

    // The lines, created and owned by this order alone.
    private final List<OrderLine> lines = new ArrayList<>();

    // Add an item: the ORDER builds the line, so nobody else owns it.
    public void add(MenuItem item, int quantity) {
        // Create the part inside the whole.
        lines.add(new OrderLine(item, quantity));
    }

    // Total number of items across all lines.
    public int itemCount() {
        // Start from zero...
        int count = 0;
        // ...and add each line's quantity.
        for (OrderLine line : lines) {
            // Accumulate.
            count += line.quantity();
        }
        // The total item count.
        return count;
    }

    // Total price across all lines.
    public int total() {
        // Start from zero...
        int sum = 0;
        // ...and ask each line for its subtotal.
        for (OrderLine line : lines) {
            // Accumulate.
            sum += line.subtotal();
        }
        // The order's total.
        return sum;
    }
}

Saved: katas/src/main/java/com/katas/coupling/Checkout.java

// Placing an order: one job, announcing it. High cohesion.
package com.katas.coupling;

// Checkout HOLDS a Notifier for its whole life (an ASSOCIATION to an
// interface: loose coupling) and only BRIEFLY USES an Order passed into one
// method call (a DEPENDENCY: the weakest link of all).
public class Checkout {

    // The channel to announce on. Typed by the interface, handed in from
    // outside, so Checkout never knows or cares which channel it is.
    private final Notifier notifier;

    // The caller chooses the channel.
    public Checkout(Notifier notifier) {
        // Remember it.
        this.notifier = notifier;
    }

    // Announce an order. The Order is only a parameter: Checkout does not
    // keep it after this method returns.
    public void place(Order order) {
        // Ask the order for its numbers and send one message.
        notifier.send("Order placed: " + order.itemCount() + " items, total " + order.total());
    }
}

Saved: katas/src/main/java/com/katas/coupling/Main.java

// The runnable demo for Lesson 04's kata.
package com.katas.coupling;

// List.of for building the menu's item list.
import java.util.List;

// Builds the same order twice: once through the naive all-in-one class, once
// through the small cohesive classes. The output is identical; the structure
// is what differs, and that is what the lesson measures.
public class Main {

    // The JVM starts here when you run this class.
    public static void main(String[] args) {
        // NAIVE: one class does everything. Full name, because the class lives
        // in the naive sub-package.
        com.katas.coupling.naive.OrderManager manager = new com.katas.coupling.naive.OrderManager();
        // Two margheritas...
        manager.add("Margherita", 2);
        // ...and one cola...
        manager.add("Cola", 1);
        // ...announced straight to the console.
        manager.placeOrder();

        // COHESIVE AND LOOSELY COUPLED: each class does one job.
        // The items exist on their own, before any menu or order.
        MenuItem margherita = new Pizza("Margherita", 9);
        // A drink item.
        MenuItem cola = new Drink("Cola", 3);
        // The menu gathers existing items (aggregation).
        Menu menu = new Menu(List.of(margherita, cola));
        // A fresh order.
        Order order = new Order();
        // The order creates its own lines (composition).
        order.add(menu.find("Margherita"), 2);
        // A second line.
        order.add(menu.find("Cola"), 1);
        // The channel is chosen HERE, not inside Checkout.
        Checkout checkout = new Checkout(new ConsoleNotifier());
        // Same announcement as the naive version.
        checkout.place(order);
    }
}

What happens when it runs

  1. The naive OrderManager walks its if-else ladder twice (9 × 2, then 3 × 1). Its total is 21 with 3 items, and it prints straight to the console.
  2. The cohesive version builds two items, then a menu that gathers them, then an empty order.
  3. menu.find("Margherita") loops the menu's items and returns the pizza. order.add(pizza, 2) makes the order create an OrderLine. The same happens for the cola.
  4. new Checkout(new ConsoleNotifier()): the output channel is chosen in Main.
  5. checkout.place(order) runs exactly the sequence diagram in 3.6: item count 3, total 18 + 3 = 21, then one send, which ConsoleNotifier prints.

The tests: where loose coupling pays

Remember the test team's request from Section 1? With the naive class it was impossible. Now Checkout depends only on the Notifier contract, so a test can hand it a stand-in that just remembers messages:

Saved: katas/src/test/java/com/katas/coupling/RecordingNotifier.java

// A test-only helper, living under src/test so it never ships.
package com.katas.coupling;

// The JDK's growable list.
import java.util.ArrayList;
// The JDK's list interface.
import java.util.List;

// A Notifier that delivers nowhere: it just remembers every message, so a
// test can check exactly what Checkout "sent". This is possible ONLY because
// Checkout depends on the Notifier interface rather than on the console.
class RecordingNotifier implements Notifier {

    // Every message received, in order.
    private final List<String> messages = new ArrayList<>();

    // "Deliver" by remembering.
    @Override
    public void send(String message) {
        // Store it for the test to inspect.
        messages.add(message);
    }

    // What has been sent so far, as an unmodifiable snapshot.
    List<String> messages() {
        // A read-only copy.
        return List.copyOf(messages);
    }
}

Saved: katas/src/test/java/com/katas/coupling/CheckoutTest.java

    // Placing an order sends exactly one message with the right numbers.
    @Test
    void placingAnOrderSendsOneMessage() {
        // The recorder stands in for any real channel.
        RecordingNotifier notifier = new RecordingNotifier();
        // Checkout cannot tell it is talking to a recorder.
        Checkout checkout = new Checkout(notifier);
        // An order of 2 x 9 + 1 x 3.
        Order order = new Order();
        order.add(new Pizza("Margherita", 9), 2);
        order.add(new Drink("Cola", 3), 1);
        // Place it.
        checkout.place(order);
        // Exactly one message, with count 3 and total 21.

6In the wild

JDBC, Java's database access, is loose coupling at industrial scale. Your code asks DriverManager.getConnection(url) for a connection and gets back a java.sql.Connection, which is an interface. The real class behind it comes from whichever database vendor's driver is on the classpath: PostgreSQL, MySQL, Oracle. Your code knows only the interface, so switching databases changes a URL and a driver dependency, not your queries' Java code. That is Checkout → Notifier, with a database in place of the console.

Cohesion in the JDK. java.lang.Math holds only mathematical functions (max, abs, sqrt…): one purpose, one sentence. Compare it with the Utils class every project eventually grows, which holds date parsing and string padding and file helpers. That is a grab-bag that changes for every reason at once.

In design interviews, "draw the classes" means a UML class diagram, and "walk me through what happens when…" means a sequence diagram, even if no one says "UML." In code review, "this class does too much" is a cohesion complaint, and "this is hard to test" is very often a coupling complaint. You now have the words for both.

7When NOT to, and gotchas

When not to decouple

Loose coupling costs indirection: every interface is another file to read and another hop when tracing a bug. Decouple at the joints that actually change, or that tests need to swap (like Notifier). Do not decouple every class from every other "for flexibility." A one-off script, a class with one obvious implementation forever, or a value like String needs no interface. Splitting a class into ten one-line classes does not raise cohesion either. It just scatters one purpose across ten files. That trap gets its own section in Lesson 05.

Gotchas

  • Arrow direction. Arrows point toward the thing depended on: child → parent, implementer → interface, user → used. Drawing them backwards reverses the meaning of the whole diagram.
  • Diamonds sit at the whole. Order ◆— OrderLine: the diamond touches the owner, not the part.
  • A diagram is not the code. Show what matters to the point you are making. A diagram listing every getter is as hard to read as the code it replaced. Keep it honest, though: every arrow you do draw must exist in the code.
  • Sequence diagrams show one scenario. The one in 3.6 is this order with two lines. A different order means a different run, even though the classes are the same.
  • Cohesion is not size. A big class can be cohesive (one deep purpose); a tiny class can be a grab-bag. Use the one-sentence test, not the line count.

8Key takeaways

  • Coupling measures how much one class knows about another, from reaching into its data (tightest) down to using only an interface or a passed-in value (loosest). Less knowledge means fewer ripples when things change.
  • Cohesion measures how well the parts inside one class serve a single purpose. A class you cannot describe in one sentence without "and" usually has low cohesion.
  • Loose coupling plus high cohesion keeps each change local. Every pattern ahead buys that at the price of indirection, which is worth paying only where change really happens.
  • Design smells (rigidity, fragility, immobility, viscosity, needless complexity, needless repetition, opacity) are the vocabulary of rot, and over-design is on that list too.
  • A UML class diagram shows structure through six relationship lines (inheritance, implementation, association, aggregation, composition, dependency). A sequence diagram shows one scenario's calls in time order, top to bottom.

9Challenge

Read this code and (a) name every relationship it creates, the UML line you would draw, and which end gets the arrowhead or diamond; (b) say which relationship is the tightest coupling, and how to loosen it if a test needed a fake gate.

class Car extends Vehicle { }
class Gate implements Openable { public void open() { } }

class Garage {
    private final List<Car> cars = new ArrayList<>();    // cars arrive via park()
    private final Gate gate = new Gate();                  // created right here
    public void park(Car car) { gate.open(); cars.add(car); }
    public void report(Printer printer) { printer.print(cars.size() + " cars"); }
}

(b) The tightest coupling is new Gate() inside Garage. Garage names a concrete class and creates it itself, so no other gate can ever be used. A test cannot substitute a fake gate that, say, records that open() was called. To loosen it, depend on the contract and let the caller choose, exactly like Checkout and Notifier:

private final Openable gate;                           // the contract, not the class
public Garage(Openable gate) { this.gate = gate; }      // the caller chooses

Notice how the diagram changes: the filled diamond to Gate becomes a plain association to the Openable interface, because Garage no longer creates or owns a specific gate. This exact move, "depend on an abstraction handed in from outside," becomes a named principle in Lesson 09.
